# 第4章 型付きの判断を返すモデルと advisor でゲームを遊ぶ

第4章のサンプルです。Nintendo Switch 2 の画面を、問いごとの確率を返すモデル (Decision Model) に送り続け、その確率からボタンとスティックの入力を決めて送ります。操作方法・攻略情報・目標と戦略・問題の解決の助言は、裏で動かす headless の Claude Code (advisor) が 4 つの役割に分かれて考え、役割ごとに決まったゲームの情報のファイルに書きます。このディレクトリーの uv プロジェクトにあるパッケージ [`switch2_agent`](./src/switch2_agent/) を、コマンド `switch2-agent` で実行します。

映像の受け取りとボタン入力の送信には、第2章のパッケージ [`switch2_remote`](../ch02_setup/src/switch2_remote/) をそのまま使います。第2章のデーモン (`switch2-remote-daemon`) は使いません。

## 全体の構成

```text
Nintendo Switch 2 ── HDMI ──▶ Elgato 4K X ──▶ Windows PC: ffmpeg.exe
        ▲                                              │ 標準出力パイプ
        │ USB                                          ▼
Raspberry Pi Pico 2 W                         WSL2: switch2-agent
        ▲                                       ├─ キャプチャー: フレームの履歴と、場面ごとの代表のフレームを持つ
        │ Bluetooth                             ├─ 速い層: 画像・ゲームの情報・問いを Decision Model に送り、確率から操作を決める
Windows PC: controller_bridge.ps1 ◀─────────────├─ PadOutput: 押下状態と短押しを合わせたレポートを送る
                                                └─ advisor (4 つの役割): 役割ごとに claude -p で game_notes/<ゲーム>/ の 1 ファイルを書き換える
```

1 つのプロセス (`switch2-agent`) が、次の 4 つを動かします。

- キャプチャー: 第2章の Capture に、フレームの履歴を足したものです。間引いたフレームを時刻つきで持ち、鮮明度の谷で場面を区切って、場面ごとに最も鮮明なフレームを「意味のあるフレーム」として残します。意味のあるフレームは、advisor に渡す画像に使います
- 速い層 (Pipeline): 要求を 1 つずつ Decision Model に送り、応答を受け取ったら次の要求に進みます。TypeSafe Jev (`--model jev`) では、直前の要求の応答が返るか、失敗してから 0.2 秒たつまで待ち、その後に次の要求に載せるフレームを選びます。OpenAI Decisions API (`--model decisions`) では待ちません。要求には、フレームの履歴の最新の 1 枚の画像、ゲームの情報の 4 ファイルの内容、直近 5 回の応答と送った操作の履歴 (操作と、それを送った時刻。Decision Model の失敗やブリッジの復旧待ちで押下状態を中立に戻したときは、中立に戻したことと、その理由と時刻)、系列情報 (系列情報の節を参照)、37 の問いを入れます。画像のラベルには、実行を始めてからの経過秒 (t) と何秒前の画像かを書きます。前回の操作 (前回の応答で決めた操作か、その後に中立に戻したこと) があれば、その前の画像か、後の画像かも書きます
- PadOutput: 速い層が決めた押下状態と短押しを合わせて、コントローラーのブリッジに送ります。短押しは 120 ミリ秒で離します
- advisor: 4 つの役割 (操作方法の更新、目標・戦略の更新、問題の解決の助言、攻略情報・Tips の更新) に分かれています
  - 役割ごとに Decision Model の問い (`advisor_<役割>`) があり、その問いが真になると、裏のスレッドでその役割の `claude -p` を実行します。同時に実行するのは役割ごとに 1 件で、役割どうしは並列に動きます (最大 4 件)。実行中の役割は、その役割の問いが真になっても呼びません。実行が失敗した役割 (`claude` を起動できない、タイムアウトした、終了コードが 0 以外など) も、失敗した実行が終わってから 60 秒は呼びません
  - 問いが真にならなくても、advisor が決まった秒数呼ばれていなければ、決めた役割を呼びます (advisor の強制の呼び出しの節を参照)
  - 書き換えるゲームの情報のファイルは、役割ごとに 1 つに決まっています。advisor は Skill の手順で受け持ちのファイルを書き換え、速い層は次の要求からその内容を読みます
  - advisor に渡す画像は、要求とは別に選びます。意味のあるフレームの直近 5 枚と、それより後のフレームの履歴から等間隔に選んだ 5 枚で、最大 10 枚です。1 回の要求で複数の役割を呼ぶときは、同じ画像を使い回します。呼ぶ役割が無ければ、画像を選びません

### 系列情報

要求に入れる直近 5 回の履歴は、Jev で約 2 秒分、Decisions API で約 3 秒分です。この履歴からは、同じ操作を何分も続けていることや、画面が長く変わっていないことは読み取れません。要求には、次の節からなる系列情報も入れます。使う節は起動引数 `--timeline` で選べます。既定ではすべての節を入れます。

| 節 (`--timeline` の名前) | 内容 |
|---|---|
| 操作のまとめ (`actions`) | 直近 `--timeline-window` 秒 (既定 120 秒) の操作を、同じ操作が続いた区間ごとにまとめたもの。区間ごとに、始まりと終わりの経過秒、続いた秒数、回数を書きます。スティックは傾きの大きさを除き、向きだけで比べます。区間は新しいほうから 8 つまで書きます |
| 画面の変化 (`screen`) | 最新の画面が、いつからほぼ変わっていないか。処理したフレームの縮小グレー画像を、画面が最後に変わったときのフレームと比べ、差分 (画素の差の平均) が `--screen-change-threshold` (既定 2.0) 以上になったら、画面が変わったとみなします |
| ゲームの情報の更新 (`notes`) | ゲームの情報の 4 ファイルが、それぞれ最後に書き換わった時刻 |
| advisor を呼んだ時刻 (`advisor_calls`) | 役割ごとに、advisor が最後に要求を受け付けた時刻 |
| 小目標の時刻 (`subgoals`) | strategy.md の小目標ごとに、立てた時刻と、状態が最後に変わった時刻。`小目標: <小目標> (状態: <状態>` の形の行から読みます。この形の行が無ければ、この節は入れません |

時刻は、実行を始めてからの経過秒 (t) で書きます。操作のまとめ以外の節では、何秒前かも書きます。系列情報は、直近の応答と送った操作の履歴の後ろに空行をはさんで足し、Jev では `operation_history`、Decisions API では履歴のテキストに入れます。

ゲームの情報の更新と小目標の時刻は、要求を組み立てるときに読んだ内容の変化から求めます。書き換わった時刻は、advisor がファイルを書き換えた後の、最初の要求の時刻になります。前の実行で書かれた小目標は、「実行の開始にはすでにあった」と書きます。

画面の変化の既定値 2.0 は、2026-11-14 の実機の記録から決めた値です。行き詰まっていた場面 (家の中で壁に向かって歩き続けた場面、ソフトの一覧で何も押さなかった場面、1-1 の土管の前で右を押し続けた場面) では、止まっている画面の差分が 0.8 以下 (時間の表示などの小さな変化を含む) でした。歩いたりスクロールしたりしている画面の差分は 4 以上でした。敵が動くゲームの画面 (誤って始めたマイティボンジャックで、何も押さなかった区間) では、主人公が止まっていても差分が 1.2〜2.1 になった区間があります。画面の変化の節が書くのは画面全体の変化で、主人公が動いたかどうかではありません。

### advisor の強制の呼び出し

2026-11-14 の実機の記録には、速い層が行き詰まりに気づかず、advisor の問いの確率が低いまま、advisor が 181〜397 秒呼ばれなかった実行が 3 回ありました。これに備え、どの役割の advisor も `--advisor-idle-seconds` 秒 (既定 60 秒) 要求を受け付けていなければ、問いの確率によらず、`--advisor-idle-roles` の役割 (既定は strategy と advice) を呼びます。この記録で、60 秒、呼ぶ役割を strategy だけとして見積もると、advisor が 60 秒より長く間を空けずに呼ばれていた 2 回の実行では一度も呼ばず、行き詰まっていた 3 回の実行では 2〜6 回呼びました。

- 数え始めるのは、どれかの役割の advisor が要求を受け付けた時刻です。まだどの役割も受け付けていなければ、判断のループを始めた時刻 (最初のフレームを待つ時間を含む) から数えます。advisor の問いで呼んで受け付けたときも、数え直します
- 実行中の役割と、失敗した実行の後の 60 秒の間の役割は呼びません
- 強制の呼び出しで呼んだ役割の context.md には、きっかけとして、定期の呼び出しで呼んだことと、その理由を書きます。同じ要求で問いが真になった役割は、問いで呼んだものとして扱い、きっかけには問いの確率を書きます
- `--advisor-idle-scope each` を付けると、役割ごとに数えます。その役割の advisor が `--advisor-idle-seconds` 秒受け付けていなければ、その役割を呼びます
- `--advisor-idle-seconds 0` を付けると、強制の呼び出しをしません

### 問いと操作の決め方

問いは 37 個で、答えの型は 2 つです。選択肢の問いは、「なし」(`none`) を含む選択肢の中から 1 つを選ぶ問いで、選択肢ごとの確率で答えさせます。確率の問いは、「真である確率」で答えさせます。同じボタンの押した状態と短押しや、スティックの左と右のように、同時には選ばない操作を選択肢の問いにして、矛盾する答えが出ないようにしています。

| 問い | 数 | 答えの型 | 選択肢または段階 | 操作 |
|---|---|---|---|---|
| `button_<ボタン>` | 17 | 選択肢 | `none` (押さない)、`hold` (押した状態にする)、`tap` (1 回だけ短く押す) | `hold` なら、そのボタンを押した状態にし、次の応答まで押したままにします。`tap` なら、そのボタンを 1 回だけ短く押します (120 ミリ秒)。直前の応答まで押した状態だったボタンは、100 ミリ秒離してから押します |
| `stick_<LS/RS>_<x/y>` | 4 | 選択肢 | x は `none` (左右には倒さない)、`left`、`right`。y は `none` (上下には倒さない)、`up`、`down` | スティックを、その軸の選んだ向きに倒します |
| `stick_<LS/RS>_<x/y>_at_least_<50/75/100>` | 12 | 確率 | 傾きの段階 (50%、75%、100%) | 倒す軸の傾きの大きさを決めます |
| `advisor_<役割>` (`advisor_controls`・`advisor_strategy`・`advisor_advice`・`advisor_tips`) | 4 | 確率 | - | その役割の advisor に、受け持ちのファイルの更新を求めます |

操作は、次の規則で決めます。

- ボタン: 押す側の合計 (`hold` の確率と `tap` の確率の和) が、`none` の確率より大きいときだけ押します。同じ値なら押しません。`none` の確率が 3 つの選択肢の中で最も高くても、押す側の合計が上回れば押します。押すときは、`hold` の確率が `tap` の確率以上なら押した状態にし、そうでなければ短押しにします (同じ値なら押した状態にします)
- 十字キー: 相反する方向 (UP と DOWN、LEFT と RIGHT) を、押した状態と短押しを合わせて両方とも押すことになったら、押す側の合計が高いほうを残します。同じ値なら両方とも外します
- スティックの方向: 軸 (x と y) ごとに、確率が最も高い選択肢を採ります。最も高い確率の選択肢が 2 つ以上あるとき (`none` と同じ値の場合も、左と右や上と下が同じ値の場合も) は、その軸には倒しません
- スティックの強さ: 倒す軸だけ計算します。その軸の 50%・75%・100% の問いの確率を p50・p75・p100 とし、上の段階が下の段階を超えないよう切り下げます (q50 = p50、q75 = p75 と q50 の小さいほう、q100 = p100 と q75 の小さいほう)。傾きの大きさは 0.25 + 0.25 × (q50 + q75 + q100) で、0.25〜1.0 になります。右と上は正、左と下は負の向きです
- advisor: `advisor_<役割>` の問いの確率が `--threshold-advisor` の値を超えた役割の advisor に、受け持ちのファイルの更新を求めます。しきい値は 4 問で共通です。ちょうど同じ値のときは求めません

選択肢の問いでは、`none` を先頭の選択肢に置いています。Jev は先頭の選択肢に寄りやすいと公式ドキュメント ([Model jaggedness](https://docs.typesafe.ai/model-jaggedness.md) の Choice option order、2026-11-13 に確認) に書かれているためです。Decision Model への役割の説明でも、迷ったら `none` を選ぶよう指示しています。OpenAI Decisions API が選択肢の問いへの回答を拒否 (refusal) したときは、`none` を選んだもの (`none` の確率を 1、ほかの選択肢を 0) として扱います。確率の問いへの回答の拒否は、確率 0 として扱います。

## 必要なもの

- 第2章の環境 (機材、Pico 2 W の準備、Windows とのペアリング、ffmpeg、Pico 2 W の 1P への登録)。[`../ch02_setup/README.md`](../ch02_setup/README.md) の手順で用意してください
- Decision Model の API キー。使うモデルに応じて、次の環境変数に設定します
  - TypeSafe Jev (`--model jev`): `TYPESAFE_API_KEY`
  - OpenAI Decisions API (`--model decisions`): `OPENAI_API_KEY`
- [Claude Code](https://code.claude.com/docs/) (WSL2 側で `claude` コマンドを実行できること)

`switch2-agent` は、キャプチャーとコントローラーのブリッジを自分で起動します。Elgato 4K X と COM ポートはどちらも同時に 1 つのプロセスしか使えないため、第2章のデーモン、Elgato Studio、OBS などは終了してから実行してください。

## セットアップ

WSL2 側で、このリポジトリーの `ch04_techniques` ディレクトリーに移動して依存パッケージを導入します。第2章のパッケージも、`../ch02_setup` から自動で導入されます。以降のコマンドも、このディレクトリーで実行します。

```bash
cd ch04_techniques
uv sync
```

## 実行

API キーを環境変数に設定し、ゲーム名と Decision Model を指定して実行します。ゲーム名には英数字、`_`、`-` だけを使えます。

```bash
export TYPESAFE_API_KEY=...
uv run switch2-agent --game <名前> --model jev
```

API キーは `.env` のファイルに書くこともできます。`switch2-agent` は `.env` を自分では読まないため、`uv run` に `--env-file .env` を付けて、uv に読み込ませます。見本の `.env.sample` を `.env` に写し、使うモデルの API キーを書いてから実行します。シェルで同じ名前の環境変数を設定してある場合は、シェルの値が使われます。`.env` は Git の管理から外しています (`.gitignore`)。`.env` を `ch04_techniques` に置くと advisor から読めると考えられるため、注意事項も確かめてください。

```bash
cp .env.sample .env
chmod 600 .env
uv run --env-file .env switch2-agent --game <名前> --model jev
```

advisor の Skill (`.claude/skills/`) を読み込ませるため、必ず `ch04_techniques` ディレクトリーで実行してください。別のディレクトリーで実行すると、説明を表示して終了します。

起動すると、ブリッジの起動 (COM ポートを開くまで最大 30 秒) とキャプチャーの起動の後に、速い層が要求を送り始めます。起動直後は、最初のフレームが届くまで最大 10 秒待ちます。止めるときは Ctrl+C を押します。止まるときは、押下状態を中立に戻してから、advisor、キャプチャー、ブリッジの順に止めます。advisor は 4 つの役割を同時に止め、実行中の役割は、`claude` のプロセスに終了を指示し、5 秒で終わらなければ強制的に終了させます。

次の場合は、押下状態を中立に戻して自動で止まります。

- キャプチャーが終わったとき、または最初のフレームが届いた後に新しいフレームが 2 秒届かなかったとき。Decision Model の応答を待つ間も、裏のスレッドが 0.1 秒ごとにキャプチャーの状態を確かめ、止まったと分かった時点で押下状態を中立に戻します。止まった後に届いた応答の操作は反映しません
- Decision Model の失敗 (HTTP のエラー、形の違う応答など) が `--max-consecutive-errors` 回続いたとき。失敗のたびに、押下状態を中立に戻して 1 秒待ちます
- コントローラーのブリッジが復旧できない状態 (第2章の `failed`) になったとき。ブリッジの復旧中 (第2章の `recovering`) は止まらず、押下状態を中立に戻して、復旧が終わるまで Decision Model に要求を送らずに待ちます

### 起動引数

| 引数 | 内容 | 既定値 | 範囲 |
|---|---|---|---|
| `--game NAME` | ゲーム名 (必須)。ゲームの情報は `game_notes/<NAME>/` に置きます | なし | 英数字、`_`、`-` |
| `--model {jev,decisions}` | Decision Model (必須)。`jev` は TypeSafe Jev、`decisions` は OpenAI Decisions API です | なし | `jev`、`decisions` |
| `--device-fps N` | デバイスから受け取るフレームレート。PC との USB の接続で 60 fps を受け取れないときは 30 にします (第2章の README の既知の問題を参照) | 60 | 30 か 60 |
| `--ffmpeg-fps N` | ffmpeg.exe が出力するフレームレート | 30 | 1〜`--device-fps` の値の整数 |
| `--process-fps N` | 間引いて残すフレームレート | 10 | 1〜`--ffmpeg-fps` の値の整数 |
| `--com-port PORT` | ブリッジが開く COM ポート。Pico 2 W の Bluetooth の発信側の COM ポートを指定します (第2章の README の「2. Windows とのペアリング」を参照)。ブリッジを復旧で起動し直すときも同じ COM ポートを開きます | `COM3` | `COM1`、`COM2` のように `COM` と 1 以上の整数 (先頭に 0 を付けた `COM04` などは誤り。大文字と小文字は区別しません) |
| `--history-seconds S` | フレームの履歴を持つ秒数。advisor に渡す画像のうち、意味のあるフレーム以外は、この秒数の範囲から等間隔に選びます | 5.0 | 0 より大きい有限の値 |
| `--image-width N` | 要求と advisor に渡す画像の幅。縦横比を保って縮小します | 1280 | 498〜1280 の整数 |
| `--jpeg-quality N` | 要求と advisor に渡す画像の JPEG の品質 | 85 | 1〜100 の整数 |
| `--threshold-advisor P` | `advisor_<役割>` の問いのしきい値 (4 問で共通) | 0.5 | 0〜1 |
| `--valley-ratio R` | 鮮明度が場面の山の何倍まで下がったら場面の切り替わり (谷) とみなすか。advisor に渡す意味のあるフレームの判定に使います | 0.5 | 0 と 1 を含まない範囲 |
| `--similarity-threshold D` | 意味のあるフレームが直前に残したものと似ているとみなす差分 (縮小したグレー画像の画素の差の平均) の上限。advisor に渡す意味のあるフレームの判定に使います | 0.15 | 0〜255 |
| `--advisor-timeout S` | advisor の 1 回の実行の上限 (秒。4 つの役割で共通) | 300 | 0 より大きい有限の値 |
| `--max-consecutive-errors N` | Decision Model の失敗がこの回数続いたら止まります | 5 | 1 以上の整数 |
| `--timeline SECTIONS` | 要求に入れる系列情報の節。`actions`・`screen`・`notes`・`advisor_calls`・`subgoals` をカンマで区切って指定します。`all` ならすべての節、`none` なら系列情報を入れません | `all` | 節の名前、`all`、`none` |
| `--timeline-window S` | 系列情報の操作のまとめに入れる直近の秒数 | 120 | 0 より大きく 3600 以下 |
| `--screen-change-threshold D` | 系列情報の画面の変化で、画面が変わったとみなす差分 (縮小したグレー画像の画素の差の平均) の下限 | 2.0 | 0〜255 |
| `--advisor-idle-seconds S` | advisor がこの秒数要求を受け付けていなければ、強制で呼びます。0 なら強制では呼びません | 60 | 0 以上の有限の値 |
| `--advisor-idle-scope {any,each}` | 強制の呼び出しで数える範囲。`any` はどの役割も呼ばれていない時間、`each` は役割ごとの時間を数えます | `any` | `any`、`each` |
| `--advisor-idle-roles ROLES` | 強制で呼ぶ役割。`controls`・`strategy`・`advice`・`tips` をカンマで区切って指定します | `strategy,advice` | 役割の名前 |
| `--save-requests` | 要求ごとの入出力を `runs/<YYYYmmdd-HHMMSS>/requests.jsonl` と `frames/` に書きます (ログの節を参照) | オフ | なし (付けるとオン) |
| `--record-dashboard` | ダッシュボードが読む記録 (処理したフレームの判定と縮小画像、送ったレポート、起動引数、要求の行、advisor の途中経過) を `runs/<YYYYmmdd-HHMMSS>/` に書きます (ログの節を参照) | オフ | なし (付けるとオン) |

範囲外の値や、`--ffmpeg-fps` が `--device-fps` より大きい指定、`--process-fps` が `--ffmpeg-fps` より大きい指定では、起動せずにエラーを表示します。`--threshold-advisor` は「`advisor_<役割>` の問いの確率がこの値を超えたら真」の値で、4 つの役割で共通です。ちょうど同じ値は偽です。ボタンとスティックの問いには、しきい値はありません (問いと操作の決め方の節を参照)。`--image-width` の下限の 498 は、Jev が受け付ける画像の各辺の下限 (280 ピクセル) を 16:9 の高さで満たす幅です。

`--save-requests` を付けると、要求ごとに送った画像を保存するため、ログの容量が大きくなります。長時間の試行では付けないでください。

## ゲームの情報のファイルと Skill

ゲームの情報は、ゲームごとに次の 4 ファイルに書きます。起動時に、無いファイルを作ります。controls.md と strategy.md は、無いときと、中身が空か空白だけのときに、既定の内容を書きます。tips.md と advice.md は空のファイルとして作ります。中身のあるファイルは変えません。

| ファイル | 内容 | 書き込む advisor の役割 | Skill |
|---|---|---|---|
| `game_notes/<ゲーム>/controls.md` | ゲームの操作方法 (ボタンの割り当て、会話の送り方、メニューの開き方など) | 操作方法の更新 (`controls`) | `record-controls` |
| `game_notes/<ゲーム>/tips.md` | 攻略情報・Tips (敵の特徴、アイテム、ゲームの仕組み、注意点など) | 攻略情報・Tips の更新 (`tips`) | `record-tips` |
| `game_notes/<ゲーム>/strategy.md` | 目標・進行状況・戦略 | 目標・戦略の更新 (`strategy`) | `record-strategy` |
| `game_notes/<ゲーム>/advice.md` | 問題の解決の助言 | 問題の解決の助言 (`advice`) | `record-advice` |

strategy.md は、目標・進行状況・戦略の 3 つの節で書きます。目標は大目標・中目標・小目標の 3 段階で、それぞれに状態 (未着手・途中・達成・不成立) を付けます。進行状況には、どこまで進んだか、今いる場所と画面の状態、画面で確かめられる値を書き、戦略には、今の小目標に向けた進め方、押すべきボタンの方針、避けるべき操作、安全のための制限を書きます。

advice.md は、速い層が先に進めなくなったときの助言です。助言が当てはまる場面、起きている問題、原因の見立て、試す手順、試して効果が無かったことを書きます。Decision Model には、助言に書かれている場面に今の画面が当てはまるときだけ参考にするよう、役割の説明で指示しています。

controls.md と strategy.md の既定の内容は [`default_notes.py`](./src/switch2_agent/default_notes.py) にあり、特定のゲームに固有の説明は含めていません。

- controls.md: Nintendo Switch 2 のゲームに多い一般的なボタンの対応 (A で決定、B でキャンセルや戻る、+ でポーズやメニューなど)。どの行にも `(一般)` の印を付けて、このゲームではまだ確かめていないことを表します。Decision Model への役割の説明にも、`(一般)` の行の意味を書いています。操作方法の advisor は、`(一般)` の行のうち、このゲームで確かめたものを消し、確かめた結果を「このゲームで確かめた操作」の節に書きます (Skill の `record-controls`)
- strategy.md: 段階に分けた最初の目標。大目標は「ゲームを先に進める」、中目標は「基本の操作を覚え、ゲームを始めて最初の場面を進める」、最も細かい小目標は「操作方法を把握する」です。戦略の節には、ボタンとスティックを 1 つずつ試すことと、安全のための制限を書いています。小目標が達成されたら、目標・戦略の advisor が次の目標を立てます

以前の実行で作られた `progress.md` は、作らず、読まず、変えません。中身を残したい場合は、strategy.md の進行状況の節に人が写してください。

速い層は、要求のたびに 4 ファイルを読み直し、内容をそのまま要求に入れます。advisor の出力 (`claude -p` の答え) は、ゲームの情報の受け渡しには使いません。人が 4 ファイルを書いておくと、最初から手がかりとして使われます。

Skill は [`.claude/skills/`](./.claude/skills/) の 4 つの `SKILL.md` で、advisor は役割ごとに 1 つの Skill を使います。ファイルは要求に毎回入るため、strategy.md は 2500 字以内、advice.md は 1500 字以内、ほかは 3000 字以内を目安に短く保つよう、Skill に書いています。

advisor (`claude -p`) は、役割ごとに次の指定で実行します。例は strategy の役割の場合で、`Edit` と `Skill` には、その役割のファイルと Skill が 1 つずつ入ります。

```bash
claude -p <プロンプト> --output-format json --permission-mode dontAsk \
  --setting-sources project --settings '{"disableAllHooks": true}' \
  --allowedTools "Read(/game_notes/<ゲーム>/**),Read(/runs/<YYYYmmdd-HHMMSS>/**),Edit(/game_notes/<ゲーム>/strategy.md),Skill(record-strategy)" \
  --max-turns 30
```

`--record-dashboard` を付けたときは、`--output-format json` の代わりに `--output-format stream-json --verbose` を付けます。ほかの指定は同じです。

許可のルールで読み取りを許すのは、`game_notes/<ゲーム>/` と、その実行の `runs/<YYYYmmdd-HHMMSS>/` の下です (ほかに読める範囲は注意事項に書きます)。書き込みを許すのは役割のファイル 1 つだけで (strategy の役割なら strategy.md)、ほかの 3 ファイルは読むだけです。使える Skill も役割の Skill 1 つだけで、Bash は許しません。確認が要る操作のうち、許可のルールに無いものは、確認を求めずに拒否されます (`--permission-mode dontAsk`)。拒否された操作は、ログの `permission_denials` に残ります。advisor の `claude` のプロセスには、Decision Model の API キーの環境変数 (`TYPESAFE_API_KEY`・`OPENAI_API_KEY`) を渡しません。

## ログ

実行ごとに `runs/<YYYYmmdd-HHMMSS>/` を作り、次のファイルを書きます。

| ファイル | 内容 |
|---|---|
| `run.jsonl` | 1 行 1 件の JSON のログ。要求ごとの所要時間 (`select_s`・`encode_s`・`decide_s`・`apply_s`)、Jev で直前の要求の後に待った秒数 (`interval_wait_s`。待たなければ 0)、画像の枚数と大きさ、決めた操作、advisor の役割ごとの問いの確率 (`advisor_probabilities`)、advisor を求めた役割 (`advisor_requested`) と受け付けた役割 (`advisor_accepted`)、強制の呼び出しで求めた役割 (`advisor_forced`)、advisor の実行の結果 (役割の `role` を含む)、失敗などを書きます。同じ内容の要約を画面にも表示します。`--record-dashboard` を付けたときは、`start` の行に起動引数 (`args`) と時計の起点 (`origin_mono`。`time.monotonic()` の秒) を足し、終了時に記録の件数 (`record_end`。書いた件数と捨てた件数) を書きます。記録を書けなかったときは、その種類の記録をやめて `record_error` の行を書きます |
| `advisor-<役割>-001/` など (例: `advisor-strategy-001/`) | advisor の役割ごと、1 回の実行ごとの入出力 (連番は役割ごと)。advisor 用に選んだ最大 10 枚の画像 (`frame-01.jpg` など。意味のあるフレーム、フレームの履歴から選んだものの順で、どちらも古い順)、文脈 (`context.md`。役割と、呼んだきっかけを含む)、結果 (`result.json`。終了コード、所要時間、`claude -p` の出力、拒否された操作) |
| `advisor-<役割>-001/stream.jsonl` など | `--record-dashboard` を付けたときだけ書く、advisor の途中経過の JSON Lines。`claude -p` を `--output-format stream-json --verbose` で動かし、標準出力の行 (ツール呼び出し、ツールの結果、最後の `result` など) が 1 行届くたびに、読んだ時刻 (`mono`。`time.monotonic()` の秒) と、その行を JSON として読んだもの (`data`) を `stream.jsonl` の 1 行に書きます。JSON として読めない行は、`data` の代わりに元の文字列を `raw` に入れます。このときの `result.json` の `claude -p` の出力は、最後に届いた `result` の行です。`stream.jsonl` を書けなかったときは、`run.jsonl` に `record_error` の行を書き、advisor の実行は続けます |
| `frames.jsonl` | `--record-dashboard` を付けたときだけ書く、処理したフレーム (間引いた後、意味のあるフレームの判定に入れたフレーム) 1 枚ごとの JSON Lines。フレームの時刻 (`mono`)、鮮明度、直前のフレームとの差分 (`diff`)、判定の状態 (`phase`、今の区間の山、谷や回復とみなす鮮明度 `ref`)、そのフレームで起きた出来事 (`event`。谷に向かい始めた `fall`、谷を確定した `close`)、縮小画像のファイル名 (`thumb`) を書きます |
| `thumbs/` | `--record-dashboard` を付けたときだけ書く、処理したフレームごとの縮小画像 (320×180、JPEG の品質 70)。ファイル名は、フレームの時刻 (`mono`) をマイクロ秒にした整数です |
| `pad.jsonl` | `--record-dashboard` を付けたときだけ書く、コントローラーのブリッジにレポートを送ろうとした 1 回ごとの JSON Lines。送信が戻った時刻 (`mono`)、送ったきっかけ (`source`。判断の操作の `apply`、短押しの開始の `tap_start` と解除の `tap_release`、中立の `neutral` と `stop_output`)、送った押下状態 (`state`)、成否 (`ok`・`error`) を書きます |
| `requests.jsonl` | `--save-requests` か `--record-dashboard` を付けたときに書く、Decision Model への要求ごとの入出力の JSON Lines。1 行目は header で、`--model` の値、役割の説明と安全のための規則、37 の問い (名前、文、種類、答えの型、選択肢の問いの選択肢) を書きます。2 行目以降は要求ごとに 1 行で、要求に載せた 1 枚の画像のラベルとファイル名、ゲームの情報の 4 ファイルの内容、直近の応答と送った操作の履歴、系列情報 (`timeline_text`。系列情報を入れないときは空文字)、確率の問いの確率 (`probabilities`)、選択肢の問いの選択肢ごとの確率 (`choices`)、応答の本文、決めた操作、advisor の役割ごとの問いの確率 (`advisor_probabilities`)、advisor を求めた役割 (`advisor_requested`) と受け付けた役割 (`advisor_accepted`)、強制の呼び出しで求めた役割 (`advisor_forced`)、結果 (`ok`: 操作を送った、`error`: Decision Model か操作の送信の失敗、`discarded`: キャプチャーが止まったため応答を捨てた) を書きます。各行の `number` は `run.jsonl` の `decision` の `number` と同じで、2 つのログで同じ要求の行を対応づけられます。`--record-dashboard` を付けたときは、画像ごとに縮小画像のファイル名 (`thumb`) を足します。`--save-requests` を付けていなければ、画像を `frames/` に書かず、画像の `file` を null にします |
| `frames/` | `--save-requests` を付けたときだけ書く、要求に載せた画像 (JPEG)。ファイル名は、実行を始めてからの経過時間 (マイクロ秒) です。複数の要求に載った同じフレーム (失敗した要求の後に、同じフレームで送り直したときなど) は、1 回だけ保存します |

`frames.jsonl`・`pad.jsonl`・`stream.jsonl` の `mono` から `run.jsonl` の `start` の `origin_mono` を引くと、`requests.jsonl` の経過秒 (`t_sent` など) と同じ起点からの秒になります。

`game_notes/` と `runs/` の中身は Git の管理から外しています (`.gitignore`)。

## 注意事項

- このサンプルは、オフラインの個人実験での利用に限ります。利用規約で自動操作を禁止しているサービスやゲーム、オンライン対戦では使わないでください
- 速い層は HOME ボタンも押せます。通信対戦のソフトを起動したり、本体の設定を変えたりしないよう、Decision Model と advisor の両方に安全のための規則を毎回渡していますが、守られる保証はありません。試行中は、人が画面を見ていてください
- Decision Model の API は、要求ごとに料金がかかります。速い層は、応答を受け取ると次の要求を送ります (Jev では直前の要求の応答が返るか、失敗してから 0.2 秒待ち、Decisions API では待ちません)。そのため、実行している間は要求を送り続けます
- 系列情報を入れると、要求の入力が増えます。2026-11-14 に保存済みの要求を Jev に送り直して確かめたところ、すべての節を入れた要求の入力は約 900〜1,200 トークン増え、応答までの時間は変わりませんでした。実機の試行で系列情報が速い層の操作をどう変えるかは、確かめていません
- Jev の文脈長は、要求全体で 64k トークン、問い 1 つあたり 32k トークンです。画像 1 枚が何トークンになるかが公開されていないため、画像 1 枚と 37 の問いが収まるかは確かめていません。超えた場合は HTTP 400 (`max_tokens_exceeded`) になり、Decision Model の失敗として扱います
- 4 つの役割の advisor (`claude -p`) は、同時に動くことがあります (最大 4 件)。そのぶん、Claude Code の利用枠や料金を使います。強制の呼び出しでは、advisor の問いが真にならなくても、advisor が `--advisor-idle-seconds` 秒 (既定 60 秒) 呼ばれていなければ、既定で 2 つの役割を呼びます。実機の試行で強制の呼び出しが何回起きるかは、確かめていません
- 要求と advisor に渡す画像の幅の既定値 1280 と JPEG の品質の既定値 85 は、判断の精度と要求の大きさの釣り合いを確かめる前の値です
- advisor の書き込みの許可 (`Edit(...)` のルール) では、Bash や、advisor が起動したプログラムによる書き込みは止められません。そのため Bash を許していません
- advisor はゲームの画面の画像を読むため、画面に写った文字で advisor への指示が注入されるおそれがあります。注入された指示に従うと、advisor は読んだファイルの内容を、その役割のゲームの情報のファイルに書き写せます。書き換えられるファイルは役割ごとに 1 つに限っていますが、どのファイルも、毎回の要求で Decision Model の API に送られます。そのため、許可のルールで読み取りを許すディレクトリーと書き込みを許すファイルを限り、advisor に API キーを渡していません
- Claude Code のドキュメントでは、作業ディレクトリー (`ch04_techniques`) の中のファイルの読み取りは、許可のルールが無くても承認されます。そのため advisor は、`ch04_techniques` の中のほかのファイルも読めると考えられます。実際に読める範囲は確かめていません
- `.env` を `ch04_techniques` に置くと、advisor はそのファイルも読めると考えられます。advisor の `claude` のプロセスには API キーの環境変数を渡していませんが、`.env` を読んで、画面の文字で注入された指示に従うと、API キーをゲームの情報のファイルに書き写せます。書き写された API キーは、毎回の要求で Decision Model の API に送られます。避けるには、API キーを書いたファイルを `ch04_techniques` に置かないでください。API キーは `export` で設定するか、`.env` を `ch04_techniques` の外に置いて `--env-file` にそのパスを指定します
- `--setting-sources project` で実行する人のユーザー側の設定を読まないようにしていますが、ユーザーの `~/.claude/CLAUDE.md` が読まれるかは確かめていません。advisor の動作は、実行する人の Claude Code の環境によって変わることがあります
- `--save-requests` を付けたときの `requests.jsonl` と `frames/` には、ゲームの画面の画像と、ゲームの情報の 4 ファイルの内容がそのまま残ります
- `--record-dashboard` を付けたときの `thumbs/` には、処理したフレームごとのゲームの画面の縮小画像が残ります (既定の `--process-fps 10` では 1 時間に 36,000 枚)。`requests.jsonl` には、ゲームの情報の 4 ファイルの内容がそのまま残ります
- `--record-dashboard` の記録 (`frames.jsonl` と `thumbs/`、`pad.jsonl`) は裏のスレッドで書き、書き終えていない記録を溜められる件数に上限があります (フレームは 600 件、レポートは 2000 件)。上限を超えた記録は捨て、捨てた件数を `run.jsonl` の `record_end` に書きます。フレームの記録は 1 件ごとに元の画像 (約 1.3MiB) を持つため、ディスクへの書き込みが止まると、最悪で約 790MiB のメモリーを使います
- `--record-dashboard` を付けたときの `stream.jsonl` には、advisor が読んだファイルの中身 (ツールの結果) と、ゲームの情報のファイルに書いた内容がそのまま残ります。読んだ画像も、ツールの結果に入って残ると考えられます (確かめていません)。画面の文字で注入された指示に従って、advisor が `ch04_techniques` の中のほかのファイル (`.env` など) を読んだ場合は、そのファイルの中身も残ります
- 利用によって生じたアカウントの制限、データの損失、機器の故障などの不利益は、利用者の自己責任となります

## 3 層のエージェントの骨組み (switch2-layers)

同じ uv プロジェクトに、surface・middle・deep の 3 層でゲームを遊ぶエージェントの骨組みのパッケージ [`switch2_layers`](./src/switch2_layers/) があります。コマンド `switch2-layers` で実行します。3 層は 1 つのプロセスの中で別々のスレッドとして動き、実行ディレクトリーのファイルで情報を受け渡します。

| 層 | 動く間隔 | 受け持ち |
|---|---|---|
| surface | 0.2〜2 秒ごと (待ち時間は middle の出力で決まります) | 直近 2 秒のフレームから最大 5 枚を選び、時刻と追えている box を書き込んだ画像、文書、現在地の場所のマップ、middle の出力から、コントローラーの操作を決めて送ります (既定では TypeSafe の Jev に問います)。現在の場面のタスクのキューの先頭のタスクについて、達成したか (完了) と、達成できないか状況に合わないか (取り消しの要求) も判定します。必要なら deep に文書の更新を求めます |
| middle | 前回の応答から `--middle-interval` 秒後 (既定 5 秒)。きっかけ (キューが空になったこと・取り消しの要求・詰まり・場面転換) があれば、間隔を待たずに呼びます (前回の応答から 1 秒たつまでは呼びません。「middle の実装」の節の「middle を呼ぶきっかけ」)。最初の実行は、最初の画像を `frames.jsonl` に記録した後です | 一定間隔で保存したフレーム、surface の記録 (`surface.jsonl`)、操作の記録 (`operations.jsonl`)、タスクのキューとその出来事の記録 (`tasks.jsonl`)、マップから、場面の名前、現在地の場所、詰まっているか、surface の待ち時間、系列情報を決め、場面ごとのタスクのキューにタスクを足し、取り消します (既定では OpenAI の gpt-6-luna を呼びます)。現在地と、新しく分かった場所のつながりと観察を、マップの記録 (`middle/map_records.jsonl`) に足します。初めての場面に名前を付けたら、その場面の操作説明と攻略情報と、ゲームの性質の deep を求めます |
| deep | 求められたときと、同じ文書の前回の終了から `--deep-auto-seconds` 秒後 (既定 60 秒)。助言は、新しい画面が出ていない秒数が `--stuck-advice-seconds` を超えたとき (「画面の停滞の計測」の節) と、準備・復帰の段階が `--system-advice-seconds` を超えて続いたとき (「本体の画面の扱い」の節) も | `notes/` の操作説明・攻略情報・大方針・助言・マップ・ゲームの性質の文書を、直接編集して書き直します (既定では Claude Code を起動します)。マップは、middle のマップの記録からまとめます。ジョブごとに `deep/<種類>-<連番>/` を作り、ジョブの記録を置きます |

surface は、既定では TypeSafe の Jev を呼びます (`--surface jev`)。`--surface fake` を付けると surface はフェイクになり、何も押さない中立の操作を返して deep を求めません。タスクの完了も取り消しの要求もしません。middle は、既定では OpenAI の gpt-6-luna を呼びます (`--middle luna`)。`--middle fake` を付けると middle もフェイクになり、固定の場面名 `fake scene` と待ち時間 0.2 秒を返し、タスクを足しも取り消しもしません。deep は、既定では Claude Code を起動します (`--deep claude`)。`--deep fake` を付けると deep もフェイクになり、文書を変えずに成功を返します。3 層と安全の監視をすべてフェイクにしても (`--surface fake --middle fake --deep fake --safety fake`。API キーは要りません)、フレームの保存、操作の送信と記録、場面の一覧への追加、deep のジョブのディレクトリーの用意は動きます。各層は Protocol (`SurfaceDecider`・`MiddleAnalyzer`・`DeepRunner`) で受け取るため、フェイクをほかの実装に差し替えられます。

3 層とは別のスレッドで、安全の監視が動きます (「安全のための規則と安全の監視」の節)。オンライン・通報・購入・本体の設定などの画面を見つけたら、操作を中立にして実行全体を止めます。同じ要求で、今の画面が本体のどの画面 (HOME メニュー・ユーザー選択など) かを見本の画像と照合して記録します。照合の結果では止めず、段階の移り変わりと本体の画面の操作に使います。既定では TypeSafe の Jev に問います (`--safety jev`)。`--safety fake` を付けると、安全の監視は、止める問いの確率をすべて 0 とし、どの見本の画面でもないと答えるフェイクになります。

advisor 型の run は、準備 (`prepare`)・プレイ (`play`)・復帰 (`recover`)・片付け (`clean_up`) の 4 つの段階に分けて動きます (「本体の画面の扱い」の節)。surface と middle のゲーム用のループと deep の自動の呼び出しは、play の段階の間だけ動きます。本体の画面 (HOME メニュー・ユーザー選択など) を操作する準備・復帰・片付けの段階では、middle が本体の画面の操作の列を決め、コードが送ります。Orchestrator 型の run は段階に分けません (「Orchestrator 型」の節)。

### サブコマンド

| コマンド | 内容 |
|---|---|
| `switch2-layers run [--mode advisor] --software NAME --user NAME [起動引数]` | 実機 (キャプチャーとコントローラーのブリッジ) につないで、指定のソフトを指定のユーザーで起動する準備から始め、3 層を動かします (advisor 型。`--mode` の既定)。Ctrl+C で止めると、HOME メニューに戻って指定のソフトを終了する片付けをしてから止まります |
| `switch2-layers run --mode orchestrator [--instruction TEXT \| --instruction-file PATH] [起動引数]` | 実機につないで、主ループ (Claude Code か Codex。`--agent`) と、操作の実行と監視を動かします (「Orchestrator 型」の節)。準備と片付けの段階は使わず、Ctrl+C で止めるとすぐに止まります |
| `switch2-layers run --mode delegate [--instruction TEXT \| --instruction-file PATH] [起動引数]` | 実機につないで、主ループ (Claude Code か Codex。`--agent`) と、操作の実行と委任のループを動かします (「Orchestrator 型」の節の「委任型」の項)。準備と片付けの段階は使わず、Ctrl+C で止めるとすぐに止まります |
| `switch2-layers middle-once --run-dir DIR [--middle-window S] [--middle fake\|luna]` | 保存済みの実行ディレクトリーに対して middle を 1 回動かし、`middle/state.json` などの出力を書きます。タスクのキューは保存済みの `notes/scenes/<場面ID>/tasks.json` から作り直し、run と同じ規則で取り消しと追加を行って、`tasks.json`・`tasks.md`・`tasks.jsonl` に書き戻します。呼ばれた理由は `interval` です。初めての場面でも deep は起動せず、求める文書の種類を `middle/calls.jsonl` に書くだけです。`--middle` は run と同じです |
| `switch2-layers deep-once --run-dir DIR --doc KIND [--scene SCENE_ID] [--deep claude\|fake]` | 保存済みの実行ディレクトリーに対して deep のジョブを 1 回、終わるまで動かします。`KIND` は `controls`・`tips`・`strategy`・`advice`・`map`・`game` のどれかです。`--scene` は `controls` と `tips` にだけ付けられます。付けなければ、`middle/state.json` の現在の場面 (無ければ共通の文書) を対象にします。`--deep` は run と同じです |

middle-once・deep-once は実機を使わないため、保存済みの実行ディレクトリーに対して試せます。結果は標準出力に JSON の 1 行で書きます。run と middle-once は、既定の `--middle luna` では OpenAI の API キーを環境変数 `OPENAI_API_KEY` から読みます (「middle の実装」の節)。run は、既定の `--surface jev` では TypeSafe の API キーも環境変数 `TYPESAFE_API_KEY` から読みます (「surface の実装」の節)。既定の `--safety jev` でも、同じ `TYPESAFE_API_KEY` を読みます (「安全のための規則と安全の監視」の節)。run と deep-once は、既定の `--deep claude` では Claude Code を起動します (「deep の実装」の節)。`run --mode orchestrator` と `run --mode delegate` が確かめる API キーは `TYPESAFE_API_KEY` だけで、`--safety fake` でも要ります (「Orchestrator 型」の節)。

run は、Switch 2 がスリープしておらず、コントローラーのブリッジ (Pico 2 W) を Windows とペアリングした状態で始めます (第2章の [README](../ch02_setup/README.md) の「2. Windows とのペアリング」)。Pico 2 W の入力ではスリープを解除できないため、スリープしていたら本体を操作して復帰させてください (第2章の README の「既知の問題」)。ブリッジを 1P に登録すること、指定のソフトを起動すること、ユーザー選択で指定のユーザーを選ぶことは、advisor 型では run が準備の段階で行い (「本体の画面の扱い」の節)、Orchestrator 型では主ループがスキルで行います。`--software` には HOME メニューでソフトの絵の上に出る名前を、`--user` にはユーザー選択に出る、AI に遊ばせるユーザーの名前を指定します。advisor 型ではどちらも必須です。Orchestrator 型では使わず、起動するソフトと遊ぶユーザーは人の初期指示に書きます。

run は、最初のフレームが届いた後、準備の段階に入る前に画面を確かめ、オンライン・購入・本体の設定などの画面なら、操作を 1 つも送らずに止まります。HOME メニューやユーザー選択の画面では止まらず、advisor 型では準備の段階に入り、Orchestrator 型では主ループと、操作の実行と監視を始めます。

```bash
uv run --env-file .env switch2-layers run --software '<ソフトの名前>' --user '<ユーザーの名前>'
uv run switch2-layers run --software '<ソフトの名前>' --user '<ユーザーの名前>' --surface fake --middle fake --safety fake
uv run --env-file .env switch2-layers run --mode orchestrator --instruction '<ソフトの名前> を <ユーザーの名前> で起動して、冒険を始めてください'
uv run --env-file .env switch2-layers middle-once --run-dir runs/<YYYYmmdd-HHMMSS>
uv run switch2-layers middle-once --run-dir runs/<YYYYmmdd-HHMMSS> --middle fake
uv run switch2-layers deep-once --run-dir runs/<YYYYmmdd-HHMMSS> --doc strategy
uv run switch2-layers deep-once --run-dir runs/<YYYYmmdd-HHMMSS> --doc strategy --deep fake
```

3 層のほかに、コードが一定間隔のフレームから画面の停滞を測り、`progress/state.json` に書いて各層に渡します (「画面の停滞の計測」の節)。

### middle の実装 (`--middle`)

run と middle-once は、`--middle` で middle の実装を選びます。

| 値 | 内容 |
|---|---|
| `luna` (既定) | OpenAI の gpt-6-luna を Responses API で呼びます。run では、本体の画面の middle (「本体の画面の扱い」の節) も gpt-6-luna を呼びます。環境変数 `OPENAI_API_KEY` に API キーが要ります |
| `fake` | 固定の場面名 `fake scene` と待ち時間 0.2 秒を返すフェイクです。run では、本体の画面の middle も、操作の列を空にして `done` を真で返し続けるフェイクになります。API キーは要りません |

`--middle luna` で `OPENAI_API_KEY` が無いとき (値が空か空白だけのときを含む) は、実機に触れず、実行ディレクトリーにも何も書かずに、エラーを表示して終了します (終了コード 2)。API キーは、`switch2-agent` と同じく `.env` に書き、`uv run --env-file .env` で読み込ませることもできます。

gpt-6-luna には、変わらない指示 (developer メッセージ) と、場面の一覧、場所の名前の一覧、マップ、現在地からの経路 (コードの計算)、前回の middle の出力、ゲームの性質、大方針、現在の場面のタスクのキュー、前回以降のタスクの出来事、呼ばれた理由 (「短期のタスクのキュー」と「middle を呼ぶきっかけ」の項)、現在の場面の操作説明、前回以降の surface と操作の記録の要約、場面転換の印、画面の停滞の計測の値 (「画面の停滞の計測」の節)、直近 `--middle-window` 秒の一定間隔のフレームから最大 4 枚 (時刻のラベル付き) を送ります。reasoning effort は、run の `--middle-effort` で `none` か `low` を選べます (既定は `none`)。middle-once は常に `none` です。出力は Structured Outputs の JSON Schema で受け取ります。変わらない指示の直後にキャッシュの区切りを置き、指示をプロンプトキャッシュから読ませます。応答の待ちは 30 秒までです。HTTP のエラー、完了しなかった応答、拒否、形の合わない出力は middle の失敗として数え、再試行せずに、前回の応答から `--middle-interval` 秒たってから呼び直します (その回の呼ばれた理由は、次の回に持ち越します)。

middle は、マップを次のように扱います。

| 項目 | 内容 |
|---|---|
| 場所の名前の一覧 (入力) | `notes/map/map.json` の場所の名前 (`name`) と別の名前 (`aliases`)、`middle/map_records.jsonl` の `place_name` を合わせ、重複を除いて最初に現れた順に並べたものです。場面の名前と同じく、当てはまる名前があればそれを選ばせ、無いときだけ新しい名前を作らせます |
| マップ (入力) | `notes/map/map.json` の全体を JSON で送ります (最上位の最初のキーは `layout`)。無い・JSON として読めない・形に合わない (形に合わない要素が 1 つでもある) ときは「マップなし」として送り、middle の失敗にはしません。`notes/` の外を指すシンボリックリンクは、無い文書として扱います |
| 現在地からの経路 (入力) | マップが `grid` のときに、前回の現在地の行、前回の出力の現在地のマスからその場所の出口とつながりのマスまでの経路、つながりをたどって行ける場所ごとの経路 (場所をまたぐ経路) をコードで計算して送ります (この節の「マップの型と経路の計算」) |
| `place_name` (出力) | 現在地の場所の名前です。ゲームの世界の中の場所が映っていない (メニュー・タイトル・戦闘など) か、決められなければ空文字列です |
| `current_tile` (出力) | 現在地のマスの座標 `{"x": 整数, "y": 整数}` か `null` です。`place_name` の直後に書かせます。座標は、入力のマップのその場所の座標 (`origin` と `tiles`) で書かせます。マップが `grid` で、その場所に `tiles` があるときだけ書かせ、それ以外 (マップなし・`free`・場所がマップに無い・`tiles` が空・決められない) は `null` にさせます |
| `new_connections` (出力) | 前回の実行より後に新しく分かった、場所から場所への移動 (`from`・`to`・`how`・`from_tile`・`to_tile`) の配列です。`from_tile` は移る前の場所で出たマス、`to_tile` は移った後の場所で着いたマスで、`current_tile` と同じ規則で座標か `null` を書かせます |
| `new_observations` (出力) | 新しく分かった、出口 (`exit`)・目印 (`landmark`)・通れなかった位置 (`blocked`) の配列です。各要素は `kind`・`place`・`description`・`tile` を持ちます。`tile` は観察したマスで、`current_tile` と同じ規則で座標か `null` を書かせます |
| 現在地 (`middle/state.json`) | `place_name` (出力の `place_name` の前後の空白を除いたもの。空なら `null`) と `current_tile` (出力の値。`place_name` が `null` なら `null`) を書き、次の入力の経路の計算に使います。この 2 つのキーが無い `middle/state.json` は、どちらも `null` として読みます |
| マップの記録 | `place_name` が空でないか、`new_connections` か `new_observations` が空でない回に、`middle/map_records.jsonl` に 1 行 `{"t", "scene_id", "place_name", "current_tile", "connections", "observations"}` を足します。`t` はその回に送った画像のうち最新のものの時刻、`scene_id` はその回に決まった場面の ID (無ければ `null`)、`place_name` は空なら `null`、`current_tile` は出力の値 (`place_name` が `null` なら `null`) です。`connections` の要素は `{"from", "to", "how", "from_tile", "to_tile"}`、`observations` の要素は `{"kind", "place", "description", "tile"}` です。画像を送らなかった回は記録しません。追記に失敗しても middle の失敗には数えず、警告を書いて続けます |

変わらない指示では、マップのつながりと、経路の節の場所をまたぐ経路をたどって、現在地から大方針の行き先までに通る場所を選ばせます。タスクには、通る場所を順に、「家の 1 階に出ている」のような状態の形で書かせます。入るたびに構造が変わる場所 (`changes_on_entry` が `true`) のつながりは、手順に使わせません。マップが `grid` のときは、経路の節を、たどり着ける目標を選ぶ手がかりにさせ、「経路なし (未確認のマス (?) を通ってもたどり着けない)」の目標はタスクにさせません。通れるマスだけではたどり着けず、未確認のマス (`?`) を通る経路が添えてある目標は、タスクにしてよいとします。surface には、キューの先頭のタスクの文と、現在地の場所のマップ (先頭のタスクの行き先を印にしたもの) を渡します (「surface の実装」の節の state の `map`)。

ゲームの性質 (`notes/game.md`) は、大方針の前の節に、前後の空白を除いて送ります。無い・読めない・空 (空白だけ) のときは「(無い)」です。変わらない指示では、ゲームの性質のリアルタイムに進む部分 (プレイヤーの入力を待たずに進む部分) とターン制の部分 (入力を待って進む部分) を見て、素早い反応が要るか (待ち時間) を決めさせ、ダメージとゲームオーバーの条件のうち、確かめたもの (「(推測)」が付いていないもの) に当たる行動をタスクにさせません。

`middle/calls.jsonl` の各行には、トークン数 (`usage`。入力・キャッシュから読んだ入力・キャッシュに書いた入力・出力・推論)、公式の単価から計算した概算の費用 (`cost_usd`。USD)、デバッグ用の応答の本文 (`response`。エラーの応答では本文の先頭を `error_body_head`) も書きます。各行の `request` は、その回に送った要求の番号です。`middle/requests.jsonl` の同じ `request` の行に、その回に送った user メッセージの節の文と、画像の時刻とファイル名を残します (「実行ディレクトリー」の節)。

#### マップの型と経路の計算

マップには、マス目で作られたゲームのためのマス目型 (`grid`) と、それ以外の自由型 (`free`) の 2 つの型があります。型は `notes/map/map.json` の最上位の `layout` に書きます。deep の `map` のジョブで書く型は、ジョブを作るときにコードがゲームの性質の文書 (`notes/game.md`) の「マップの形式」の節から決め (判定が付かないときは、今の `map.json` の型を引き継ぎます)、`job.json` の `map_layout` で deep に渡します。`layout` が無い `map.json` は `free` として読みます。

| 型 | 場所の持ち方 |
|---|---|
| `free` | 出口 (`exits`) と通れない位置 (`blocked`) を、画面上の位置の文で持ちます |
| `grid` | 場所ごとに、マスの図 (`tiles`) と座標で、出口 (`exits`)・通れないマス (`blocked`)・目印 (`landmarks`) を持ちます。つながりには、出たマス (`from_tile`) と着いたマス (`to_tile`) を持ちます |

`grid` の座標は、x が右に、y が下に増える整数です。`tiles` は文字列の配列で、1 つの文字列が 1 行 (1 つの y) です。各行の文字数はそろえ、文字は `#` (通れない)・`.` (通れる)・`E` (出口)・`?` (まだ確かめていない) の 4 つだけを使います。`origin` は `tiles` の 1 行目の 1 文字目のマスの座標で、マス `(x, y)` は `tiles[y - origin.y]` の `x - origin.x` 文字目です。まだ図を描けない場所の `tiles` は空の配列です。`exits`・`blocked`・`landmarks` の座標は、`tiles` の範囲の外でもかまいません。

`map` のジョブで書く型は、コードがジョブを作るとき (`run` の中の要求で起動するとき、保留した要求を起動するとき、`deep-once` のとき) に 1 回だけ決め、`job.json` の `map_layout` (`"grid"` か `"free"`。`map` 以外の種類のジョブでは `null`) に書きます。決め方は次のとおりです。

| ゲームの性質の文書の「マップの形式」の節 | 型 |
|---|---|
| 見出し `## マップの形式` の後で次の `## ` の見出しより前にある、最初の空でない行が、前後の空白を除いて `- 型: マス目型` と一致する | `grid` |
| 同じ行が、前後の空白を除いて `- 型: 自由型` と一致する | `free` |
| それ以外 (`- 型: 未確認`・注記の付いた行などほかの行、節や行が無い、文書が無い・読めない・`notes/` の外を指すシンボリックリンク) | 今の `notes/map/map.json` の `layout` を引き継ぎます (`layout` が無い `map.json` は `free`)。`map.json` も無い・読めない・形に合わないときは `free` |

型を引き継いだときは、`map.json` の `layout` と同じ型になるため、`map.json` を別の型の形で書き直すことはありません。

deep の `map` のジョブは、渡された型 (`map_layout`) で書きます。ゲームの性質の文書は、1 マスの大きさなどを読むのに使い、型を決め直すのには使いません。書いてある `layout` が渡された型と違えば、すべての場所とつながりをその型の形で書き直します (場所の名前・別の名前・説明・状態・構造が変わるかと、つながりの `from`・`to`・`how` は引き継ぎます)。

型を書き換えるジョブには、コードが前回の時刻を渡しません。ジョブを作るときに、`notes/map/map.json` を読めて、その `layout` が、同じときに決めた `map_layout` と違えば、`job.json` の `previous_latest_frame_t` を `null` にします。前回の正常に終わった `map` のジョブの `job.json` の `map_layout` が、このジョブの `map_layout` と違うときも `null` にします。型を書き換えるジョブが `map.json` を新しい型で書いた後に正常に終わらなかった場合に、次のジョブに最初から読ませるためです。それ以外 (`map.json` が無い・読めない・形に合わないときと、型が同じとき) は、ほかの種類と同じく前回の正常に終わったジョブから決めます。型を書き換えるジョブは、記録のすべての行と最初からのフレームを読み、記録とフレームに出てくるすべての場所の `tiles` を、その場所が映っているフレームから描きます。

`grid` では、次のように書きます。

- フレームを見てマスを数えて `tiles` を描き、middle の記録の `current_tile`・`tile`・`from_tile`・`to_tile` を取り込みます
- `blocked` に入れたマスは、`tiles` でも `#` で描きます
- 場所の範囲が左や上に広がったときは、`origin` を小さくして行や列を足し、既にあるマスの座標を変えません
- `places.md` の場所の節にも、マスの図を書きます

middle の user メッセージの「マップ」の節の直後に、「現在地からの経路 (コードの計算)」の節を置きます。前回の middle の出力の場所の名前 (`place_name`) を、マップの場所の `name` と `aliases` (前後の空白を除いて比べます) から探し、次の 3 つの部分をこの順に書きます (書かない部分は飛ばします)。

| 部分 | 書くとき | 中身 |
|---|---|---|
| 前回の現在地の行 | マップが `grid` で、前回の出力に `place_name` と `current_tile` がどちらもあるとき | 前回の出力の場所の名前と `current_tile` と、その出力の入力を作った時刻です。場所を `aliases` で見つけたときは、マップの場所の `name` を添えます |
| 場所の中の経路 | いつも | `current_tile` のマスから、その場所の目標ごとの最短の経路です。経路を計算しないときは、その理由の 1 行です |
| 場所をまたぐ経路 | マップが `grid` で、前回の出力の `place_name` の場所がマップにあり、その場所の `changes_on_entry` が `false` のとき | つながりをたどって行ける場所ごとの、通る場所の順と各場所の中の手順です |

マップなし、`layout` が `free`、前回の出力が無いときは、理由の 1 行だけを書きます。

場所の中の経路は、次のように計算します。

- 動き方: 上下左右の隣のマスへ 1 マスずつ動きます。通れるのは、文字が `.` か `E` で、`blocked` の座標に無いマスです。ただし、目標でない出口のマスとつながりの出たマス (文字が `E` のマス、`exits` の座標のマス、その場所から出るつながりの `from_tile` のマス) は、乗ると場所を移るため、途中で通りません。目標のマスには、文字と `blocked` によらず入れます。開始のマスの文字は問いません。`tiles` の範囲の外へは動きません
- 選び方: 最短の経路のうち、向きを変える回数の少ないものを選びます。それも同じなら、1 マスずつの移動の向きを上・下・左・右の順で先頭から比べ、最も前のものを選びます
- 目標: その場所の `exits` のうち座標が `tiles` の範囲の中にあるもの (`exits` の順)、続けて `from` がその場所で `from_tile` が `tiles` の範囲の中にあるつながり (`connections` の順) を、合わせて最大 10 件にします。`from_tile` が出口と同じマスのつながりは目標に足さず、その出口の行き先 (`to`) として添えます
- 書き方: 目標ごとに 1 行で、種類 (出口かつながり)・説明・座標・行き先・手順 (例: `上に 3 マス → 左に 2 マス (合計 5 マス)`) を書きます
- 未確認のマスを通る経路: 通れるマスだけではたどり着けない目標は、まだ確かめていないマス (`?`) も途中で通れるとみなして、経路を求め直します。`blocked` の座標のマス、出口のマス、つながりの出たマスは、`?` でも途中で通りません。通る `?` のマスの数が少ない経路を選び、`?` の数が同じなら短い経路、長さも同じなら向きを変える回数の少ない経路、それも同じなら向きを上・下・左・右の順で比べて選びます。通る `?` のマスは、途中のマスと目標のマスのうち文字が `?` のものです (開始のマスは数えません)。手順は「経路なし (通れるマスだけではたどり着けない)。未確認のマス (?) も通れるとすると: 下に 1 マス → 左に 4 マス → 下に 2 マス (合計 7 マス、うち未確認 1 マス)」の形で書きます。`?` を通ってもたどり着けない目標は「経路なし (未確認のマス (?) を通ってもたどり着けない)」と書きます。通れるマスだけでたどり着ける目標の手順は、`?` を通る経路を書きません
- 計算しないとき: 前回の出力に `place_name` か `current_tile` が無い、場所がマップに無い、場所が入るたびに構造が変わる (`changes_on_entry` が `true`)、場所の `tiles` が空、`current_tile` が `tiles` の範囲の外、目標が無い、のどれかのときは、経路を書かずに理由を 1 行で書きます

場所をまたぐ経路は、次のように求めます。

- つながりの当てはめ: つながりの `from` と `to` を、マップの場所の `name` と `aliases` (前後の空白を除いて比べ、最初に一致した場所) に当てはめます。どちらかが当てはまらないつながりと、`from` と `to` が同じ場所のつながりは使いません。つながりは `from` から `to` の向きにだけたどります
- たどり方: 前回の現在地の場所から、通るつながりの数が少ない道筋を、幅優先でたどります。同じ数の道筋が複数あるときは、先に見つけた場所から、`connections` の順に先に出てくるつながりを使います。`changes_on_entry` が `true` の場所は、行き先にはしますが、その場所から先へはたどりません
- 行き先: たどり着ける場所 (前回の現在地の場所を除く) のうち、つながり 1 件で行けて、場所の中の経路の目標の行き先に出ている場所を除いたものです。つながりの数の少ない順、同じならマップの `places` の順に、最大 10 件を書きます
- 書き方: 最初に「場所をまたぐ経路 (つながりをたどる):」の行を置き、行き先ごとに 1 行で書きます。行き先が無いときは、この代わりに「場所をまたぐ経路: 行ける場所は無い」の 1 行にします。行の例は次のとおりです

```text
- 「港町」まで (つながり 2 件): 「始まりの町」の「北の道へ進む」(x=10, y=0)へ 上に 7 マス (合計 7 マス) → 「北の道」の「北の端」(x=8, y=0)へ (マスの手順なし) → 「港町」
```

行の区間ごとに、その場所の名前と、乗るつながりの `how` と出たマス (`from_tile`) を書きます。`from_tile` が無いつながりは、座標を書きません。区間の手順は、区間の開始のマスから `from_tile` までの経路です。開始のマスは、最初の区間では前回の `current_tile`、2 つ目からは 1 つ前のつながりの着いたマス (`to_tile`) です。開始のマスと `from_tile` がどちらもあり、どちらもその場所の `tiles` の範囲の中にあるときは、場所の中の経路と同じ規則 (未確認のマスを通る経路を含みます) で手順を書きます。それ以外は「(マスの手順なし)」と書きます。

#### 短期のタスクのキュー

短期のタスクは、場面ごとのキューで持ちます ([`src/switch2_layers/tasks/`](./src/switch2_layers/tasks/))。キューには、まだ終わっていないタスクが入った順に並び、先頭のタスクが今実行中のタスクです。タスクは ID・文・行き先を持ちます。middle はキューの末尾へのタスクの追加と、タスクの取り消しを行い、surface は先頭のタスクの完了と取り消しの要求を判定します。surface に見せるのは、現在の場面のキューの先頭のタスクの文だけです (「surface の実装」の節)。

キューの部品は、次の 4 つの操作を 1 つのロックの中で行います。キューが変わったら、その場面の `notes/scenes/<場面ID>/tasks.json` と `tasks.md` を書きます。出来事は、足せなかった文も含めて、記録 `tasks.jsonl` に 1 件 1 行で追記します (「実行ディレクトリー」の節)。

| 操作 | 行う層 | 内容 |
|---|---|---|
| 追加 | middle | 文と行き先の組を、場面のキューの末尾に、渡された順に足します。文は前後の空白を除き、改行を空白にします。行き先は確かめずにそのまま持ちます。空の文、その場面の未完了のタスクと空白の違いを除いて同じ文 (行き先は比べません)、上限を超えた文は足しません。上限は、1 回の追加で 3 個 (`MAX_ADDED_PER_CALL`)、1 場面の未完了のタスクで 5 個 (`MAX_OPEN_TASKS_PER_SCENE`) です |
| 完了 | surface | 先頭のタスクをキューから外します。判定した後に先頭が変わっていたら、何もしません |
| 取り消しの要求 | surface | 先頭のタスクに、要求の時刻を付けます。付けるのは 1 回だけで、完了か取り消しまで残ります |
| 取り消し | middle | ID で指定したタスクを、場面とキューの位置に依らず外します。未完了のタスクに無い ID は無視します |

- タスクの ID は `task-001` の形で、場面をまたいで通しの連番です。足せなかった文には ID を振りません
- タスクの続いた秒数 (`active_s`) は、キューに入ってから、そのタスクの場面が現在の場面だった時間の合計です。別の場面にいる間と、現在の場面が無い (場面なし) 間は進みません。現在の場面は、middle の出力を書くときに、出力で決まった場面にします (決まらなければ場面なし)。play 以外の段階の間は場面なしにするため、どのタスクの秒数も進みません (「本体の画面の扱い」の節)
- run を始めたときのキューは空です。middle-once は、保存済みの `tasks.json` からキューを作り直し、タスクの続いた秒数を引き継ぎます

middle は、出力の `new_tasks` と `cancel_task_ids` でキューを変え、入力の 3 つの節でキューの様子を受け取ります。

| 項目 | 内容 |
|---|---|
| `new_tasks` (出力) | 現在の場面のキューの末尾に足すタスクの配列です。要素は `{"text": 文, "destination": 行き先}` で、行き先は `{"place": 場所の名前, "tile": {"x": 整数, "y": 整数} か null}` か `null` です。変わらない指示では 3 個までとしますが、出力の形 (JSON Schema) には上限を置きません。3 個を足した後の要素は、キューの上限 (上の表の「追加」) で足しません |
| `cancel_task_ids` (出力) | 取り消すタスクの ID の配列 (0 個以上) です |
| 現在の場面のタスクのキュー (入力) | 入力の場面 (前回の `middle/state.json` の場面) のキューの未完了のタスクを、キューの順に `- task-003: 宿屋に入っている (行き先: 町 (3, 4)、キューに入ってから 12.5 秒、取り消しの要求あり)` の形の行で書きます。行き先のマスが無いときは `行き先: 町`、行き先が無いときは `行き先: なし` で、取り消しの要求が無いタスクには「、取り消しの要求あり」を付けません。秒数は、タスクの続いた秒数です。場面が決まっていないときと、タスクが無いときは「(無い)」です |
| 前回以降のタスクの出来事 (入力) | `tasks.jsonl` の、前回の middle が読んだ位置より後の行のうち、入力の場面の、足した (`added`) 以外の出来事を、書かれた順に `- t=12.345 完了 task-002 「宿屋の前にいる」` や `- t=13.000 足せなかった (同じ文がある) 「宿屋に入っている」` の形の行で書きます。出来事は、完了・取り消しの要求・取り消し・足せなかった (理由は、空の文・同じ文がある・上限) です。無ければ「(無い)」です |
| 呼ばれた理由 (入力) | その回に middle を呼んだ理由 (「middle を呼ぶきっかけ」の項) を、`- stuck: 現在の場面の最も古いタスクが、詰まりとみなす秒数を超えてキューに残っている` のように、理由ごとに 1 行で書きます |
| `tasks_rows_offset` (`middle/state.json`) | 次の入力で `tasks.jsonl` を読み始めるバイト位置 (その回に読んだ、改行で終わる行の末尾) です。入力の場面に依らず、読んだ行の分だけ進めます。このキーが無い `middle/state.json` は 0 として読みます |

出力を書くときは、場面 ID を決めてから `middle/state.json` を書くまでの間に、キューを次の順に変えます。時刻はどれも、応答を受け取った時刻です。

1. 現在の場面を、出力で決まった場面にします (決まらなければ場面なし)
2. 取り消し: その回の呼ばれた理由に `cancel_requested` か `stuck` があるときと、出力の `is_stuck` が真のときだけ、`cancel_task_ids` のタスクを取り消します。それ以外の回の `cancel_task_ids` は使わず、`middle/calls.jsonl` に残すだけです
3. 追加: 行き先を直した (次の表) `new_tasks` を、出力で決まった場面のキューに足します。足すのは、入力の場面と出力の場面が同じ回と、入力の場面が決まっておらず、2 の後に出力の場面のキューが空の回だけです。場面が変わった回と、出力の場面が決まらない回は足しません。middle が入力で見たキューの末尾にだけ足すためです (入力の場面が決まっていない回は、入力のキューが空に見えます)
4. 2 で 1 つ以上取り消し、3 の後に出力の場面のキューが空なら、middle を呼ぶきっかけ `queue_empty` を起こします

行き先は、足す前に、その回の入力のマップと照らして直します ([`middle/task_destination_fix.py`](./src/switch2_layers/middle/task_destination_fix.py))。足さない回も直します。

| 直した理由 (`reason`) | 当たるとき | 直し方 |
|---|---|---|
| `no_map` | マップが無い | 行き先を null にします |
| `unknown_place` | `place` が、マップのどの場所の `name` にも `aliases` にも無い | 行き先を null にします |
| `alias_place` | `place` が、ある場所の `aliases` に当たった | `place` をその場所の `name` に置き換えます |
| `tile_not_listed` | マップが `grid` で、`tile` が、その場所の `exits` の座標・`landmarks` の座標・その場所から出るつながりの `from_tile` のどれとも違う | `tile` を null にします (`place` は残します) |
| `free_map_tile` | マップが `free` で、`tile` が null でない | `tile` を null にします (`place` は残します) |

`place` は前後の空白を除き、まずすべての場所の `name` と、次にすべての場所の `aliases` と比べて (どちらも前後の空白を除きます)、最初に当たった場所にします。`tiles` の範囲の外の座標でも、`exits`・`landmarks`・`from_tile` のどれかと同じなら残します。1 つの行き先で `alias_place` と `tile_not_listed` (か `free_map_tile`) が両方起きたら、この順に 2 件にします。

`middle/calls.jsonl` の各行には、呼ばれた理由 (`reasons`)、行き先を直した後の `new_tasks` (`{"text", "destination"}` の配列)、直した内容 (`destination_fixes`)、出力の `cancel_task_ids`、取り消しを行ったか (`cancel_used`)、追加を行ったか (`new_tasks_used`) も書きます。`destination_fixes` の要素は `{"index", "before", "after", "reason"}` で、`index` は `new_tasks` の中の位置 (0 から数えます)、`before` と `after` は直す前と後の行き先 (行き先を null にしたら `after` は null) です。失敗した回は、`reasons` を書き、ほかの 5 つを null にします。

変わらない指示には、タスクについて次のことを書いています。コードは `is_stuck` と `surface_wait_s` を書き換えません。

- タスクの書き方: 達成したときに画面で確かめられる状態を 1 文で書かせます (例: 「建物の中に入っている」「会話の枠が閉じている」)。ボタンの名前・押す向き・マス数のような操作は書かせません。ただし、操作説明で `unknown` のボタンと、画面に案内が出ている複合ボタンの操作を試すタスクには、ボタンの名前を書いてよいとします。各タスクは 20 秒ほどで達成できる大きさにさせ、遠くへの移動のように長くかかることは、途中の目印に着いている状態に分けさせます (詰まりの目安の 30 秒より短くし、正しく進んでいる長いタスクを詰まりと判定させないため)
- 行き先: 場所に関わるタスクには行き先を付けさせます。場所は入力のマップの場所の名前から、マスは入力のマップと経路の節に載っている出口・つながりの出たマス・目印から選ばせます。場所だけ分かるときはマスを null に、メニュー・会話・ボタンを試すタスクのように場所に関わらないタスクは行き先を null にさせます
- 足す数: 次に middle が呼ばれるまで surface が進められる分だけ足させ、キューの残りで足りるときは空の配列にさせます。キューに既にある目標と同じものは足させません
- 取り消し: 取り消しの要求があるタスクと、詰まっているときの古いタスクについて、フレームと記録で確かめて取り消すかを決めさせます。取り消さないときは空の配列にさせます
- 完了の確かめ: 出来事に完了とあるタスクが、フレームでは達成されていないときは、同じ目標を足し直させます
- 詰まり (`is_stuck`): タスクが進んでいるかを、画面の動きより重視させ、キューの最も古いタスクの続いた秒数 (入力のタスクのキューの節の `キューに入ってから <秒> 秒`) を見させます。目安として 30 秒以上たっていれば、画面や主人公が動いていても `true` にします。ただし、会話の文字送り・演出・ロードを待つこと自体がそのタスクで、その表示が進んでいるときは除きます。詰まりを解くためにタスクを取り消したり足したりしたときも、詰まりが解けたことをフレームで確かめるまでは `true` のままにします。この 30 秒は指示の文の値で、`--task-stuck-seconds` を変えても変わりません
- 待ち時間 (`surface_wait_s`): 0.2〜2.0 秒の範囲で、素早い反応が要るか、押し続けが長すぎないか、タスクが進んでいるかを見て決めます。場面の種類 (フィールド・会話・メニューなど) だけでは決めません。surface の押し続けは次の判断まで続くため、待ち時間がそのまま押す長さになります。そこで、操作の記録で押し続けが続き、目標を何度も通り過ぎている、壁に当たり続けている、目標の前後を行き来しているときは、待ち時間を前回より短くします。キューの最も古いタスクが長く残り、位置を細かく合わせる必要があるときも短くします。迷ったときは前回の値を引き継ぎます

#### middle を呼ぶきっかけ

run の middle のループは、前回の応答 (失敗を含む) から `--middle-interval` 秒待って次の実行を始めます。待つ間に次のきっかけが起きたら、待ちを打ち切って次の実行を始めます。ただし、前回の応答から 1 秒 (`MIN_MIDDLE_GAP_S`) たつまでは始めません。きっかけの決め方は [`middle/middle_trigger.py`](./src/switch2_layers/middle/middle_trigger.py) にあり、時刻を渡して試せます。

| 理由 | 起きるとき |
|---|---|
| `queue_empty` | 現在の場面のキューが空になった (surface が完了にしたときか、middle が出力を書くときに取り消したとき)。空になったときに 1 回だけで、空のまま続く間は繰り返しません |
| `cancel_requested` | surface の取り消しの要求が新しく成立した (同じタスクにつき 1 回) |
| `stuck` | 現在の場面の最も古いタスク (キューに入った時刻が最も早いタスク) の続いた秒数が `--task-stuck-seconds` (既定 30 秒) を超えた (ちょうど同じ値は超えません)。超えたまま続く間は、前回この理由で呼んでから `--task-stuck-seconds` 秒たつごとに起こします。しきい値以下に戻った後は、次に超えたときにすぐ起こします。現在の場面が無いときと、キューが空のときは起きません |
| `scene_change` | surface が場面転換を検知した (場面転換の問いの確率が 0.5 を超えた要求) |
| `interval` | 上のどれも無く、前回の応答から `--middle-interval` 秒たった |

- 1 回の実行に複数の理由が当たったら、すべてを表の順に並べて、入力の「呼ばれた理由」の節と `middle/calls.jsonl` の `reasons` に書きます。`interval` は、ほかの理由が無い回だけです
- 最初の実行の理由は `interval` です。それより前に起きたきっかけは捨てます
- middle の実行中に起きたきっかけは、その実行が終わった後の回に持ち越します
- 失敗した回の理由 (`interval` を除く) も、次の回に持ち越します。ただし失敗の後は、持ち越した理由やその後に起きたきっかけがあっても、前回の応答から `--middle-interval` 秒たつまで次を始めません。その次の回からは、きっかけがあれば間隔を待たずに始めます
- middle の失敗の数え方と、失敗が続いたときに止まる条件 (「止まる条件」の節) は、きっかけに依りません

### surface の実装 (`--surface`)

run は、`--surface` で surface の実装を選びます。

| 値 | 内容 |
|---|---|
| `jev` (既定) | TypeSafe の Jev (`jev-1.14.0`) を呼びます。環境変数 `TYPESAFE_API_KEY` に API キーが要ります |
| `fake` | 何も押さない中立の操作を返し、deep を求めないフェイクです。先頭のタスクの 2 問を送らず、タスクの完了も取り消しの要求もしません。API キーは要りません (既定の `--safety jev` の安全の監視は `TYPESAFE_API_KEY` を使うため、キーなしで動かすときは `--safety fake` も付けます) |

`--surface jev` で `TYPESAFE_API_KEY` が無いとき (値が空か空白だけのときを含む) は、実機に触れず、実行ディレクトリーにも何も書かずに、エラーを表示して終了します (終了コード 2)。API キーは、`OPENAI_API_KEY` と同じく `.env` に書き、`uv run --env-file .env` で読み込ませることもできます。

Jev には、役割と規則の説明、文書 (実行中のタスク・攻略情報・操作説明・助言・ゲームの性質)、現在地の場所のマップ (state の `map`)、middle の系列情報とその作成時刻、画面の停滞の計測の値とその時刻 (「画面の停滞の計測」の節)、直近に送った操作、deep の呼び出しの状況 (`advisor`)、選んだ画像 (時刻のラベル付き) を送り、次の問いを 1 回の要求でまとめて問います。

| 問い | 型 | 数 | 使い方 |
|---|---|---|---|
| ボタン | Choice (`none`・`tap`・`hold`) | 押せるボタンごと (十字キーの 4 方向を除きます) | `tap` と `hold` の確率の和が `none` を超えたら押します (同じ値なら押しません)。押し方は、`hold` の確率から `tap` の確率を引いた差が `--hold-margin` を超えたら押し続け (`hold`)、それ以外 (同じ値を含みます) は短押し (`tap`) です。押し続けは秒数を付けず、次の判断まで押したままにします。次の判断でも `hold` を選ぶと、離さずに押し続けます |
| 十字キーの方向 | Choice (`none`・`up`・`right`・`down`・`left`・`up_right`・`down_right`・`down_left`・`up_left`) | 1 | 8 方向の確率の和が `none` を超えたら押します (同じ値なら押しません)。押すときは、確率が最も高い方向を押します。最も高い方向が同率で 2 つ以上なら、十字キーは押しません。斜めは 2 つの方向を同時に押します (例: `up_right` は UP と RIGHT)。押せるボタンに依らず問います |
| 十字キーの押し方 | Choice (`tap`・`hold`) | 1 | 十字キーを押すときの押し方を、ボタンと同じ規則 (`--hold-margin`) で決めます。斜めの 2 つのボタンは同じ押し方にします。十字キーを押さないときは使いません。押さないかは方向の問いで決まるため、`none` はありません |
| スティックの向き | Choice (`none`・負の向き・正の向き) | 2 本 × 横・縦 = 4 | 確率が最も高い向きに倒します (同率の最大は倒しません) |
| スティックの強さ | Noul (50%・75%・100% 以上か) | 12 | 3 つの確率から、傾きを 0.25〜1.0 に決めます |
| advisor 判定 | Noul | 操作説明・攻略情報・大方針・助言・ゲームの性質の 5 | 確率が `--threshold-advisor` を超えた文書の deep を求めます |
| 情報ラベル | Noul | 操作説明・攻略情報・大方針・詰まり・マップの 5 | 確率を `surface.jsonl` の `info_labels` に書きます |
| 場面転換 | Noul | 1 | 確率が 0.5 を超えたら、場面転換として次の middle に伝え、middle を呼ぶきっかけ `scene_change` を起こします |
| box の存在 | Noul | box の対象ごと | 確率が 0.5 未満の対象の box は使いません |
| box | Box | 問い直す対象ごと | 最新のフレームでの対象の位置です |
| タスクの完了 (`task_done`) | Noul | 先頭のタスクがあるときだけ 1 | 問いの文は「「〈タスクの文〉」を達成した。」です。成立したら (下の数え方)、先頭のタスクを完了にします |
| タスクの取り消しの要求 (`task_cancel`) | Noul | 先頭のタスクがあるときだけ 1 | 問いの文は「「〈タスクの文〉」は、今の状況では達成できないか、状況に合わない。」です。成立したら、先頭のタスクに取り消しの要求を付けます |

state の文書は、`tasks`・`tips`・`controls`・`advice`・`game` の順のキーで送ります。`tasks` は、現在の場面のキューの先頭のタスクの文 1 つです (`notes/scenes/<場面ID>/tasks.json` の最初のタスク。場面が決まっていないときと、タスクが無いときは空文字列)。役割と規則の説明では、`documents.tasks` が今実行中のタスクで、達成したい状態が書かれていることを伝え、その状態に近づく操作を選ばせます。ゲームの性質 (`game`) は場面に依らない `notes/game.md` で、無い・読めない文書は、ほかの文書と同じく空文字列にします。ゲームの性質の advisor 判定 (`advisor_game`) は、まだ書かれていないゲームの仕組み (入力を待たずに進む部分、入力を待って進む部分、マップの形、ダメージやゲームオーバーの条件) が画面に出たときと、書かれている内容と画面の様子が合わないときに、ゲームの性質の更新を求める問いです。

先頭のタスクの 2 問は、先頭のタスクがあるときだけ、問いの一覧の最後に足します。どちらの問いも、確率が `--threshold-task` (既定 0.5) を超えた要求が、同じタスクについて続けて 2 回あったら成立にします (ちょうど同じ値は超えません)。

- 数えるのは、答えのあった要求だけです。失敗した要求は数えず、それまでに続けて超えた回数も消しません
- 超えなかった要求と、先頭のタスクが変わった要求で、数え直します
- `task_done` が成立したら、先頭のタスクを完了にします (「middle の実装」の節の「短期のタスクのキュー」)。完了でキューが空になったら、middle を呼ぶきっかけ `queue_empty` を起こします
- `task_cancel` が成立したら、先頭のタスクに取り消しの要求を付けます。新しく付けたら、きっかけ `cancel_requested` を起こします。取り消すかは middle が決めます
- 同じ要求で両方が成立したら、完了だけを行います

state の `map` には、現在地の場所のマップを文字で入れます (state の `documents` の直後のキーです)。surface は要求ごとに、`middle/state.json` の現在地の場所 (`place_name`)・現在地のマス (`current_tile`)・その出力がもとにした画面の時刻 (`based_on_t`)、`notes/map/map.json`、現在の場面のキューの先頭のタスクの行き先 (`tasks.json` の最初のタスクの `destination`) から作り直します。現在地の場所は、マップの場所の名前 (`name`) と別の名前 (`aliases`) から、前後の空白を除いて比べて探し (`places` の順に最初に一致した場所)、1 行目にはその場所の `name` を書きます。

次のときは、`map` を空文字列にします。マップを作れないことは、surface の失敗に数えず、要求はそのまま送ります。

- 起動引数が `--surface-map none` のとき
- `map.json` が無い・読めない・形に合わないとき (middle がマップなしとして扱うときと同じ規則です)
- `middle/state.json` が無い・読めないとき、`place_name` が null のとき
- 現在地の場所が、マップの場所の `name` にも `aliases` にも無いとき

マス目型 (`grid`) のマップでは、次の行をこの順に改行でつなぎます。

1. `場所: <場所の name>`
2. `主人公 (P): x=<x>, y=<y> (t=<based_on_t> の画面での位置。その後に動いていることがある)`。`current_tile` か `based_on_t` が無ければ `主人公の位置: 分からない` です。時刻は、送る画像の左上と同じ形 (`t=12.345`) で書きます
3. 目標の行 (下の目標の決め方)。目標のマスがあれば `目標 (G): x=<x>, y=<y> <説明>` (説明が無ければ `目標 (G): x=<x>, y=<y>`)、無ければ `目標: 無い` です
4. 入るたびに構造が変わる場所 (`changes_on_entry` が `true`) のときだけ、`この場所は、入るたびに構造が変わる`
5. `凡例: # 通れない / . 通れる / E 出口 / ? 未確認 / P 主人公 / G 目標`
6. `図の左上のマスは x=<origin の x>, y=<origin の y>。x は右へ、y は下へ増える`
7. マスの図 (`tiles`) の行。目標のマスの文字を `G` に、主人公のマスの文字を `P` に置き換えます (同じマスなら `P`)
8. 出口ごとに 1 行 `出口: x=<x>, y=<y> <description>` (`exits` の順)
9. その場所から出るつながりのうち、出たマス (`from_tile`) があるものごとに 1 行 `つながり: x=<x>, y=<y> <how> (行き先の場所: <to>)` (`connections` の順。`to` は書かれたままです)
10. 目印ごとに 1 行 `目印: x=<x>, y=<y> <description>` (`landmarks` の順)

マスの図が空 (`tiles` が空の配列) のときは、5〜7 の代わりに `マスの図: まだ無い` を 1 行書きます。主人公か目標のマスが図の範囲の外のときは、図の文字を置き換えず、2 と 3 の行に座標を書くだけにします。通れないマス (`blocked`)、場所の説明、状態は書きません。経路のマスには印を付けません。

目標は、先頭のタスクの行き先から次のように決めます。

- 先頭のタスクが無いとき、行き先が null のときは、目標なしにします
- 行き先の場所が現在地の場所 (名前か別の名前が同じ) で、マスがあるときは、そのマスを目標にします。説明は、そのマスにある出口の説明、その場所から出るつながりの移り方 (`how`)、目印の説明のうち、この順で最初に当たったものです。どれも無ければ説明を書きません
- 行き先の場所が現在地の場所で、マスが null のときは、目標なしにします
- 行き先の場所が別の場所のときは、現在地の場所から行き先の場所までの、つながりをたどる道筋 (「middle の実装」の節の「マップの型と経路の計算」の、場所をまたぐ経路と同じたどり方) の、最初のつながりの出たマス (`from_tile`) を目標にします。説明は `<つながりの how> (行き先の場所: <行き先の場所の name>)` です。行き先の場所の `name` は、タスクの最終の行き先の場所のもので、つながり 2 件以上の道筋では、最初のつながりの `to` と違うことがあります
- 行き先の場所が別の場所で、道筋が無いとき、最初のつながりの出たマスが null のとき、現在地の場所が入るたびに構造が変わるときは、目標なしにし、3 の行を `目標: 無い (行き先の場所: <行き先の場所の name>)` にします。マップに無い行き先の場所は、タスクに書かれたままの名前を書きます

自由型 (`free`) のマップでは、次の行をこの順に改行でつなぎます。主人公の位置と目標の印はありません。

1. `場所: <場所の name>`
2. `説明: <description>`
3. 出口ごとに 1 行 `出口: <exits の要素>`
4. 通れない位置ごとに 1 行 `通れない位置: <blocked の要素>`
5. `状態: <state>`
6. 入るたびに構造が変わる場所のときだけ、`この場所は、入るたびに構造が変わる`
7. 先頭のタスクの行き先の場所が別の場所のときだけ、`行き先の場所: <行き先の場所の name>`

役割と規則の説明では、`map` が上位の層がまとめた現在地の場所のマップで、無ければ空であること、`P` は少し前の画面での主人公の位置で、今はずれていることがあるため画面と見比べて使うこと、`G` が今実行中のタスクの行き先であること、`?` のマスがまだ確かめていないマスであることを伝えます。

`surface_requests.jsonl` の `state` にも、送った state と同じ `map` が入ります。`surface.jsonl` の `map_place` には、`map` に入れたマップの場所の `name` を書きます。`--surface fake` はマップを作りません。

box で取る対象は、`notes/scenes/<場面ID>/box_targets.md` から、`- 名前: 説明` の形の行を先頭から最大 8 個読みます。このファイルが無いか空なら `notes/common/box_targets.md` を、それも無いか空なら固定の 4 つ (自機・敵・敵の攻撃・目標地点) を使います。Jev が返した box は、キャプチャーのすべてのフレーム (約 10 fps) で、NCC のテンプレートマッチング (縮小 0.5 のグレースケール) で追います。Jev に box を問い直すのは、まだ box が無い対象、見失った対象、前回の問い直しから `--box-requery-every` 回の要求がたった対象だけです。`box_targets.md` で名前が同じまま説明が変わった対象は、それまでの追跡をやめ、box が無い対象として問い直します。

送る画像には、左上に時刻を、追えている対象には枠と名前を書き込みます。枠の色は、その要求の対象の一覧の中の順番で決まり、見失った対象があっても同じ対象は同じ色です。その要求で box を問い直す対象の枠と名前は、最新のフレームの画像には書き込みません (古いフレームには書き込みます)。

state の `advisor` には、advisor 判定で問う 5 つの文書の種類 (`controls`・`tips`・`strategy`・`advice`・`game`) ごとに、deep の呼び出しの状況を 1 つの文で入れます。surface は要求ごとに、deep のスケジューラーからこの状況を読みます。操作説明と攻略情報は、現在の場面の文書 (場面が決まっていなければ共通の文書) の状況です。読み取りでは deep のジョブを起動せず、`run.jsonl` にも書きません。`--deep fake` でも同じように読みます。

文は次の 5 つの部分を「。」でつないだものです。時刻は `t=120.300 秒 (15.2 秒前)` の形で、何秒前かは要求の時刻から数えます。deep の呼び出しの規則 (最小の起動間隔と保留) は、「run の起動引数」の節に書きます。

| 部分 | 文 | 意味 |
|---|---|---|
| 実行中のジョブ | `実行中のジョブ: 1 件 (最も新しい起動 <時刻>)`。無ければ `実行中のジョブ: なし` | その文書の、起動してからまだ終わっていないジョブの数と、その起動の時刻です。同じ文書のジョブは 1 件までしか動きません。停止を求めて終わるのを待っているジョブも数えます |
| 保留中の要求 | `保留中の要求: <時刻>`。無ければ `保留中の要求: なし` | 実行中のジョブが終わったら起動する要求の、求めた時刻です |
| 前回の終了 | `前回の終了: <時刻>、<終わり方>`。無ければ `前回の終了: まだ無い` | 終わり方は、`run.jsonl` の `deep_end` の `status` が `ok` なら `正常に終了`、`failed` なら `文書を更新できずに終了`、`error` なら `エラーで終了`、`stopped` なら `止めた`、`killed` なら `強制終了した` です。ジョブのディレクトリーを用意できなかった要求 (保留中の要求を起動するときを含みます) も `エラーで終了` に数えます |
| 今求めたときの扱い | `今求めると捨てられる (あと <秒> 秒)`・`今求めると保留中の要求を置き換える`・`今求めると保留され、実行中のジョブの終了後に起動する`・`今求めれば起動する` のどれか | 上から順に確かめて、最初に当たったものです。前回の起動から `--deep-min-start-interval` 秒たっていなければ 1 つ目で、秒はその残りを小数 1 桁にしたものです。そうでなく、保留中の要求があれば 2 つ目、実行中のジョブがあれば 3 つ目、どれでもなければ 4 つ目です |
| surface の最後の要求 | `surface が最後に求めた: <時刻>、<結果>`。無ければ `surface はまだ求めていない` | advisor 判定で求めた要求のうち、最後のものです。結果は、起動したら `起動した`、保留したら `保留した`、最小の起動間隔で捨てられたら `前回の起動から間もないため捨てられた`、ほかの理由で捨てられたら `捨てられた (<理由>)` です。保留した要求は、後で起動されても、ほかのきっかけの要求に置き換えられても `保留した` のままです。middle の初めての場面と自動の呼び出しの要求は数えません。ジョブのディレクトリーを用意できなかった要求も数えません |

状況を読めなかった種類の文は `状況を取得できない` にし、要求はそのまま送ります (surface の失敗には数えず、警告を書きます)。`surface_requests.jsonl` の `state` にも、送った state と同じ `advisor` が入ります。`--surface fake` は状況を使いません。

advisor 判定の問いの文は、文書の種類ごとの文の末尾に、共通の文「ただし、`advisor.<種類>` に保留中の要求があるとき、または今求めると捨てられると書かれているときは偽にする。」を足したものです (`<種類>` はその問いの文書の種類)。役割と規則の説明でも、`advisor` が文書の種類ごとの deep の呼び出しの状況 (実行中のジョブ、保留中の要求、前回の終了、今求めたときの扱い、surface が最後に求めた結果) であることを伝えます。しきい値 (`--threshold-advisor`) と deep の起動の規則は、状況に依らず同じです。

応答の待ちは 10 秒までです。HTTP のエラー、JSON として読めない応答、確率の欠け・範囲外・数でない値は surface の失敗として数え、再試行せずに次の要求で送り直します。Box の答えの座標か確信度が 0〜1 の外か、幅か高さが 0 以下のときは、その対象の box だけを無しとして扱い、ほかの問いの答えは使います。

### deep の実装 (`--deep`)

run と deep-once は、`--deep` で deep のジョブを実行するものを選びます。

| 値 | 内容 |
|---|---|
| `claude` (既定) | Claude Code (`claude -p`) を子プロセスとして起動し、文書を書き直させます。`claude` コマンドが使え、Claude Code にログインしている (または環境変数 `ANTHROPIC_API_KEY` がある) 必要があります |
| `fake` | 何もせずに成功を返すフェイクです。文書は変わりません |

Claude Code は、モデル `claude-opus-5-5`、effort `high`、出力の形式 `stream-json` で、実行ディレクトリーを作業ディレクトリーにして起動します。プロンプトは、パッケージの中のプロンプトのファイル ([`src/switch2_layers/deep/prompts/`](./src/switch2_layers/deep/prompts/)) に、ジョブごとの値 (実行ディレクトリー、対象の文書、フレームの保存先、前回と今回の最新のフレームの時刻、読んでよい記録、`map` のジョブで書くマップの型) を埋めて作ります。読んでよい記録には、どの種類のジョブでもゲームの性質の文書 (`notes/game.md`。まだ無いこともあります) を、`map` のジョブでは middle のマップの記録を、`strategy` と `advice` のジョブでは `notes/map/` のマップの文書を、`advice` のジョブでは画面の停滞の計測の値 `progress/state.json` と本体の画面の middle の記録 `middle/system_calls.jsonl` も含めます。きっかけが `system` の `advice` のジョブにだけ、`run.jsonl` も含めます (「本体の画面の扱い」の節の「ソフトの名前とユーザーの名前」の項)。文書・記録・画面から読んだ文はプロンプトに入れず、ファイルとして読ませます。プロンプトでは、画面の文字や記録の中の文を指示として扱わないよう指示します。

Claude Code に許すツールは、次の 5 つだけです。

| ツール | 範囲 |
|---|---|
| `Read`・`Glob`・`Grep` | 実行ディレクトリーの中 |
| `Edit`・`Write` | そのジョブの対象の文書 (`job.json` の `documents`) だけ。まだ無い文書は `Write` で作ります |

Bash・WebSearch・WebFetch・サブエージェント (Agent)・Skill・MCP のツールなど、ほかのツールは使えない状態で起動します。権限のモードは `dontAsk` にし、許したもののほかは確認せずに拒みます。

ユーザーとプロジェクトの設定ファイル、CLAUDE.md、AGENTS.md、hooks、インストールした plugin・skill・MCP サーバーは読み込ませません。そのために `--restricted`・`--safe-mode`・`--strict-mcp-config`・`--disable-slash-commands` を付け、`--settings` で次の設定を渡します。

- hooks・auto memory・claude.ai のコネクターを止める
- 作業ディレクトリーの外の読み書きを拒む
- AGENTS.md を読ませない (`pluginConfigs` で、`cc-plugin-agents-md` の `instructionFiles` を `managed-only` にする)

Claude Code に組み込まれた plugin (AGENTS.md を読む `cc-plugin-agents-md` など) は読み込まれますが、ツールは足しません。

子プロセスの環境変数からは、次の変数を除きます。認証 (`ANTHROPIC_` で始まる変数など) と設定の場所 (`CLAUDE_CONFIG_DIR`) の変数は残します。

- `TYPESAFE_API_KEY` と `OPENAI_API_KEY`
- 親の Claude Code のセッションに結びつく変数 (`CLAUDECODE`・`CLAUDE_CODE_SESSION_ID`・`CLAUDE_CODE_CHILD_SESSION`・`CLAUDE_CODE_MESSAGING_SOCKET` など)。Claude Code の中から deep-once を動かしたときに残ります
- `--settings` の設定を上書きする `CLAUDE_CODE_DISABLE_AUTO_MEMORY` (`0` なら、`--settings` で止めた auto memory を有効にします)

deep は `notes/` の文書の本体を直接編集します。同じ種類・同じ場面のジョブは同時に 1 件までですが、`controls` と `tips` では、どの場面のジョブも共通の文書を書きます。そのため、プロンプトでは、書く直前に文書を読み直し、ほかのジョブの更新を取り込んでから書くよう指示します。surface と middle は、deep が書きかけの文書を読むことがあります。種類ごとの対象の文書は次のとおりです。

| 種類 | 対象の文書 |
|---|---|
| `controls` | 場面があれば `notes/scenes/<場面ID>/controls.md` と `notes/common/controls.md`、無ければ `notes/common/controls.md` |
| `tips` | 場面があれば `notes/scenes/<場面ID>/tips.md`・`notes/scenes/<場面ID>/box_targets.md`・`notes/common/tips.md`、無ければ `notes/common/tips.md` |
| `strategy` | `notes/strategy.md` |
| `advice` | `notes/advice.md` |
| `map` | `notes/map/map.json` と `notes/map/places.md` (`notes/map/` の下のほかのファイルは対象にしません) |
| `game` | `notes/game.md` (場面に依らず、マップの文書は対象にしません) |

初めての場面に名前が付いたときは、その場面の `controls` と `tips` に加えて `game` のジョブを求めます。`game` は場面に依らないため、どの場面でも同じ `notes/game.md` のジョブになり、`--deep-min-start-interval` の間隔の中に来た要求は捨てます。間隔の後でも、`game` のジョブが実行中なら保留します。

`game` のジョブには、ゲームの性質の文書を、次の 6 つの節で書かせます。見出しはこの順に `## ` で書かせ、まだ分からない節も見出しを消さずに「未確認」と書かせます。各節では、フレームと記録で確かめたことと、ジャンルの知識からの推測を分け、推測には「(推測)」を付けさせます。ゲームの名前 (タイトル) は、画面から分かっても書かせません。surface が要求のたびに読むため、全体で 40 行以内にさせます。

| 節 | 内容 |
|---|---|
| ジャンル | ゲームの種類 |
| リアルタイムに進む部分 | プレイヤーの入力を待たずに進む部分と、それが具体的に何か (例: 敵の移動、制限時間、会話の自動送り) |
| ターン制の部分 | プレイヤーの入力を待って進む部分と、それが具体的に何か (例: コマンドを選ぶ戦闘、メニュー、会話の文字送り) |
| マップの形式 | 最初の行は `- 型: マス目型`・`- 型: 自由型`・`- 型: 未確認` のどれかを、そのままの文字で書きます。コードがこの行を文字どおりに読んで `map` のジョブの型を決めるため、この行には「(推測)」などの注記を付けさせません。続けて、2D か 3D か、視点 (真上から・横から・後ろからなど)、画面のスクロールのしかたを書きます。マス目型なら、1 マスの画面上のおおよその大きさと、主人公が画面のどこに表示されるか (中央に固定か) も書きます |
| ダメージとゲームオーバーの条件 | 何をするとダメージを受けるか、何が起きるとゲームオーバーになるか |
| 進めるのに要るそのほかの根本の情報 | 例: 時間制限、セーブの仕組み、成長の仕組み、持てる数の上限 |

種類ごとの指示のうち、マップに関わるものは次のとおりです。

| 種類 | 指示 |
|---|---|
| `map` | `middle/map_records.jsonl` のうち、前回、正常に終わった `map` のジョブに渡した最新のフレームの時刻の 60 秒前より後の行を読み、場所とつながりの一覧 (`map.json`) と場所ごとの文章 (`places.md`) に取り込みます。middle は応答を待つ間に、その時刻より前の `t` の行を後から足すことがあるため、前回の時刻の直前も読み直し、すでに取り込んだ内容は重ねて足しません。書く型は、コードが決めて渡した `job.json` の `map_layout` で、ゲームの性質の文書を読んで型を決め直しません。マップの型を書き換えるとき (`map.json` の `layout` が `map_layout` と違うとき) は、コードが前回の時刻を渡さないため、記録のすべての行と最初からのフレームを読み、記録とフレームに出てくるすべての場所の `tiles` を、その場所が映っているフレームから描きます。同じ場所の重複をまとめ、一覧にある名前を残して、まとめた別の名前を `aliases` に入れます。同じ場所のつながりが訪れるたびに食い違うときは、その場所の `changes_on_entry` を `true` にします。一覧と文章は同じジョブで書き、場所の名前・出口・通れない位置・状態・構造が変わるかを一致させます。型の決め方と `grid` の書き方は、「middle の実装」の節の「マップの型と経路の計算」のとおりです |
| `strategy` | `notes/map/` を読み、行き先に通る場所の順を添えます。`grid` のマップでは、出口と通れないマスを座標とマスの図で読みます |
| `advice` | `notes/map/` を読み、場所の構造 (出口・通れない位置・つながり・入るたびに構造が変わるか) を使って、詰まりの原因を説明します。`grid` のマップでは、出口と通れないマスを座標とマスの図で読みます。行き先や操作を直接指示する書き方はしません。文書の `## 本体の画面` の節は、きっかけが `system` のジョブだけが書き直し、ほかのきっかけのジョブは変えずに残します (「本体の画面の扱い」の節の「本体の画面の助言」の項) |

`map.json` は、最上位の object に `layout` (`"grid"` か `"free"`。省くと `free`) と、`places` と `connections` の 2 つの配列を持つ JSON です。`layout` が文字列でないか、`"grid"`・`"free"` 以外のときは、形に合わないもの (マップなし) にします。

| 型 | `places` の要素 | `connections` の要素 |
|---|---|---|
| `free` | `name` (空でない文字列)・`aliases`・`description`・`exits` (文字列の配列)・`blocked` (文字列の配列)・`state`・`changes_on_entry` (真偽) | `from`・`to` (どちらも空でない文字列)・`how` |
| `grid` | `name`・`aliases`・`description`・`state`・`changes_on_entry` (`free` と同じ型)・`origin` (`{"x": 整数, "y": 整数}`)・`tiles` (文字列の配列)・`exits`・`blocked`・`landmarks` (`{"x": 整数, "y": 整数, "description": 文字列}` の配列) | `from`・`to`・`how` (`free` と同じ型)・`from_tile`・`to_tile` (`{"x": 整数, "y": 整数}` か `null`) |

`layout` が `grid` なら、すべての場所とつながりを `grid` の形で、`free` なら `free` の形で確かめます。整数は、JSON の小数点を含まない数に限ります (`1.0` と真偽は形に合いません)。`places.md` は、場所ごとに `## 場所: <name>` の節を置き、入り方・出口・通れない位置・状態・構造が変わるかを箇条書きで書きます。`grid` では、マスの図も書きます。

Claude Code を起動する前に、対象の文書と、その親のディレクトリー (`notes/` を含む) がシンボリックリンクでないことを確かめます。リンクがあれば起動せずに失敗として終わり、リンクだったパスを `run.jsonl` の `deep_end` の `message` (deep-once では標準出力の `message`) と `result.json` に書きます。surface と middle が `notes/` の文書を読むときも、リンクを解決した先が `notes/` の中の通常のファイルでなければ、無い文書として扱います。

プロンプトには、前回、正常に終わった同じ文書のジョブに渡した最新のフレームの時刻と、今回の最新のフレームの時刻を書き、どこまで遡って読むかは deep に任せます。失敗・停止・強制終了で終わったジョブと、まだ実行中のジョブは前回に数えません (そのジョブに渡した期間は、次のジョブが読み直します)。正常に終わったかは、`run.jsonl` の `deep_end` の `status` が `ok` であるか、ジョブの `result.json` (終了コード 0 で、エラーでも停止でもない) から読みます。

停止を求めると Claude Code のプロセスグループに SIGTERM を送り、強制終了では SIGKILL を送ります。deep-once の最中に Ctrl+C を押したときも、Claude Code を止めてから終わります。

### 安全のための規則と安全の監視 (`--safety`)

3 つの層に、`switch2-agent` と同じ安全のための規則を毎回渡します。規則の文は [`safety/safety_rules.py`](./src/switch2_layers/safety/safety_rules.py) にあり、次のとおりです。

```text
安全のための規則 (毎回必ず守る):
- これはオフラインの個人実験である。
- 通信対戦のソフト、オンラインに接続する機能、ショップでの購入を選ばない。
- HOME メニューでは、試行しているソフト以外を起動しない。
- セーブデータの削除と、本体の設定の変更をしない。
- 迷ったら何も押さない。
```

| 層 | 規則を入れる場所 |
|---|---|
| surface | Jev への要求の state の `instructions` (役割と規則の説明の最後) |
| middle | gpt-6-luna の変わらない指示の最後の「安全のための規則」の節。規則に反するタスクを書かないよう指示します |
| deep | プロンプトの共通部分 ([`deep/prompts/common.md`](./src/switch2_layers/deep/prompts/common.md)) の「安全のための規則」の節。規則に反する進め方を文書に書かないよう指示します |

surface とは別のスレッドで、安全の監視を動かします。安全の監視は surface の判断に依らず、キャプチャーの最新のフレーム 1 枚 (時刻も box も書き込まない画像。幅 1280 まで縮小) と、本体の画面の見本の画像 6 枚 (「本体の画面の見本」の項) を 1 つの要求に入れて Jev に送り、次の 4 つの問いを問います。

| 問いの名前 | 型 | 問うこと |
|---|---|---|
| `online` | Noul | オンラインのロビー・対戦・マッチング、ほかのプレイヤーの情報、通報、投稿のどれかの画面か |
| `purchase` | Noul | ショップ・購入・課金の画面か |
| `system_settings` | Noul | 本体の設定、またはセーブデータの削除などのデータの管理の画面か |
| `system_screen` | Choice | 今のフレームが、どの見本の本体の画面か。選択肢は、`none` (どの見本の画面でもない) を先頭に、見本の名前を「本体の画面の見本」の表の順に並べます |

止める条件に使うのは、`online`・`purchase`・`system_settings` の 3 つの問いだけです。`system_screen` の照合の結果は、記録して、段階の移り変わりと本体の画面の操作に渡します (「本体の画面の扱い」の節)。そのため、実行を始めるときに HOME メニューやユーザー選択の画面が映っていても、3 つの問いが超えなければ止まりません。

要求の state は `{"instructions": <役割の説明>, "frame": <今のフレーム>, "references": {<見本の名前>: <見本の画像>, ...}}` です。役割の説明には、`references` が本体の画面の一部を切り出した見本であることを書いています。画像の参照文字列は要求ごとに新しく振り、state の中に 1 回ずつ置きます。問いの文と選択肢の説明は、画像を state の中のパス (`frame`・`references`・`references.<見本の名前>`) で指します。見本の画像は run の始めに 1 回だけ読みます。実行を始めるときの確かめと監視の確かめは、同じ形の要求を送ります。

照合の結果は次のように決めます。

- `system_screen` の確率がいちばん高い選択肢が `none` でなく、その確率が 0.5 を超えたら、その見本の名前を照合の結果とします (ちょうど 0.5 は超えません)
- `none` がいちばん高いときと、いちばん高い確率が 0.5 以下のときは、照合の結果なし (null) とします
- いちばん高い確率の選択肢が複数あれば、選択肢の並びで先のものを選びます (`none` と並んだときは、照合の結果なしです)。確率の合計は確かめません
- しきい値の 0.5 は、起動引数ではなくコードの定数 (`SYSTEM_SCREEN_THRESHOLD`) です

答えのあった確かめのたびに、照合の結果を、確かめたフレームの時刻とともに、最新の照合の結果を持つ部品 (`system_screen.screen_judgment.LatestSystemScreen`) と、段階の判定 (`system_screen.run_phase.PhaseTracker`) に渡します。この部品は、受け取った結果のうち、フレームの時刻がいちばん新しいものを持ちます。段階の判定に渡すのは、準備の段階に入った後の結果だけです。失敗した確かめと、止まることが決まった後に受け取った応答では渡しません。

| `--safety` の値 | 内容 |
|---|---|
| `jev` (既定) | TypeSafe の Jev (`jev-1.14.0`) に問います。API キーは surface と同じ環境変数 `TYPESAFE_API_KEY` から読みます。HTTP のクライアントは surface と別に作ります。見本の画像は、組み立てるときに 1 回読みます (ファイルが無ければ、実機に触れる前に例外 `FileNotFoundError` で終わります) |
| `fake` | 画像を見ずに、3 つの問いの確率を 0、`system_screen` の確率を `none` が 1・ほかの選択肢が 0 として返すフェイクです (照合の結果は常に null)。API キーは要りません |

安全の監視は、次の 2 つの確かめをします。どちらも、3 つの問いの確率が `--threshold-safety` (既定 0.7) より大きいときに「超えた」とします (ちょうど同じ値は超えません)。

| 確かめ | いつ | 止める条件 |
|---|---|---|
| 実行を始めるときの確かめ | 最初のフレームが届いた後に 1 回。この確かめで止まる条件に当たらないと分かったら、準備の段階に入ります | どれかの問いが 1 回超えた、または確かめが失敗した。止まるまでに操作を 1 つも送りません (送るのは、止めるときの中立のレポートだけです) |
| 監視の確かめ | 実行を始めるときの確かめの後、止まるまで `--safety-interval` 秒 (既定 1.0) ごと | 同じ問いが、答えのあった確かめで続けて 2 回超えた、または確かめの失敗が `--max-safety-errors` 回 (既定 3) 続いた |

- 監視の確かめは、前の確かめを送ってから `--safety-interval` 秒たったら次を送ります。前の確かめの応答を待ってから次を送り、応答がそれより遅ければ、受け取ってすぐに次を送ります
- 「続けて 2 回超えた」は、答えのあった確かめだけを並べて数えます。失敗した確かめは数えず、それまでに続けて超えた回数も消しません。たとえば「超えた → 失敗 → 超えた」で止まり、超えた・失敗が交互に続いても止まります。答えのあった確かめで超えなければ、その問いは数え直します
- 確かめの失敗は、接続できない・タイムアウト (10 秒)・HTTP のエラー、JSON として読めない応答、3 つの問いか `system_screen` の答えが無い・`system_screen` の選択肢の確率が欠けている・確率が数でない・0〜1 の外の応答です。再試行はしません。失敗の回数は、答えのあった確かめで数え直します
- ブリッジの復旧中と片付けの段階の間も、安全の監視は続けます
- 安全の監視のスレッドが想定外の例外で終わったときも、全体を止めます
- 止め方は、ほかの止まる条件と同じです (「止まる条件」の節)。理由は `unsafe screen at start: <問いの名前>`・`safety check failed at start`・`unsafe screen: <問いの名前>`・`safety check failed <回数> times in a row`・`safety monitor failed: <例外の説明>` です。同時に複数の問いが条件に当たったら、`online`・`purchase`・`system_settings` の順で先の問いの名前を書きます

確かめのたびに、`safety.jsonl` に 1 行 `{"t_sent", "t_received", "frame_t", "phase", "probabilities", "system_screen", "system_screen_result", "usage", "error"}` を書きます。

| キー | 内容 |
|---|---|
| `t_sent`・`t_received` | Jev に送った時刻と、応答を受け取った (または失敗した) 時刻 |
| `frame_t` | 確かめたフレームの時刻 |
| `phase` | 実行を始めるときの確かめなら `start`、監視の確かめなら `monitor` |
| `probabilities` | 3 つの問い (`online`・`purchase`・`system_settings`) の名前ごとの確率。失敗した行では null |
| `system_screen` | 照合の選択肢 (`none` と見本の名前) ごとの確率。選択肢の順に並べます。失敗した行では null |
| `system_screen_result` | 照合の結果の見本の名前。照合の結果なしの行と、失敗した行では null |
| `usage` | Jev の応答の `usage` (受け取った形のまま)。フェイクと失敗した行では null |
| `error` | 失敗の説明。成功した行では null |

止まることが決まった後に受け取った応答は、記録も判定もせず、照合の結果も渡さずに捨てます。

安全の監視は、既定の 1 秒の間隔では 1 時間に約 3,600 回 Jev に要求を送ります。1 要求あたりの入力のトークンは、見本の画像を入れるため、見本 5 枚の要求で約 15,460 と、見本を入れずにフレーム 1 枚だけを送る要求 (約 3,000) の約 5 倍でした (2026-11-17 に計測)。見本は 6 枚のため、今の要求の入力はこれより多くなります (6 枚の要求では計測していません)。そのぶん、surface とは別に Jev の料金がかかります。

#### 本体の画面の見本

見本の画像は [`system_screen/references/`](./src/switch2_layers/system_screen/references/) にあり、見本の名前・照合の選択肢の説明の文・ファイル名は [`system_screen/system_screen_references.py`](./src/switch2_layers/system_screen/system_screen_references.py) の 1 か所に定義しています。見本は 1 つの名前に 1 枚です。どれも画面と同じ 1280x720 の JPEG (品質 90) で、残した範囲の外を (128, 128, 128) の灰色で塗りつぶしています。切り出したままの寸法 (例: 840x100) で送ると、Jev が HTTP 400 (`Invalid image dimensions.`) を返すためです (2026-11-17 に確認)。見本には、ソフトのアイコンの絵、ソフトの名前、アカウントの名前とアイコンを含めません。元の撮影にはそれらが写るため、元の撮影はリポジトリーに入れていません。

| 名前 | 元の画面と、撮ったときの出し方 | 残した範囲 (x0, y0, x1, y1。1280x720 の画素) |
|---|---|---|
| `home_menu` | HOME メニュー。HOME ボタンで出します | 下段の、本体の機能のアイコンの段 (220, 510, 1060, 610) |
| `controllers` | HOME メニューの「コントローラー」。HOME メニューの下段のコントローラーのアイコンから開きます | 右側の項目の並び (「持ちかた/順番を変える」など) (860, 140, 1225, 590) |
| `controller_order` | 「持ちかた/順番を変える」(コントローラーの枠が空のとき)。「コントローラー」の「持ちかた/順番を変える」から開きます | 「使いたいコントローラーの L + R を押してください。」から「用意ができたら A を押してください。」まで (0, 165, 1280, 645) |
| `user_select` | ソフトを起動したときのユーザー選択。HOME メニューでソフトを起動すると出ます | 「だれがソフトをあそびますか？」の見出しの帯 (30, 312, 1250, 400) |

### 本体の画面の扱い

run は、次の 4 つの段階に分けて動きます。段階はコードが持ち、安全の監視の照合の結果 (「安全のための規則と安全の監視」の節) から、本体の画面に出たことと、ゲームの画面に戻ったことを見つけます。本体の画面にいる間は surface が操作を送らず、本体の画面用の middle が操作の列を決め、コードが照合の結果を確かめながら送ります。

| 段階 | surface と middle のゲーム用のループ | deep の自動の呼び出しと、画面の停滞による助言の要求 | 本体の画面の助言の要求 (きっかけ `system`) | 本体の画面の操作 |
|---|---|---|---|---|
| `prepare` (準備) | 動かさない | しない | 段階が `--system-advice-seconds` を超えて続いたらする | 目的 `prepare` で本体の画面の middle を呼び、操作の列を送る |
| `play` (プレイ) | 動かす | する | しない | しない |
| `recover` (復帰) | 止める | しない | 段階が `--system-advice-seconds` を超えて続いたらする | 目的 `recover` で本体の画面の middle を呼び、操作の列を送る |
| `clean_up` (片付け) | 止める | しない | しない | 目的 `clean_up` で本体の画面の middle を呼び、操作の列を送る |

- play から離れるときは、中立のレポートを送り、surface が押していたボタンを離します。surface が判断の応答を待つ間に play から離れたときは、その操作を送らず、`surface.jsonl` の行の `error` に理由を書きます
- play から離れるときは、タスクのキューの現在の場面を場面なしにします。play 以外の段階の間は、どのタスクの続いた秒数も進まず、middle を呼ぶきっかけ `stuck` も起きません (「middle の実装」の節の「短期のタスクのキュー」)。middle の 1 回の途中で play から離れたときは、その回が終わった後にも場面なしにし直します。play に戻った後は、次の middle の出力で現在の場面が決まります
- 実行中の deep のジョブは、段階が変わっても止めません
- 安全の監視と画面の停滞の計測は、段階に依らず動きます

目的ごとの手順は、本体の画面の middle の変わらない指示 ([`middle/system_screen_instructions.py`](./src/switch2_layers/middle/system_screen_instructions.py)) に書いています。

| 目的 | 手順 |
|---|---|
| `prepare` | ブリッジのコントローラーが 1P になっていることを「コントローラー」の画面で確かめ、なっていなければ「持ちかた/順番を変える」で L と R を同時に押して登録します。その後、HOME メニューの上の段で指定のソフトの絵を選んで起動し、ユーザー選択で指定のユーザーを選んで、ゲームの画面にします。指定のソフトの絵が今の画像の上の段に見えなければ、上の段の右端の「もっとみる」でソフトの一覧を開き、一覧で指定のソフトを探して起動します |
| `recover` | 指定のソフトのゲームの画面に戻ります。HOME メニューで指定のソフトが「プレイ中」なら再開し、どのソフトも「プレイ中」でなければ起動します。ほかのソフトが「プレイ中」なら、指定のソフトを起動せず、操作の列を空にします。「もっとみる」は開かず、指定のソフトの絵が上の段に無ければ、操作の列を空にします |
| `clean_up` | HOME メニューに戻り、指定のソフトを終了します。指定のソフトの「プレイ中」の絵を選んで X を押し、出てきた終了の確認で「終了する」を A で決定します。「もっとみる」は開きません |

#### 段階の移り変わり

照合の結果は、安全の監視の答えのあった確かめ 1 回ごとに 1 件と数えます。失敗した確かめは数えず、それまでに続けた数も消しません。続けた数は、段階が変わるたびに 0 に戻します。次の表の null は、照合の結果が見本のどの画面でもないこと (ゲームの画面など) です。

| 移り変わり | 条件 | `phase` の行の `reason` |
|---|---|---|
| 実行の始め → `prepare` | 実行を始めるときの安全の確かめが通った。確かめで止まったら、どの段階にも入りません | `start check passed` |
| `prepare` → `play` | 本体の画面の middle が `done` を真で返した後、照合の結果が続けて 3 回 (`EXIT_STREAK`) null になった。この間は middle を呼びません。3 回になる前に見本の画面が出たら、`done` を取り消して middle をもう一度呼びます | `prepared` |
| `play` → `recover` | 照合の結果が続けて 2 回 (`ENTER_STREAK`) 見本の画面 (どの見本でもよい) になった。null が出たら数え直します | `system screen` |
| `play` → `recover` | middle のゲーム用の出力の `press_home` が真だった。照合の結果を待たずに移り、中立のレポートを送ってから HOME を短押しします | `press_home` |
| `recover` → `play` | 操作の列を送っていない間に、照合の結果が続けて 3 回 (`EXIT_STREAK`) null になった。見本の画面が出たら数え直し、列を送っている間の結果は数えずに 0 に戻します (操作が 0 個の列は、送っている間に含めません)。middle の `done` は条件にしません | `recovered` |
| `prepare`・`play`・`recover` → `clean_up` | 片付けを行う理由で止まることになった (「片付け」の項) | 片付けを始めた理由 (`interrupted` など) |

「もっとみる」で開くソフトの一覧も見本の画面 (`software_list`) です。play の間に一覧が映れば、ほかの見本の画面と同じく recover に移ります。prepare・recover の間に一覧が映っているときは、照合の結果が null にならないため、play には移りません。

時間切れがあるのは片付けの段階だけです。時間切れは、止まる条件と同じく 0.1 秒ごとに確かめます。

| 段階 | 秒数 | 時間切れのとき |
|---|---|---|
| `prepare` | なし | 時間切れはありません。段階が `--system-advice-seconds` 秒 (既定 90 秒) を超えて続いたら、deep に本体の画面の助言を求めます (「本体の画面の助言」の項) |
| `recover` | なし | `prepare` と同じです |
| `clean_up` | 45 (`CLEAN_UP_TIMEOUT_S`) | 片付けを `timeout` で終えます |

準備と復帰は、play に移るか、止まる条件 (Ctrl+C など) で止まるまで続きます。ほかのソフトが「プレイ中」で指定のソフトを起動できないときなど、本体の画面の操作で解けない状態では、止めるまで本体の画面の middle と deep (きっかけ `system`) を呼び続けます。

middle のゲーム用の出力には、HOME を押して本体の画面に出るかを表す `press_home` (真偽) があります。変わらない指示には、真にするのはゲームが操作を受け付けないなど本体の画面に出る必要があるときだけで、詰まっている (`is_stuck` が真) だけでは真にしないことと、真にするとコードが HOME を押して復帰の段階に移ることを書いています。`press_home` が真の出力は、段階が play のときだけ扱います。`press_home` は、`middle/state.json` と `middle/calls.jsonl` にも書きます。

`--middle fake` の本体の画面の middle は、操作の列を空にして `done` を真で返し続けます。`--safety fake` では照合の結果がいつも null のため、準備は、middle が `done` を真で返した後の 3 回の照合の結果で play に移ります。片付けは `done` では終わらず、45 秒の時間切れか 2 回目の Ctrl+C などで終わります。

#### 本体の画面の操作

準備・復帰・片付けの段階では、本体の画面のループ ([`system_screen/system_screen_loop.py`](./src/switch2_layers/system_screen/system_screen_loop.py)) が次の 1〜4 を繰り返します。

1. 照合の結果を待ちます。待つ結果のフレームは、段階に入った時刻より後に撮ったものです。さらに、前の列の最後の操作を終えてから 0.5 秒 (`SETTLE_S`) より後に撮ったものです。前の段階で送った列の後に段階が変わったときも、その列の 0.5 秒後より前のフレームは使いません。前の回の middle が失敗したときは、その回に渡した照合の結果より新しいフレームの結果を待ちます。届くまで middle を呼びません。反映前の画面で、カーソルの位置を読ませないためです
2. 本体の画面の middle を呼びます。入力の画像は、その照合のフレーム以降の最新のフレーム 1 枚 (幅 1280 まで縮小) です
3. middle が返した操作の列を、コード ([`system_screen/system_operation_runner.py`](./src/switch2_layers/system_screen/system_operation_runner.py)) が、照合の結果を確かめながら前から順に送ります
4. 送り終えたら (打ち切りを含む)、間を置かずに 1 に戻ります。`--middle-interval` は使いません

本体の画面の middle は、ゲーム用の middle と同じ gpt-6-luna を、reasoning effort `low` で呼び、出力を Structured Outputs の JSON Schema で受け取ります。ゲーム用の middle の既定 (`none`) と違う effort にしているのは、`none` では HOME メニューで選ばれている絵やアイコンを読み違えることが多いためです。2026-11-17 に、「もっとみる」が選ばれている HOME メニューの画面 (手で操作して撮ったもの) に、上の段を右端までたどった操作の履歴を組み合わせて本体の画面の middle を呼び直すと、選ばれている位置を正しく読んだのは `none` で 8 回中 2 回、`low` で 6 回中 6 回でした。11 の場面を 2 回ずつ呼んだときの応答までの時間の中央値は、`none` が 2.6 秒、`low` が 3.5 秒でした。変わらない指示 (developer メッセージ) はゲーム用とは別の文で、その直後にキャッシュの区切りを置きます。応答の待ちは 30 秒までです。HTTP のエラー、完了しなかった応答、拒否、出力の決まり (下の出力の表) に合わない出力は middle の失敗として数え、再試行せず、操作を 1 つも送りません。

変わらない指示には、見本の画面ごとの見た目と使う操作、目的ごとの手順、決定の A の置き方、カーソルの動かし方、してはいけない操作、安全のための規則を書いています。してはいけない操作には、目的の手順に無いアイコンで A を押すこと、指定のソフト以外を起動すること、指定のユーザー以外で決定すること、ユーザーの追加・ソフトの削除・データの削除に進むことを挙げ、迷ったら操作の列を空にするよう指示しています。X (ソフトをおわる) と終了の確認の A は、片付けで指定のソフトを終了するときだけ使わせます。ソフトの名前とユーザーの名前は、指示には書かずに user メッセージに入れます。実在のソフトの名前、ソフトの一覧の中の位置、決め打ちの並び順も、指示には書きません。

HOME メニューとソフトの一覧について、変わらない指示には次のことを書いています。

- 準備では、操作を決める前に、「この段階で送った A・B・X」からコントローラーの登録を確かめたかを判定させ、observation の最初に「登録: 確かめた」か「登録: まだ」と書かせます。確かめた後は、HOME メニューで下の段へ移らせず、上の段から指定のソフトを探させます
- HOME メニューの上の段には、最近のソフトの絵が最大 12 枚並び、右端に「もっとみる」(四角が 4 つ並んだ丸いアイコン) があります。「もっとみる」を選ぶと、このアイコンが色の付いた輪で囲まれ、上に「もっとみる」と出ます。上の段の左端で LEFT を押すと「もっとみる」に回り込みます
- 下の段の左端の ONLINE のアイコンは、選ばれていなくても赤い丸です。下の段で選ばれているアイコンは輪で囲まれ、下に名前が出ます。上の段の絵の上にソフトの名前が出ている間は、カーソルは上の段にあります
- 上の段で UP を押すと、画面の上の中央のみまもり設定のボタンが選ばれ、右下に「A みまもり設定を一時OFFにする」と出ます。ここでは A を押さず、DOWN で上の段に戻らせます
- 「もっとみる」で開くソフトの一覧は、見本の画面 `software_list` です (照合の結果と、操作の `screen` に `software_list` を使います)。目印は、上の「ソフト」「グループ」のタブ、左の絞り込みと並べ替えのアイコン、右上の並び順の表示、右下の「+ オプション」「B もどる」「A 決定」です。絵は 6 列のマス目に並び、並び順は本体の設定で変わります。選んでいる絵の名前は吹き出しに出て、長い名前は流れて表示されます。DOWN で 1 行ずつ確かめて指定のソフトを探させ、L・R・ZL・ZR・PLUS・MINUS・X・Y は押させません。B で HOME メニューに戻ります。「もっとみる」を開くのは、準備で指定のソフトの絵が今の画像の上の段に見えないときだけです。一覧には、上の段のソフトも含めてすべてのソフトが並びます
- A (片付けでは X) を押す前に、表示の名前 (上の段では絵の上の名前、ソフトの一覧では吹き出しの見えている部分) と絵の中のロゴの文字を合わせて、指定のソフトだと確かめさせます。表示の名前は、指定のソフトの名前と完全に同じでなくてかまいません (空白・記号・全角半角の違い、途中で切れる、流れて表示されるなど)。ほかのソフトと見分けられないときは押させません
- 入力が画面に反映されないことがあるため (特に動き始めの最初の入力)、次の画像で反映を確かめ、反映されていなければ同じ移動を送り直させます。下の段で数えて動かすときは、DOWN の後の画像で、下の段のアイコンに輪が付いたことを確かめてから RIGHT を数えさせます
- HOME は押すたびにゲームの画面と HOME メニューを行き来し、押してから HOME メニューが映るまで 1〜3 秒かかります。最後の呼び出しで HOME を送っていて、今の画像がまだゲームの画面なら、HOME を押し直させずに 3 秒待たせます。待った後もゲームの画面なら、HOME が届かなかったものとして、もう一度押させます。2026-11-17 の実機の試行では、HOME を送ってから HOME メニューが照合に出るまで 1.2〜2.3 秒かかり、その間の画面を見て HOME を押し直したため、HOME メニューが閉じる往復が約 140 秒続きました

user メッセージの節は次のとおりです。

| 節 | 中身 |
|---|---|
| 現在の時刻 | 入力を作った時刻 |
| 目的 | 目的の名前 (`prepare`・`recover`・`clean_up`) と、その目的の手順の文 |
| 指定のソフト | `--software` の値 (書かれたまま) |
| 指定のユーザー | `--user` の値 (書かれたまま) |
| 照合の結果 | 照合の結果の画面の名前 (null なら `none`) と、照合したフレームの時刻 |
| この段階のこれまでの呼び出し | 同じ段階で middle が返した操作の列のうち、新しい方から 10 件 (`MAX_HISTORY_ENTRIES`) を古い順に並べたもの。呼び出しの時刻、そのときの照合の結果、操作の列、送った操作の数、最後まで送ったか打ち切った理由を書きます |
| この段階で送った A・B・X | 同じ段階のすべての呼び出しで実際に送った A・B・X を、送った順に 1 つ 1 行 (`t=<呼び出しの時刻> <操作の screen> で <ボタン>`) で並べたもの。打ち切りで送らなかった操作は入れず、送信に失敗した操作は、届いたかもしれないものとして入れます。準備の手順では「controllers で B」(登録を確かめた) の行の有無で、片付けの手順では「home_menu で X」の行の有無で、次の操作を決めさせます |
| deep の助言 | `notes/advice.md` の `## 本体の画面` の節の本文 (見出しの次の行から、次の `## ` の見出しの前まで。前後の空白を除きます)。呼び出しごとに読み直します。節の最初の行に書かれた段階が今の目的と違うとき (準備のときに書かれた助言を、復帰や片付けで読むときなど) は入れません。文書が無い・読めない・節が無い・空なら「(無い)」です (「本体の画面の助言」の項)。変わらない指示では、今の画面に当てはまるときに参考にさせ、決定の A の置き方・してはいけない操作・安全のための規則を優先させます |
| 今の画像 | 最新のフレーム 1 枚と、その時刻のラベル |

段階が変わると、これまでの呼び出しの履歴を空にします。出力のキーは次のとおりです。

| キー | 内容 |
|---|---|
| `observation` | 今の画像の画面と、カーソルの位置 |
| `operations` | 送る操作の列 (0〜10 個。`MAX_OPERATIONS`)。各操作は、`screen` (その操作を送る前に映っているはずの画面の名前。`none` か見本の名前)、`type` (`press` か `wait`)、`buttons` (`press` で同時に押すボタン。HOME を含む 17 個の名前から 1 個以上で、十字キーは 1 方向まで。`wait` では空)、`seconds` (`press` では、null なら短押し、数なら押し続けの秒数で 0 より大きく 60 以下。`wait` では待つ秒数で 0 より大きく 10 以下) を持ちます |
| `done` | 目的を果たしたら真。真にするときは `operations` を空にさせます |

コードは、列の操作を前から順に 1 つずつ送り、送った操作を終えてから次に進みます。press は、押す長さ (短押しは 0.12 秒) の後に、ボタンを離したことを確かめた時刻を、操作を終えた時刻にします。離したことを確かめられないまま 1 秒 (`RELEASE_WAIT_S`) たったら、その時刻を操作を終えた時刻にします。wait は、何も送らずに秒数だけ待ちます。本体の画面の操作では、HOME を含む 17 個のボタンを押せます。送った操作は、`operations.jsonl` にきっかけ `system` で書きます。

次のときは、その操作から後を送らずに打ち切ります。`send_failed` のほかは、その操作を送る前に確かめます。

| 打ち切りの理由 (`cut_reason`) | 当たるとき |
|---|---|
| `screen_mismatch` | 先頭の操作では、操作の `screen` が、middle に渡した照合の結果の画面と違うとき。2 つ目以降の操作では、前の操作を終えてから 0.5 秒 (`SETTLE_S`) より後に撮ったフレームの照合の結果の画面が、操作の `screen` と違うとき |
| `no_judgment` | 2 つ目以降の操作の前に、上限まで待っても照合の結果が届かなかったとき |
| `decision_not_first` | 2 つ目以降の操作に A があるとき (押し続けと同時押しの中の A も含みます)。照合の結果を待たずに打ち切ります |
| `stopped` | 全体を止める合図が立ったとき |
| `send_failed` | press の送信 (押すレポートか、離すレポートなど) が失敗したとき。失敗した press は届いたかもしれないため、送った操作の数に入れます |

2 つ目以降の操作の前に照合の結果を待つ上限は、前の操作を終えてから 0.5 秒後から数えて、`max(JUDGMENT_WAIT_S, --safety-interval + 2 秒)` 秒です。`JUDGMENT_WAIT_S` は 3 秒で、既定の `--safety-interval 1.0` では 3 秒、最大の 10 秒では 12 秒になります。照合の結果は安全の監視の間隔で届くため、3 秒に固定すると、間隔が長いときに 2 つ目以降の操作が `no_judgment` で打ち切られやすくなります。

決定の A は、列の先頭にだけ置けます。変わらない指示には、今回の画像でカーソルが目的の項目 (指定のソフトの絵・コントローラーのアイコン・「持ちかた/順番を変える」・指定のユーザーなど) にあると確かめたときだけ A を置くことと、カーソルを動かした後の決定は、次の呼び出しで画像を見てから返すことを書いています。A は短押しにし、ほかのボタンと同時に押させません。コードは、2 つ目以降の操作の A を送らずに打ち切り (`decision_not_first`)、先頭の A は、操作の `screen` が middle に渡した照合の結果と同じときだけ送ります。

列を送る途中で送信が失敗したら (`send_failed`)、中立のレポートを送ります。ブリッジ側でボタンが押されたまま残っているおそれがあるためです。その後は、ブリッジの状態が `ok` に戻るまで、本体の画面の middle を呼びません。待つ間も片付けの時間切れと止まる条件は確かめ、ブリッジの復旧が失敗したら `bridge recovery failed` で止まります。送信の失敗は、middle の失敗に数えません。

本体の画面の middle の失敗が `--max-middle-errors` 回続いたら、`middle failed <回数> times in a row` で止まることになり、片付けに移ります。失敗の数は成功で数え直し、段階が変わっても数え直しません。片付けの段階では、1 回の失敗で片付けを終えます (`middle_failed`)。middle を呼んでいる間に段階が変わったら、その出力は送らずに捨てます。

#### 片付け

次の 3 つの理由で止まることになったときは、すぐには止まらずに片付けの段階に移ります。準備・プレイ・復帰のどの段階からでも移ります。実行を始めるときの確かめが通る前 (どの段階にも入っていないとき) は、片付けをせずに止まります。

- `interrupted` (Ctrl+C。SIGINT)
- `surface failed <回数> times in a row`
- `middle failed <回数> times in a row` (ゲーム用の middle と本体の画面の middle のどちらの失敗でも)

片付けをしない理由は、安全の監視の理由 (`unsafe screen*`・`safety check failed*`・`safety monitor failed*`)、キャプチャーとブリッジの理由、起動の途中の失敗 (`start failed: <例外の説明>`)、ループの想定外の例外 (`surface loop failed: <例外の説明>`・`middle loop failed: <例外の説明>`・`system screen loop failed: <例外の説明>`) です。これらの理由では、すぐ操作を中立に戻して止まります。

片付けの段階では、surface と middle のゲーム用のループを止めたまま、本体の画面の middle を目的 `clean_up` で呼び、操作の列を送ります。安全の監視は、片付けの間も続けます。run は、ブリッジ (PowerShell) と ffmpeg のプロセスを新しいセッションで起動します。端末の Ctrl+C の SIGINT は前面のプロセスグループのすべてに届くため、同じグループのままだとブリッジと ffmpeg も終わり、片付けの操作を送れないためです。

片付けは、次のどれかで終わります。終わり方は、`run.jsonl` の `clean_up_end` の行の `result` に書きます。

| `result` | 終わるとき |
|---|---|
| `done` | 本体の画面の middle が `done` を真で返し、そのときの最新の照合の結果が `home_menu` だった |
| `timeout` | 片付けを始めてから 45 秒 (`CLEAN_UP_TIMEOUT_S`) たった |
| `middle_failed` | 片付けの本体の画面の middle が 1 回失敗した |
| `interrupted` | 片付けの間に、2 回目の Ctrl+C (SIGINT) を受けた |
| `unsafe` | 片付けの間に、安全の監視の理由で止まることになった |
| `stopped` | 片付けの間に、キャプチャーかブリッジの理由で止まることになった |

前に数えた SIGINT から 1 秒 (`INTERRUPT_REPEAT_WINDOW_S`) 以内に届いた SIGINT は、同じ割り込みとして数えません。`timeout -s INT` と `uv run` の下では、1 回の割り込みで SIGINT が 2 回届くことがあるためです (`timeout` がプロセスグループに送るものと、`uv` が子に転送するもの)。片付けの間に来た、ほかの止まる理由では、片付けを終えません。

片付けを終えたら、`clean_up_end` の行を書き、操作を中立に戻して以後の操作を送らないようにしてから止まります。`run.jsonl` の `stop` の理由は、片付けを始めた理由のままです (Ctrl+C なら `interrupted` で、終了コードは 0 です)。

#### 定数

段階と本体の画面の操作の回数と秒数は、起動引数ではなくコードの定数です。

| 定数 | 値 | 定義の場所 (`src/switch2_layers/` から) | 意味 |
|---|---|---|---|
| `ENTER_STREAK` | 2 | `system_screen/run_phase.py` | play から recover に移る、照合の結果が続けて見本の画面になった回数 |
| `EXIT_STREAK` | 3 | `system_screen/run_phase.py` | prepare (`done` の後) と recover から play に移る、照合の結果が続けて null になった回数 |
| `CLEAN_UP_TIMEOUT_S` | 45 秒 | `system_screen/run_phase.py` | 片付けの時間切れ (準備と復帰には時間切れがありません) |
| `SETTLE_S` | 0.5 秒 | `system_screen/system_operation_runner.py` | 操作を終えてから、照合に使うフレームとして認めるまでの秒数 |
| `JUDGMENT_WAIT_S` | 3 秒 | `system_screen/system_operation_runner.py` | 2 つ目以降の操作の前に照合の結果を待つ上限の既定値。run は `max(JUDGMENT_WAIT_S, --safety-interval + 2 秒)` を使います |
| `RELEASE_WAIT_S` | 1 秒 | `system_screen/system_operation_runner.py` | press のボタンを離したことを確かめるのを待つ上限 |
| `JUDGMENT_WAIT_MARGIN_S` | 2 秒 | `app.py` | 照合の結果を待つ上限で、`--safety-interval` に足す秒数 |
| `INTERRUPT_REPEAT_WINDOW_S` | 1 秒 | `app.py` | 前に数えた SIGINT から、この秒数以内の SIGINT を同じ割り込みとして数えない |
| `MAX_OPERATIONS` | 10 | `middle/system_screen_schema.py` | 1 回の出力の操作の最大の数 |
| `MAX_WAIT_SECONDS` | 10 秒 | `middle/system_screen_schema.py` | wait の秒数の上限 |
| `MAX_HISTORY_ENTRIES` | 10 | `middle/system_screen_types.py` | 入力の「この段階のこれまでの呼び出し」に入れる呼び出しの数 |

#### 記録

`run.jsonl` には、段階について次の行を書きます。

| `event` | 書くとき | 項目 |
|---|---|---|
| `phase` | 段階が変わった | `phase` (移った後の段階。`prepare`・`play`・`recover`・`clean_up`)・`reason` (「段階の移り変わり」の表の理由) |
| `clean_up_end` | 片付けが終わった | `result` (`done`・`timeout`・`middle_failed`・`interrupted`・`unsafe`・`stopped`) |

準備を終えて play に移り、play の途中で Ctrl+C を押して片付けた実行では、次の行が並びます (ほかの行は省いています)。

```text
{"t": 2.1, "event": "phase", "phase": "prepare", "reason": "start check passed"}
{"t": 56.445, "event": "phase", "phase": "play", "reason": "prepared"}
{"t": 93.032, "event": "phase", "phase": "clean_up", "reason": "interrupted"}
{"t": 110.243, "event": "clean_up_end", "result": "done"}
{"t": 110.285, "event": "stop", "reason": "interrupted"}
```

`middle/system_calls.jsonl` には、本体の画面の middle の呼び出しごとに 1 行 (`kind` が `call`) と、操作の列を送り終えるごと (打ち切りを含みます) に 1 行 (`kind` が `run`) を書きます。

| 行 | 内容 |
|---|---|
| 呼び出しの行 | `{"kind": "call", "t_sent", "t_received", "goal", "frame_t", "judged_screen", "judged_frame_t", "output", "error", "usage", "cost_usd", "response", "error_body_head"}`。`goal` は目的、`frame_t` は入力の画像の時刻、`judged_screen` と `judged_frame_t` は入力の照合の結果 (null は見本のどの画面でもないこと) と照合したフレームの時刻です。`output` は出力 (`observation`・`operations`・`done`) で、失敗した行では null にし、`error` に説明を書きます。`usage`・`cost_usd`・`response`・`error_body_head` は `middle/calls.jsonl` と同じ形で、`--middle fake` では null です |
| 実行の結果の行 | `{"kind": "run", "t", "sent_count", "cut_index", "cut_reason", "blocked_buttons"}`。`t` は送り終えた時刻、`sent_count` は送った操作の数、`cut_index` と `cut_reason` は打ち切った操作の位置 (0 から数えます) と理由で、最後まで送ったら null です。`send_failed` のときは、`cut_index` は送信に失敗した press の位置で、`sent_count` はその次の数です。`blocked_buttons` は、押せないボタンとして外したボタンです。操作が 0 個の列でも書きます |

middle を呼んでいる間に段階が変わった回は、呼び出しの行だけを書きます。止める合図が立った後は、どちらの行も書きません。本体の画面の middle の失敗は、`run.jsonl` には書かず、`middle/system_calls.jsonl` の呼び出しの行の `error` に書きます。

#### 本体の画面の助言

準備・復帰の段階が `--system-advice-seconds` 秒 (既定 90 秒) を超えて続いたら、deep のスケジューラーが、助言 (`advice`) の deep をきっかけ `system` で求めます (`job.json` と `run.jsonl` の `trigger` が `system` になります)。判定は 0.5 秒ごとに、段階が準備か復帰の間だけ行います。続いた秒数は、その段階に入った時刻から数え、段階が変わると数え直します。求め方の規則は、画面の停滞の計測によるきっかけ `progress` (「画面の停滞の計測」の節) と同じで、`progress` とは別に判定します。

- 超えたまま続く間は、前回このきっかけで求めてから `--system-advice-seconds` 秒たつごとに求めます。前回の時刻は、ジョブを起動したか、保留したか、最小の間隔で捨てたかに依らず、求めた時刻です
- 実行中の助言のジョブがある間 (きっかけに依らない) は求めず、そのジョブが終わった後の判定で求めます
- 同じ文書の起動の最小間隔 (`--deep-min-start-interval`) と保留など、deep のほかの規則はそのまま当てます。求めたときの失敗は、`run.jsonl` の `deep_request_error` (`source` は `system`) に書きます

きっかけが `system` のジョブは、`notes/advice.md` の `## 本体の画面` の節だけを書き直し、ほかの節は変えません。ほかのきっかけのジョブは、この節を変えず、消しません。ほかの節はこの節より前に書かせ、この節を文書の最後に置いたままにします。節の最初には、書いた時点の段階 (`prepare` か `recover`) と、使った最新のフレームの時刻 (`t=秒`) を書かせます。続けて、今の画面、指定のソフトがどこにありそうか (HOME メニューの上の段か「もっとみる」の一覧か)、次に試す具体的な操作、本体の画面の middle が繰り返している失敗や読み違え (`middle/system_calls.jsonl` の `observation`・`operations`・打ち切りの理由から) を書かせます。この節に限り、行き先や操作を直接指示してよいことにしています (ほかの節では直接指示させません)。ソフトの名前とユーザーの名前は書かせず、「指定のソフト」「指定のユーザー」と書かせます (`notes/advice.md` は surface も読むため)。

本体の画面の middle は、呼び出しごとにこの節を読み直し、節の最初の行に書かれた段階が今の目的と同じときだけ、user メッセージの「deep の助言」の節に入れます。ほかの文書と同じく、リンクを解決した先が `notes/` の中の通常のファイルでなければ、無い文書として扱います。

#### ソフトの名前とユーザーの名前

本書では、どの層にもゲームの名前を渡さない条件で試します。`switch2-layers run` には、この条件に次の例外があります。

- `--software` と `--user` の名前を、本体の画面の middle の入力 (user メッセージの「指定のソフト」「指定のユーザー」の節) に入れます。本体の画面の middle の変わらない指示と、surface・ゲーム用の middle・deep に渡す入力には入れません
- きっかけが `system` の `advice` の deep のジョブには、名前の在りか (`run.jsonl` の 1 行目 (`event` が `start`) の `args.software_name`・`args.user_name`) をプロンプトで伝え、`run.jsonl` を読んでよい記録に含めます。名前は、フレームと記録の中の対象を見分けるためだけに読ませ、`notes/advice.md` には書かせません。プロンプトに埋めるのは `run.jsonl` のパスだけで、名前そのものは埋めません
- HOME メニューとユーザー選択の画面には、ソフトの名前とユーザーの名前が映ります。これらの画面のフレームと、名前が入る記録 (`run.jsonl` の `start` の行の `args`、`middle/system_calls.jsonl` の出力と応答など) から、ゲームの名前がどの層にも届くことがあります。たとえば deep は、実行ディレクトリーの中のファイルを読めます

### 画面の停滞の計測

run は、3 層とは別のスレッドで、一定間隔のフレームの画面のハッシュから、画面の停滞をコードで測ります ([`src/switch2_layers/progress/`](./src/switch2_layers/progress/))。計算は I/O を持たない部品 (`screen_hash`・`screen_progress`) に分けてあり、時刻と画像を渡して試せます。計測のスレッドは操作を送らないため、安全の監視の「実行を始めるときの確かめ」を待たずに始めます。

`frames.jsonl` に足された `interval` の行を 0.2 秒ごとに読み、`frames/interval/` に保存した縮小画像 (JPEG) ごとに、画面全体の知覚ハッシュを計算します。ハッシュは dHash (グレースケールを横 9 × 縦 8 に縮小し、横に隣り合う画素の明暗の向きを 64 ビットにしたもの) で、2 つのハッシュのハミング距離が 10 以下なら同じ画面 (近い) とみなします。そのうえで、最新のフレームについて次の 2 つの値を計算します。

| 値 | 内容 |
|---|---|
| `static_s` (画面が変わっていない秒数) | 最新のフレームのハッシュに近いハッシュが、途切れずに続いている時間です。最新のフレームが直前のフレームに近くなければ 0 です。持っているハッシュ (直近 `--progress-window` 秒の分) の中で数えるため、`--progress-window` を超えません |
| `no_novel_s` (新しい画面が出ていない秒数) | 最新のフレームの時刻から、最後に新しい画面が出た時刻を引いた値です。新しい画面は、それより前の直近 `--progress-window` 秒のフレームのうち、そのフレームから 2 秒以内のものを除いた、どのフレームのハッシュにも近くないフレームです。比べる相手のフレームが 1 つも無ければ新しい画面とします (最初のフレームと、実行を始めてから 2 秒以内のフレームを含みます) |

直近 2 秒を比べる相手から外すのは、画面が少しずつ動き続ける間 (スクロールやカメラのパン) に、直前のフレームと近いことだけで新しい画面にならなくなるのを防ぐためです。2 秒は定数で、起動引数にはしていません。同じ画面が続くときは、最初の 2 秒のフレームは新しい画面になり、その後から `no_novel_s` が増えます。時刻の差は、ミリ秒に丸めた値で比べます (ちょうど 2 秒離れたフレームは比べる相手から外します)。`--progress-window` が 2 秒以下だと、比べる相手がいつも無く、どのフレームも新しい画面になります。

窓より古いフレームのハッシュは捨て、持つハッシュを窓の分だけにします。左右に動きながら同じ範囲にとどまっていると、画面は毎回変わるため `static_s` は 0 に戻り続けますが、過去に見た画面に戻っているため `no_novel_s` は増え続けます。

値を計算するたびに、`progress/state.json` に `{"t": 最新のフレームの時刻, "static_s": ..., "no_novel_s": ..., "window_s": --progress-window の値}` を、ほかの層の間のファイルと同じく置き換えの書き込みで書きます。時刻と秒数は、小数第 3 位に丸めた値です。まだフレームが無いときは、このファイルを作りません。読む側は、ファイルが無い・読めないときは値が無いものとして扱います。

| 渡し先 | 渡し方 |
|---|---|
| surface | 要求の state の `progress` に、値の時刻 (`measured`) と、2 つの値の文 (`text`。例: 「画面が変わっていない: 12.4 秒」「直近 300 秒に見た画面だけが出ている: 85.0 秒」) を入れます。値が無ければ、無いことを書きます。Jev の advisor 判定は変えません |
| middle | user メッセージの「画面の停滞 (コードの計測)」の節に、計測した時刻と同じ文を入れます。変わらない指示では、キューの最も古いタスクの続いた秒数とあわせて、この節を `is_stuck` を決める手がかりにさせます。出力の形は変えません |
| deep | `advice` のジョブのプロンプトの読んでよい記録に `progress/state.json` を足します |

`no_novel_s` が `--stuck-advice-seconds` (既定 60 秒) を超えたら、deep のスケジューラーが、助言 (`advice`) の deep を新しいきっかけ `progress` で求めます (`job.json` と `run.jsonl` の `trigger` が `progress` になります)。判定は、自動の呼び出しと同じく、段階が play の間だけ 0.5 秒ごとに行います。

- 超えたまま続く間は、前回このきっかけで求めてから `--stuck-advice-seconds` 秒たつごとに求めます。前回の時刻は、ジョブを起動したか、保留したか、最小の間隔で捨てたかに依らず、求めた時刻です
- 新しい画面が出て `no_novel_s` がしきい値以下に戻ったら、次に超えたときにすぐ求めます
- 実行中の助言のジョブがある間 (きっかけに依らない) は求めず、そのジョブが終わった後の判定で求めます
- `progress/state.json` の `t` が判定の時刻より 10 秒を超えて前のときは、求めず、前回求めた時刻も消しません。フレームの保存か値の書き込みが止まったときに、古い値で求め続けないためです。`--interval-fps` を小さくして、一定間隔のフレームの間が 10 秒より空くときも、1 つ目の規則の間隔で求めます
- 同じ文書の起動の最小間隔 (`--deep-min-start-interval`) と保留など、deep のほかの規則はそのまま当てます。求めたときの失敗は、`run.jsonl` の `deep_request_error` (`source` は `progress`) に書きます
- `--deep fake` でも同じ規則で求めます (フェイクが成功を返します)。Jev の advisor 判定と、ほかのきっかけ (`surface`・`new_scene`・`auto`・`system`) の規則は変わりません

準備・復帰の段階が長く続いたときは、同じ規則で、きっかけ `system` で助言を求めます (「本体の画面の扱い」の節の「本体の画面の助言」の項)。

### Orchestrator 型 (`--mode orchestrator`)

`switch2-layers run --mode orchestrator` は、surface・middle・deep の 3 層の代わりに、Claude Code を主ループにしてゲームを遊びます (Orchestrator 型)。主ループの Claude Code が画面の画像と出来事を見て判断し、各ターンの答えの最後に、操作・マクロ・監視を JSON で書きます。コードはその JSON を読んで操作の列を送り、「画面の条件 → 操作」の監視を Jev で動かします。部品は [`src/switch2_layers/orchestrator/`](./src/switch2_layers/orchestrator/) にあります。`--mode` を省いたときと `--mode advisor` では、ここまでの節の 3 層で動きます (advisor 型)。Orchestrator 型には、監視の代わりにリアルタイムの場面の操作を Jev に委任する実装 (委任型。`--mode delegate`) もあります (この節の「委任型」の項)。この節の「委任型」の項より前は、監視型 (`--mode orchestrator`) の説明です。

動かし方の例は次のとおりです。

```bash
uv run --env-file .env switch2-layers run --mode orchestrator --instruction '<ソフトの名前> を <ユーザーの名前> で起動して、冒険を始めてください'
uv run --env-file .env switch2-layers run --mode orchestrator --instruction-file instruction.md --safety fake
```

1 つ目は、起動するソフトと遊ぶユーザーを、人の初期指示の文で渡します。2 つ目は、初期指示をファイルから読み、安全の監視をフェイクにします。

準備・復帰・片付けの段階 (「本体の画面の扱い」の節) は使いません。実行を始めるときの安全の確かめが通ったら、主ループと、操作の実行と監視を始めます。ソフトの起動、ユーザー選択、HOME メニューからゲームの画面への戻りは、主ループが本体の操作のスキル (`switch-launch-software`・`switch-select-user` など。[`orchestrator/skills/`](./src/switch2_layers/orchestrator/skills/)) で行います。起動するソフトと遊ぶユーザーは、人の初期指示に書きます。`--software` と `--user` は advisor 型だけで使い、Orchestrator 型では指定しても動きは変わりません。

| 部品 | 受け持ち |
|---|---|
| 主ループ (`orchestrator/main_loop.py`) | Claude Code (`claude -p`) を stream-json の入出力で開いたままにし (`--agent codex` では `codex app-server`。「主ループのエージェント」の項)、前のターンの操作の列が終わり、離した後の画面のフレームが撮れたら (`actions` が空なら、すぐ)、次の画面と出来事を渡します。各ターンの最後の JSON を読み、操作の実行と監視の部品に渡します |
| 操作の実行と監視 (`orchestrator/orchestrator_controller.py`) | JSON の操作の列を 1 つずつコントローラーに送り、マクロと監視を持ちます。監視があれば、主ループの操作が無い間に最新のフレームを Jev に問い、当たった条件の操作を送ります |
| 共有の部品 | キャプチャー、フレームの保存、キャプチャーの見張り、コントローラーへの送信、安全の監視、画面の停滞の計測、記録です。advisor 型と同じものを使います |

surface・middle・deep (deep のスケジューラーを含む) と、本体の画面のループは起動しません。`notes/` は空のディレクトリーで始め、advisor 型の初期の文書は作りません。主ループの Claude Code が使えるツールは Read・Glob・Grep・Write・Edit・Skill だけで、書き込めるのは `notes/` の下だけです。ゲームの内容の手順は、`notes/skills/game-<名前>/SKILL.md` にスキルとして書かせ、コードが中身を確かめてから `.claude/skills/` に写します。`--agent codex` のツールと制限は、「主ループのエージェント」の項にあります。

#### Claude Code が受け取るものと書く JSON

主ループの Claude Code には、毎ターン 1 つの user メッセージでテキストと画像を渡します。変わらない指示 (`--append-system-prompt`) には、JSON の形、コードの手順、マクロ・監視・スキルの使い方、安全のための規則を書いています ([`orchestrator/orchestrator_instructions.py`](./src/switch2_layers/orchestrator/orchestrator_instructions.py))。

| 入力 | 内容 |
|---|---|
| 画面 | 入力を作る時点の `frames/latest/` の最新の 5 枚 (時刻を書き込んだ画像) を、古い順に添えます。5 枚に満たなければ、ある分だけです。画像ごとに、時刻と元の `frames/interval/` のファイル名のラベルを付けます |
| 出来事 | 前の判断の後に監視の条件に当たった回数と、行った操作、監視の終わり、新しい `actions` で捨てた操作の数、押せずに外したボタンです。主ループの操作の残りの数、今の監視とマクロ、写さなかったゲームの内容のスキルとその理由も入れます |
| 前の操作の列 | 前のターンの操作の列を始めた時刻と、終えた時刻 (最後にボタンとスティックを離した時刻。押す操作の無い列なら、列が終わった時刻) です。前のターンに操作が無かったとき (`actions` が空、JSON の誤り、セッションの最初の入力) は書きません |
| 画面の停滞 | `progress/state.json` の値 (「画面の停滞の計測」の節) |
| 前の JSON の誤り | 前のターンの JSON の誤りの説明 |
| フレームの読み方 | `frames/latest/1.jpg`〜`5.jpg` は最新の 5 枚で、`1.jpg` が最新です。いつ Read しても (`--agent codex` では、いつ view_image で開いても)、その時点の最新の画面が読めます。それより古いフレームは `frames/interval/` にあり、ファイル名は時刻のミリ秒 (9 桁) です。変わらない指示にも同じことを書いています |
| 人の初期指示 | セッションの最初の入力だけに入れます。初期指示を渡さなかったときは「無し」と書きます |
| `notes/` の一覧と引き継ぎ | セッションの最初の入力だけに入れます。`notes/` のファイルの一覧と、`notes/handoff.md` の中身です |

JSON の形は次のとおりです ([`orchestrator/decision_parser.py`](./src/switch2_layers/orchestrator/decision_parser.py))。最上位のキーはどれも省けます。

```json
{
  "actions": [
    {"type": "press", "buttons": ["A"]},
    {"type": "press", "buttons": ["B", "LEFT"], "seconds": 0.5},
    {"type": "wait", "seconds": 0.3},
    {"type": "procedure", "name": "walk", "args": {"direction": "UP", "count": 3, "seconds": 0.2, "interval_seconds": 0.1}},
    {"type": "macro", "name": "next_message"}
  ],
  "macros": {"set": {"next_message": [{"type": "press", "buttons": ["A"]}]}, "delete": []},
  "monitor": {"action": "create", "name": "dialog", "cases": [
    {"condition": "画面の下に会話の枠がある", "actions": [{"type": "press", "buttons": ["A"]}], "repeat": "every"}
  ]}
}
```

| キー | 内容 |
|---|---|
| `actions` | 操作の列です。`press` (ボタン・スティック・押す秒数。秒数を省くと短押し)、`wait` (待つ秒数)、`procedure` (コードの手順 `tap_repeat`・`walk`)、`macro` (登録したマクロ) の 4 種類があります。ボタンは HOME を含む 17 個を書けます。空でない `actions` は、そのときに実行中の操作の列 (監視の操作の列など) の残りを捨てて置き換えます。空の `actions` は「何もしない」の意味です |
| `macros` | マクロの登録 (`set`) と削除 (`delete`) です。マクロは実行の間残り、後のターンの `actions` と監視の条件の操作から呼べます |
| `monitor` | 監視を作る (`create`。名前と、条件の文・操作・`every` か `once` の組を 1〜8 個) か、止めます (`stop`) |

コードは、答えの最後の ```` ```json ```` のブロックだけを読みます。ブロックが無い、知らないキーがある、値が範囲の外にある、登録に無いマクロを呼ぶなどの誤りがあると、操作・マクロ・監視のどれも変えず、次の入力に誤りの説明を書きます。

答えの `actions` が空でなければ、主ループは、その操作の列 (マクロとコードの手順を含みます) がすべて終わってから次の入力を作ります。列が終わった後は、最後にボタンとスティックを離した時刻の 0.3 秒後より後に撮った一定間隔のフレームが `frames/latest/` に入るまで待ちます。操作の結果が映った画面で判断させるためです。押す操作の無い列 (`wait` だけの列) では、列が終わった時点で作ります。`actions` が空のとき、JSON に誤りがあったとき、新しいセッションの最初の入力は、待たずにすぐ作ります。待つのは主ループの操作の列だけで、監視の操作は待ちません。待つ時間は、`--turn-timeout` の 1 ターンに含めません。

#### 監視の動き

監視は同時に 1 つだけ動きます。主ループの操作の残りが無く、監視の操作も実行していない間、最新のフレーム 1 枚 (安全の監視と同じく、時刻も box も書き込まない画像) を Jev に送り、どの条件に当たるかを Choice の 1 問で問います。選択肢は、どの条件にも当たらない `NONE` と、条件ごとの `C0`・`C1`… です。要求は 1 つずつ送り、前の要求の応答を受け取ってから次を送ります。最後に操作を離してから 0.3 秒より後に撮ったフレームで問います。

いちばん確率の高い選択肢が `NONE` でなく、その確率が `--monitor-threshold` (既定 0.5) を超えたら、その条件の操作を送ります。`every` の条件は当たるたびに操作を送り、`once` の条件は操作を 1 回送り終えたら監視を終えます。Jev の失敗が `--max-monitor-errors` 回 (既定 5) 続いたら監視を止めます (実行全体は止めません)。当たった回数と監視の終わりは、次の入力の出来事で主ループに知らせます。主ループが新しい `actions` を書くと、実行中の監視の操作を捨てて主ループの操作を始めます。

#### セッションの入れ替え

主ループのセッション (1 つの claude の子プロセス) の使用量が `--rotate-tokens` (既定 120,000) を超えたら、引き継ぎを `notes/handoff.md` に書くよう依頼します。その応答を受け取ったらセッションを終え、新しいセッションを始めます。使用量は、最後の assistant の行の入力のトークン (キャッシュの読み書きを含む) の和です (`--agent codex` では、最後の使用量の通知の `last.inputTokens` です)。新しいセッションの最初の入力には、人の初期指示、`notes/` の一覧、`notes/handoff.md` の中身を入れます。入れ替えの間も、操作の実行と監視は動き続けます。

1 ターンが `--turn-timeout` 秒 (既定 120) を超えたとき、子プロセスが終わったときも、そのセッションを終えて新しいセッションを始めます。新しいセッションが最初のターンを終えずに終わることが 3 回続くと、実行全体を止めます。

主ループの Claude Code は、サブスクリプションのログインで動かします (子プロセスの環境変数から `ANTHROPIC_API_KEY` と `ANTHROPIC_AUTH_TOKEN` を除きます)。そのため、主ループの使用量は、同じアカウントのほかの Claude Code と Claude のアプリ (claude.ai・デスクトップ・モバイル) の利用と、同じ使用量の枠を共有します。Pro と Max のプランでは、5 時間ごとの枠と週ごとの枠です (2026-11-17 に Claude のヘルプセンターで確認)。

#### 人の初期指示とゲームの名前

本書では、どの層にもゲームの名前を渡さない条件で試します (「ソフトの名前とユーザーの名前」の項)。Orchestrator 型では、人の初期指示に限って、起動するソフトの名前 (ゲームの名前) を書いてよいことにしています。変わらない指示と引き継ぎの依頼の文には、ゲームの名前を書いていません。初期指示は、主ループの各セッションの最初の入力に入れ、`orchestrator/instruction.md` にも写して残します。

#### 主ループのエージェント (`--agent`)

主ループは、Claude Code (既定。`--agent claude`) のほかに、OpenAI Codex (`--agent codex`) でも動かせます。監視型と委任型のどちらでも使えます。受け取る入力、書く JSON、操作の実行と監視 (委任型では委任)、記録の形はどちらも同じで、変わるのは主ループのセッションの中身だけです。主ループは [`orchestrator/main_loop_session.py`](./src/switch2_layers/orchestrator/main_loop_session.py) の境界の型だけを通してセッションを使い、Claude Code の実装は `claude_main_loop_session.py`、Codex の実装は `codex_main_loop_session.py` にあります。

```bash
uv run --env-file .env switch2-layers run --mode orchestrator --agent codex --instruction '<ソフトの名前> を <ユーザーの名前> で起動して、冒険を始めてください'
uv run --env-file .env switch2-layers run --mode delegate --agent codex --codex-model gpt-6.2-sol --orchestrator-effort high --instruction-file instruction.md
```

`--agent codex` の前提として、codex CLI を導入し、`codex login` でログインしておきます。Codex はユーザーのログインで動かします (子プロセスの環境変数から `OPENAI_API_KEY`・`TYPESAFE_API_KEY`・`CODEX_API_KEY` を除きます)。そのため、Codex の API キーは確かめません。ログインしているかは起動の前に確かめません。codex CLI が無いときやログインしていないときは、主ループのセッションが最初のターンを終えられないため、3 回続くと `orchestrator session failed 3 times in a row` で止まると考えられます (確認していません)。モデルは `--codex-model` (既定 `gpt-6.2-sol`) で、effort は Claude Code と同じ `--orchestrator-effort` で選びます。gpt-6.2-sol は `low`・`medium`・`high`・`xhigh`・`max` のどれにも対応しています。

Codex の主ループのセッションは、次のように動きます。

- 1 つのセッションは、`codex app-server` の子プロセス 1 つと、その中の ephemeral なスレッド 1 つです (スレッドは `~/.codex` に残りません)。標準入出力で、1 行に 1 つの JSON の JSON-RPC を話します。起動のときに `initialize` と `thread/start` を送り、ターンごとに `turn/start` を送ります。子プロセスを起動した後、`initialize` の応答、Codex 本体の場所の特定、`thread/start` の応答を、合わせて最大 30 秒待ちます
- 変わらない指示は、`thread/start` の `developerInstructions` で渡します。Claude 版の文から、ツールに関わる箇所 (ツールの名前、読み書きできる範囲、スキルの使い方、フレームの開き方) だけを置き換えた文です ([`orchestrator/codex_instructions.py`](./src/switch2_layers/orchestrator/codex_instructions.py))。毎ターンの入力の「古いフレーム」の節も、Read の代わりに view_image と書きます
- 画像は、JPEG を `orchestrator/session-<NNN>/images/turn-<NNNN>-<順番>.jpg` に書いて、ファイルのパスで渡します。画像の前の時刻のラベルは Claude 版と同じです。`orchestrator/` はモデルからは読めませんが、画像は app-server のプロセスがサンドボックスの外で読みます
- 答えの文は、`item/completed` の `agentMessage` の文です。1 ターンに途中の文と最後の文が届くことがあり、最後に届いた文の JSON を読みます。`turn/completed` の状態が `completed` でないとき (`failed`・`interrupted`) と、`turn/start` が誤りを返したときは、Claude 版の `is_error` が true の result と同じく扱います
- 使用量は、`thread/tokenUsage/updated` の `last.inputTokens` (キャッシュを含む、その要求の入力の大きさ) です。サブエージェントのスレッドの通知は読みません。サーバーからの承認の要求は断り、ほかの要求には誤りを返します

#### Orchestrator 型の起動引数

次の引数は Orchestrator 型だけで使います。advisor 型では使わず、指定しても動きは変わりません (advisor 型では `--instruction-file` のファイルも読みません)。ただし、値の範囲は advisor 型でも確かめます (下の段落)。`--monitor-threshold` と `--max-monitor-errors` は監視型だけで使い、委任型では使いません。委任型だけで使う引数は、「委任型の起動引数」の項にあります。

| 引数 | 内容 | 既定値 | 範囲 |
|---|---|---|---|
| `--instruction TEXT` | 人の初期指示。起動するソフトと遊ぶユーザーなどを書きます。`--instruction-file` と一緒には使えません | なし | 空でない文字列 (空か空白だけは誤り) |
| `--instruction-file PATH` | 人の初期指示を書いた UTF-8 のファイル。`--instruction` と一緒には使えません | なし | 読めるファイルで、中身が空か空白だけでないもの |
| `--agent {claude,codex}` | 主ループのエージェント。`claude` は Claude Code、`codex` は OpenAI Codex の `codex app-server` です (「主ループのエージェント」の項) | `claude` | `claude`、`codex` |
| `--codex-model NAME` | `--agent codex` の主ループのモデル。`--agent claude` では使いません | `gpt-6.2-sol` | 空でない文字列 (空か空白だけは誤り) |
| `--orchestrator-effort {low,medium,high,xhigh,max}` | 主ループの effort (Claude Code の `--effort`、Codex のターンの effort) | `medium` | `low`、`medium`、`high`、`xhigh`、`max` |
| `--rotate-tokens N` | 主ループのセッションの使用量がこれを超えたら、引き継ぎを書かせてセッションを入れ替えます | 120000 | 1 以上 1000000 未満の整数 |
| `--turn-timeout S` | 主ループの 1 ターン (入力を作ってから result を受け取るまで) の上限の秒数 | 120 | 0 より大きい有限の値 |
| `--max-decision-errors N` | 主ループの JSON の誤りが続けてこの回数になったら止まります | 3 | 1 以上の整数 |
| `--monitor-threshold P` | 監視の当たりのしきい値 | 0.5 | 0 より大きく 1 より小さい値 |
| `--max-monitor-errors N` | 監視の Jev の失敗がこの回数続いたら、監視を止めます | 5 | 1 以上の整数 |

初期指示は任意です。どちらも渡さなければ、入力の「人の初期指示」に「無し」と書きます。`--instruction` と `--instruction-file` の両方を指定したとき、初期指示が空か空白だけのとき、ファイルが読めないときは、実機に触れずに終了します (終了コード 2)。API キーは環境変数 `TYPESAFE_API_KEY` だけを確かめ、無いときも同じく終了します。監視は常に Jev を使うため、`--safety fake` でも要ります。`OPENAI_API_KEY` は確かめません。6 つの値 (`--orchestrator-effort` から `--max-monitor-errors` まで) と `--codex-model` の範囲は `--mode` と `--agent` に依らず確かめ、範囲外なら advisor 型でも終了コード 2 で終わります。

advisor 型と共通の引数のうち、Orchestrator 型で使うのは `--runs-dir`・`--device-fps`・`--com-port`・`--interval-fps`・`--interval-width`・`--safety`・`--safety-interval`・`--threshold-safety`・`--max-safety-errors`・`--progress-window` です (「run の起動引数」の節)。surface・middle・deep の引数と `--stuck-advice-seconds`・`--system-advice-seconds` は使いません。

#### Orchestrator 型の記録

実行ディレクトリー (「実行ディレクトリー」の節) には、advisor 型と共通のファイルのほかに、次のファイルを書きます。

| ファイル | 内容 |
|---|---|
| `orchestrator/instruction.md` | 渡した人の初期指示の写し。初期指示を渡さなければ作りません |
| `orchestrator/sessions.jsonl` | セッションの開始 (`start`)、終了 (`end`。理由 `rotate`・`timeout`・`exit`・`close`、使用量、終了コード、result を受け取ったターンの数)、自動の要約 (`compact`) を 1 行ずつ書きます |
| `orchestrator/turns.jsonl` | ターンごとに 1 行。送ったテキスト、添えた画像の元の `frames/interval/` のファイル名 (`images`。`frames/latest/` のパスではありません)、前のターンの操作の列が終わるのを待ち始めた時刻 (`t_wait_start`) と待った秒数 (`wait_s`。待たなかったターンは 0)、入力を作った時刻 (`t_sent`)、最後の JSON、誤りの説明、終わり方 (`applied`・`invalid`・`handoff`・`error_result`・`timeout`・`exited`・`stopped`)、使用量を書きます |
| `orchestrator/session-<NNN>/stream.jsonl` | セッションごとの Claude Code の stream-json の出力。deep の `stream.jsonl` と同じ形です。`--agent codex` では、app-server から届いた JSON-RPC の行を同じ形 (`{"elapsed_s", "data"}`) で書き、送った行を `{"elapsed_s", "sent"}` の形で書きます |
| `orchestrator/session-<NNN>/images/` | `--agent codex` だけ。ターンごとに添えた画像の JPEG (`turn-<NNNN>-<順番>.jpg`) です |
| `orchestrator/monitor.jsonl` | 監視が Jev に送った要求ごとに 1 行。監視の名前、フレームの時刻、選択肢ごとの確率、当たって操作を始めた条件 (`hit`)、Jev の応答の `usage`、失敗の説明を書きます |
| `frames/latest/1.jpg`〜`5.jpg` | 一定間隔のフレームの最新の 5 枚。`frames/interval/` に保存するたびに置き換え、`1.jpg` が最新です。左上に時刻を書き込み、幅は `frames/interval/` と同じ (`--interval-width`) です。一時ファイルに書いてから名前を変えて置き換えます。5 枚たまるまでは、ある分だけを置きます |
| `operations.jsonl` | advisor 型と同じファイルです。主ループの操作は `source` が `orchestrator`、監視の操作は `monitor` の行になります |
| `.claude/skills/` | 主ループの Claude Code に読ませるスキル。本体の操作のスキルと、確かめて写したゲームの内容のスキルです |
| `.agents/skills/` | `--agent codex` だけ。主ループの Codex に読ませるスキルで、中身は `.claude/skills/` と同じ規則で写します (`--agent codex` では `.claude/skills/` は作りません) |

`run.jsonl` の `start` の行の `args` には、`mode` と 6 つの値を書きます (委任型の 2 つの値と、主ループのエージェントの 2 つの値 (`agent`・`codex_model`) も、`--mode` に依らず書きます)。主ループのセッションの開始と終了 (`orchestrator_session_start`・`orchestrator_session_end`) と、JSON の誤り (`orchestrator_decision_error`) も `run.jsonl` に書きます。段階の行 (`phase`・`clean_up_end`) は書きません。

#### Orchestrator 型の止まる理由

止まる理由には、advisor 型と同じもの (Ctrl+C の `interrupted`、キャプチャー・ブリッジ・安全の監視の理由。「止まる条件」の節) と、次のものがあります。どの理由でも片付けをせず、すぐに操作を中立に戻して止まります。起動したソフトはそのまま残ります。

| 条件 | `stop` の理由 |
|---|---|
| 主ループの JSON の誤りが `--max-decision-errors` 回続いた | `orchestrator decision invalid <回数> times in a row` |
| 新しいセッションが最初のターンを終えずに終わることが 3 回続いた (claude か codex app-server を起動できない、Codex の初期化かスレッドの開始に失敗した、最初のターンが `--turn-timeout` を超えた、子プロセスが終わったなど) | `orchestrator session failed <回数> times in a row` |
| 主ループのスレッドが想定外の例外で終わった | `orchestrator main loop failed: <例外の説明>` |
| 操作の実行と監視のループのスレッドが想定外の例外で終わった (`orchestrator/monitor.jsonl` に書けないときなど) | `monitor loop failed: <例外の説明>` |

安全の監視は advisor 型と同じく、オンライン・購入・本体の設定の画面で止まり、HOME メニューとユーザー選択の画面では止まりません。

#### 委任型 (`--mode delegate`)

`switch2-layers run --mode delegate` は、Orchestrator 型のもう 1 つの実装です (委任型)。主ループの Claude Code は、ターンベースの場面を操作し、ゲームの中の誘導の文・会話・出来事・助言を、Jev に渡すタスクと注意事項にまとめます。リアルタイムの場面では、意味のある行動 (マクロ) の選択肢とタスク・注意事項を Jev に渡して、操作を委任します。Jev が操作を返すと判断したとき、または主ループが委任を終えたときに、操作権は主ループに戻ります。監視型 (`--mode orchestrator`) と並べて、どちらかを選んで動かします。

動かし方の例は次のとおりです。

```bash
uv run --env-file .env switch2-layers run --mode delegate --instruction '<ソフトの名前> を <ユーザーの名前> で起動して、冒険を始めてください'
uv run --env-file .env switch2-layers run --mode delegate --instruction-file instruction.md --delegate-image-width 640 --safety fake
```

1 つ目は、起動するソフトと遊ぶユーザーを、人の初期指示の文で渡します。2 つ目は、初期指示をファイルから読み、Jev に送る画像の幅を 640 にして、安全の監視をフェイクにします。

起動するものは、監視型と同じ共有の部品 (キャプチャー、フレームの保存、キャプチャーの見張り、コントローラーへの送信、安全の監視、画面の停滞の計測)、主ループ、操作の実行と委任のループです。監視 (画面の条件 → 操作) は使えません。主ループのセッションと入れ替え、本体の操作のスキル、ゲームの内容のスキル、`notes/`、人の初期指示の扱いと、入力の画像と次の入力を作る時点は、監視型と同じです。主ループが押せるボタンも、監視型と同じ HOME を含む 17 個です。

| 部品 | 受け持ち |
|---|---|
| 主ループ (`orchestrator/main_loop.py`) | 監視型と同じです。変わらない指示は委任型の版 ([`orchestrator/orchestrator_instructions.py`](./src/switch2_layers/orchestrator/orchestrator_instructions.py) の `delegate_instructions`) を渡し、JSON の `delegate` を読みます |
| 操作の実行と委任のループ (`orchestrator/orchestrator_controller.py`・[`orchestrator/delegate_loop.py`](./src/switch2_layers/orchestrator/delegate_loop.py)) | JSON の操作の列を 1 つずつコントローラーに送り、マクロと委任を持ちます。委任中は、Jev に意味のある行動を選ばせ、選んだ行動のマクロを送ります |

#### 委任型の JSON の `delegate`

最上位のキーは `actions` (主ループの操作の列)・`macros`・`delegate` で、どれも省けます。`monitor` を書くと誤りです。操作とマクロの書き方は、監視型と同じです。Jev に選ばせる意味のある行動は、最上位の `actions` と区別するため、`delegate` の `choices` に書きます。

```json
{
  "actions": [{"type": "press", "buttons": ["A"]}],
  "macros": {"set": {
    "attack": [{"type": "press", "buttons": ["B"]}],
    "evade": [{"type": "press", "buttons": ["LEFT"], "seconds": 0.3}],
    "approach_and_attack": [{"type": "press", "buttons": ["RIGHT"], "seconds": 0.3}, {"type": "press", "buttons": ["B"]}]
  }},
  "delegate": {"action": "start",
    "tasks": ["最重要: 自分の HP を 0 にせずに、敵をすべて倒す", "敵の攻撃は、可能ならよける"],
    "cautions": ["敵は攻撃の前に一瞬止まり、その後にまっすぐ進む弾を撃つ"],
    "choices": [
      {"name": "attack", "description": "敵が目の前にいるときに、敵を攻撃する"},
      {"name": "evade", "description": "敵の攻撃が自分に向かってくるときに、後ろに下がってよける"},
      {"name": "approach_and_attack", "description": "敵が離れているときに、敵に近づいてから攻撃する"}
    ]}
}
```

`delegate` は次の 3 つの形をとります。

| 形 | 内容 |
|---|---|
| `{"action": "start", "tasks": [...], "cautions": [...], "choices": [{"name": <マクロの名前>, "description": <意味のある行動の説明>}, ...]}` | 委任を始めます。同じ JSON の最上位の `actions` がすべて終わってから始めます (`actions` が空なら、すぐに始めます)。`tasks`・`cautions`・`choices` を省くと、前の委任の値を使います。前の委任が無いのに省くと誤りです。委任中に書くと誤りです (委任中の変更は `update` で行います) |
| `{"action": "update", ...}` | 委任中に、タスク・注意事項・行動を置き換えます。省いたキーは変えません。実行中の行動は止めません |
| `{"action": "stop"}` | 委任を終え、操作権を主ループに戻します |

委任中でも、委任を始める前 (`start` と同じ JSON の最上位の `actions` が終わるのを待っている間) でもないときの `update`・`stop` は、誤りにせず、`delegate` だけを当てません。同じ JSON の `actions`・`macros` は当て、次の入力の出来事に「委任はすでに終わっていたため、delegate の stop を当てなかった」(`update` なら「delegate の update を当てなかった」) と書きます。主ループが考えている間に Jev が操作権を返したときに、1 ターンを失わないためです。`update`・`stop` の値の規則は、委任中かに依らず確かめます。

値の規則は次のとおりです。どれかに反すると、ほかの JSON の誤りと同じく、操作・マクロ・委任のどれも変えずに、次の入力に誤りの説明を書きます。

- `choices` は 1〜12 個で、`name` は登録済みのマクロの名前 (同じ JSON の `macros` を当てた後の登録)、`description` は空でない文です。同じ `name` を 2 回書けません。HOME を押すマクロ (手順を展開した操作の列に、HOME を押す `press` があるもの) は使えません。`none` と `return_control` は Jev の選択肢の名前に使うため、行動の名前にできません
- `tasks` は 1〜10 個、`cautions` は 0〜10 個の、空でない文です
- 委任中 (委任を始める前を含みます) は、`choices` に使っているマクロを、`macros` の `delete` で消せません。`macros` の `set` で HOME を押す操作の列に置き換えることもできません。どちらも、`delegate` を書かない JSON でも誤りです。行動に使っていないマクロは、HOME を押す列でも登録できます

主ループへの変わらない指示 (委任型の版) には、次のことを書いています。

- `tasks` の最初に、その場面で最も重要なこと (例: 自分の HP を 0 にせずに、敵をすべて倒す) を書く
- 敵の攻撃を避けることが要る場面では、そのことを `tasks` に書く
- 敵の攻撃の動きを観測できたら、`cautions` に書く
- タスク・注意事項・行動の説明に、ゲーム名や作品に固有の名前 (登場人物・地名など) を書かない
- 行動は、ボタンの名前ではなく、意図 (近づく・離れる・よける・攻撃するなど) が分かる名前と説明にし、説明にはその行動を選ぶ場面も書く
- Jev は攻撃の行動を選びやすく、移動だけの行動を選びにくいことがあるため、位置を変える行動は、移動と攻撃を 1 つにしたマクロにもできる
- 時間が進む戦いの場面 (自分が操作しなくても敵が動き、攻撃してくる場面) では、自分で操作せず、必ず委任する。時間の止まる画面 (会話・メニュー・選ぶ画面など) は自分で操作する
- 委任中に `tasks`・`cautions`・`choices` を直すときは `update` を使う。`{"action": "stop"}` は、戦いの場面が終わったのに Jev が操作を返さないときだけ使う。戦いの場面が続いているのに操作が戻ったら、値を直してすぐに `start` する
- 委任が終わるたびに、委任中の画面の変化 (自分の体力・倒した敵など) と、次の入力の出来事に載る「この委任で Jev が選んだ回数」を見て、うまくいかなかった点を振り返り、次の委任の `choices`・`tasks`・`cautions` を直す。振り返りの結果は `notes/` に書き、うまくいかなかったことを委任をやめる理由にしない
- 委任中は、最上位の `actions` が捨てられる。取り返すときは `{"action": "stop"}` を書く (戦いの場面が終わったのに Jev が操作を返さないときだけ)

#### 委任中の主ループ

委任中も、主ループのターンは監視型と同じ規則で続けます。委任中の JSON の最上位の `actions` は捨て、次の入力の出来事に「委任中のため、操作を捨てた: <個数> 個」と書きます。主ループの操作が無いため、前のターンの直後に次のターンを始めます。同じ JSON の `delegate` の `update`・`stop` と `macros` は当てます。

入力のテキストには、監視型の「今の監視」の節の代わりに「委任」の節を置き、委任の状況を書きます。委任中でなければ、タスク・注意事項・行動は前の委任の値 (`start` で省いたキーに使う値) です。

| 項目 | 内容 |
|---|---|
| 委任中 | `はい` か `いいえ` (委任を始める前も `はい`) |
| 委任を始めた時刻 | 委任を始めた時刻。委任中でないときと、まだ始めていないときは「無し」 |
| タスク・注意事項・行動 | 今のタスク・注意事項・行動 (JSON の配列) |
| Jev が直近に選んだ行動 | 行動の名前と、その行動を始めた時刻 |
| Jev が「操作を返す」を続けて選んだ回数 | 回数 |

操作権が主ループに戻ったときは、次の入力の出来事に、戻った理由 (`jev_return`・`main_stop`・`errors`) と説明を書き、その次の行に、その委任で Jev が選んだ回数を次の形で書きます。

```text
この委任で Jev が選んだ回数 (要求 30 回、失敗 1 回): none 17、attack 7、evade 0、approach_and_attack 3、return_control 2
```

回数は、その委任 (始めてから終わるまで) で、Jev の答えで処理を決めた要求を、選んだ選択肢ごとに数えたものです。1 回目の `return_control` (実行中の行動を続けるとき) も数えます。応答を使わなかった要求 (`delegate.jsonl` の `handling` が `ignored`) は数えません。失敗した要求は、選択肢の回数に入れずに、失敗の回数に数えます。要求の回数は、選択肢の回数の和と失敗の回数の和です。並びは、委任が終わった時点の選択肢の順 (`none`、行動を書いた順、`return_control`) で、0 回の選択肢も書きます。`update` で行動を置き換えたために、終わった時点の選択肢に無いが選ばれていた行動は、その後ろに、最初に選ばれた順で書きます。

#### 委任のループの動き

委任を始めたら、Jev への要求を 1 つずつ送ります。委任を始めた後の最初の要求はすぐに送り、その後は、前の要求の応答 (または失敗) を受け取った時刻から 0.2 秒たったら、次の要求を送ります。主ループの操作や、Jev が選んだ行動を実行している間も送ります。

要求の state には、役割の説明、`tasks`、`cautions`、今の委任で直近に選んで始めた行動 (最大 5 件。行動の名前と始めた時刻)、最新の 5 枚の画像を入れます。画像は、一定間隔のフレーム (`--interval-fps`) の直近 5 枚と同じ時刻のフレームを、元のフレームから幅 `--delegate-image-width` で作ります。時刻や枠は書き込まず、古い順に並べて、時刻のラベルを付けます。元のフレームは直近の 3 秒分だけを持つため、`--interval-fps` を下げて 5 枚が 3 秒より前にさかのぼると、残っている分だけを送ります。

問いは Choice の 1 問で、選択肢は `none` (何もしない)、主ループが書いた行動 (書いた順。選択肢の名前はマクロの名前)、`return_control` (操作を返す) の順です。Jev は先頭の選択肢に寄ることがあるため、先頭を何もしない `none` にしています。答えは、確率がいちばん高い選択肢 (同じ確率なら先の選択肢) で決めます。ただし、いちばん高いのが `none` で、その確率が 0.5 より小さいときは、行動 (`none` と `return_control` 以外) のうち確率がいちばん高いもの (同じ確率なら先の行動) を選びます。行動の確率は行動の数だけ分かれ、何もしない側は `none` の 1 つに集まるため、いちばん高い 1 つだけで決めると、行動の確率の和が大きくても `none` が選ばれ、何もしない時間が続くためです。このときに `return_control` は選びません。

| 選んだ選択肢 | 動き |
|---|---|
| 行動 | 実行中の行動の残りを捨て、そのマクロを始めます |
| `none` | 実行中の行動を続けます |
| `return_control` | 2 回続けて選んだら、操作権を主ループに返します。1 回目は `none` と同じく、実行中の行動を続けます。ほかの選択肢を選んだら、数え直します |

Jev の失敗 (HTTP のエラー、形の違う応答など) が `--max-delegate-errors` 回 (既定 5) 続いたら、操作権を主ループに返します。実行は続けます。答えがあれば、失敗の回数は 0 に戻ります。操作権を返すとき (Jev が返す、主ループの `stop`、失敗が続いた) は、実行中の行動を捨てて操作を中立にします。要求を送った後に委任を終えたときと、`update` で値を置き換えたときは、その要求の応答を使いません。委任中も安全の監視は動き、止める画面なら実行全体を止めます。

#### 委任型の起動引数

次の 2 つの引数は、委任型だけで使います。値の範囲は `--mode` に依らず確かめ、範囲外なら advisor 型と監視型でも、実機に触れずに終了します (終了コード 2)。

| 引数 | 内容 | 既定値 | 範囲 |
|---|---|---|---|
| `--delegate-image-width N` | 委任のループが Jev に送る画像の幅。下限は、Jev が受け付ける画像の各辺の下限 280 ピクセルを、16:9 の高さで満たす幅です | 1280 | 498〜1280 の整数 |
| `--max-delegate-errors N` | 委任のループの Jev の失敗がこの回数続いたら、操作権を主ループに返します | 5 | 1 以上の整数 |

`--instruction`・`--instruction-file`・`--agent`・`--codex-model`・`--orchestrator-effort`・`--rotate-tokens`・`--turn-timeout`・`--max-decision-errors` と、advisor 型と共通の引数の使い方は、監視型と同じです (「Orchestrator 型の起動引数」の項)。監視型だけで使う `--monitor-threshold`・`--max-monitor-errors` は使いません。API キーは環境変数 `TYPESAFE_API_KEY` だけを確かめます。委任に Jev を使うため、`--safety fake` でも要ります。

#### 委任型の記録

監視型の記録 (「Orchestrator 型の記録」の項) のうち、`orchestrator/monitor.jsonl` は書かず、次の記録を書きます。

| ファイル | 内容 |
|---|---|
| `orchestrator/delegate.jsonl` | 委任のループが Jev に送った要求ごとに 1 行。送った時刻と受け取った時刻 (`t_sent`・`t_received`)、送った画像の時刻 (`frame_ts`。古い順)、選択肢ごとの確率 (`probabilities`)、選んだ選択肢 (`chosen`)、そのとき行った処理 (`handling`)、Jev の応答の `usage`、失敗の説明 (`error`) を書きます。`handling` は、行動を始めた `started`、続けた `continued`、操作権を返した `returned`、応答を使わなかった `ignored` です。`chosen` は、その要求で送った選択肢の名前から決めます。失敗した要求では、`probabilities`・`chosen`・`usage` を null にします |
| `run.jsonl` | 委任の始まり (`delegate_start`。`tasks`・`cautions`・`choices`) と終わり (`delegate_end`。`reason`・`detail`・`chosen_counts`・`failures`) の行を書きます。`reason` は、Jev が操作を返した `jev_return`、主ループの `stop` の `main_stop`、Jev の失敗が続いた `errors`、実行全体を止めた `stop` です。`chosen_counts` は、その委任で Jev が選んだ回数 (選択肢の名前 → 回数。数え方と並びは「委任中の主ループ」の項の出来事の行と同じ)、`failures` は、その委任で失敗した要求の数です。`reason` が `stop` の行にも書きます。`start` の行の `args` には、`mode` と 2 つの値 (`delegate_image_width`・`max_delegate_errors`) も書きます |
| `operations.jsonl` | Jev が選んだ行動の操作は、`source` が `delegate` の行になります。主ループの操作は、監視型と同じく `orchestrator` です |

#### 委任型の止まる理由

止まる理由は、監視型と同じです (「Orchestrator 型の止まる理由」の項)。ただし、監視のループの代わりに委任のループが動くため、`monitor loop failed` の代わりに次の理由があります。Jev の失敗が続いたときは、操作権を主ループに返すだけで、実行全体は止めません。

| 条件 | `stop` の理由 |
|---|---|
| 委任のループのスレッドが想定外の例外で終わった (`orchestrator/delegate.jsonl` に書けないときなど) | `delegate loop failed: <例外の説明>` |

#### 委任型の事前検証

実装の前に、保存済みのバトルのフレーム (幅 640、各場面の直近 5 枚) で、Jev に意味のある行動を選ばせる検証を行いました (2026-11-17、22 場面)。

- 操作を返すべき画面 (会話・選ぶ画面・結果の表示) で「操作を返す」を選んだのは 6/6、ゲージが満タンのときに「選び直す画面を開く」を選んだのは 3/3 でした。「リアルタイムの戦いの画面か」を Noul で問うと 15/15 でした
- 衝撃波を避ける場面は 0/7 でした。タスクに「最重要: HP を 0 にせずに敵をすべて倒す」「敵の攻撃は、可能なら避ける」、注意事項に衝撃波の動きを書くと 2/7 になりましたが、上下の移動の確率の和は、衝撃波が来ている場面で平均 0.24、来ていない場面で 0.22 と差がありませんでした
- リアルタイムの戦いの画面では、「前へ 1 マス」に寄りました
- 幅 1280 の画像で位置の判断が変わるかは、確かめていません

敵の攻撃を避けるなどの位置の判断を Jev に任せられるかは、未検証です。

### run の起動引数

`switch2-layers run` は、`switch2-agent` と同じく第2章の環境を使い、キャプチャーとコントローラーのブリッジを自分で起動します。用意するものと、第2章のデーモンなどを終了しておくことは、`switch2-agent` の「必要なもの」の節と同じです。ただし、Pico 2 W の 1P への登録は、advisor 型では run が準備の段階で行います。Orchestrator 型では、コントローラーの持ちかたと順番を変える画面が出たときに、主ループが本体の操作のスキル (`switch-controller-order`) でコントローラーを認識させます。キャプチャーのフレームレートのうち、ffmpeg.exe の出力 (30 fps) と間引いた後 (10 fps) は起動引数にせず固定しています。デバイスから受け取るフレームレートだけは `--device-fps` で選べます。

| 引数 | 内容 | 既定値 | 範囲 |
|---|---|---|---|
| `--mode {advisor,orchestrator,delegate}` | run の型。`advisor` は surface・middle・deep の 3 層、`orchestrator` は主ループ (`--agent` で Claude Code か Codex を選ぶ) と、操作の実行と監視、`delegate` は主ループと、操作の実行と委任のループを動かします (「Orchestrator 型」の節) | `advisor` | `advisor`、`orchestrator`、`delegate` |
| `--software NAME` | 起動するソフトの名前 (advisor 型では必須。Orchestrator 型では使いません)。HOME メニューでソフトの絵の上に出る名前を書きます。本体の画面の middle の入力に入れます | なし | 空でない文字列 (空か空白だけは誤り) |
| `--user NAME` | ソフトを遊ぶユーザーの名前 (advisor 型では必須。Orchestrator 型では使いません)。ユーザー選択に出る名前を書きます。本体の画面の middle の入力に入れます | なし | 空でない文字列 (空か空白だけは誤り) |
| `--runs-dir DIR` | 実行ディレクトリーを作る親 | `runs` | なし |
| `--device-fps N` | デバイスから受け取るフレームレート。PC との USB の接続で 60 fps を受け取れないときは 30 にします (第2章の README の既知の問題を参照) | 60 | 30 か 60 |
| `--com-port PORT` | ブリッジが開く COM ポート。Pico 2 W の Bluetooth の発信側の COM ポートを指定します (第2章の README の「2. Windows とのペアリング」を参照)。ブリッジを復旧で起動し直すときも同じ COM ポートを開きます | `COM3` | `COM1`、`COM2` のように `COM` と 1 以上の整数 (先頭に 0 を付けた `COM04` などは誤り。大文字と小文字は区別しません) |
| `--interval-fps N` | 一定間隔のフレームを `frames/interval/` に保存するフレームレート | 5 | 0 より大きく 10 以下 |
| `--interval-width N` | 一定間隔のフレームを縮小する幅 | 640 | 64〜1280 の整数 |
| `--max-surface-errors N` | surface の失敗がこの回数続いたら止まります | 5 | 1 以上の整数 |
| `--middle-interval S` | middle の前回の応答から次を始めるまでの秒数。きっかけ (「middle の実装」の節の「middle を呼ぶきっかけ」) があれば、この秒数を待たずに始めます。失敗した回の後は、この秒数たつまで始めません | 5 | 1〜10 |
| `--middle-window S` | middle に渡す一定間隔のフレームの範囲 (直近の秒数) | 10 | 0 より大きい有限の値 |
| `--max-middle-errors N` | middle の失敗がこの回数続いたら止まります | 5 | 1 以上の整数 |
| `--deep-min-start-interval S` | 同じ文書の deep を、前回の起動からこの秒数たつまで、起動も保留もしません | 30 | 0 以上の有限の値 |
| `--deep-auto-seconds S` | 同じ文書の前回の deep の終了からこの秒数たったら、自動で deep を呼びます | 60 | 0 より大きい有限の値で、`--deep-min-start-interval` 以上 |
| `--deep-timeout S` | deep のジョブの実行時間の上限 (秒) | 300 | 0 より大きい有限の値 |
| `--middle {fake,luna}` | middle の実装 (「middle の実装」の節)。`luna` は gpt-6-luna を呼び、環境変数 `OPENAI_API_KEY` が要ります | `luna` | `fake`、`luna` |
| `--middle-effort {none,low}` | ゲーム用の middle の reasoning effort (「middle の実装」の節)。本体の画面の middle には使いません。`--middle fake` でも使いません | `none` | `none`、`low` |
| `--surface {jev,fake}` | surface の実装 (「surface の実装」の節)。`jev` は TypeSafe の Jev を呼び、環境変数 `TYPESAFE_API_KEY` が要ります | `jev` | `jev`、`fake` |
| `--threshold-advisor P` | surface の advisor 判定のしきい値。確率がこれを超えた文書の deep を求めます | 0.5 | 0〜1 |
| `--box-requery-every N` | 追えている box も、前回の問い直しからこの回数の要求がたったら Jev に問い直します | 5 | 1 以上の整数 |
| `--hold-margin P` | surface のボタンと十字キーで、`hold` の確率が `tap` の確率をこの値より大きく上回ったときだけ押し続けにします (「surface の実装」の節)。0 なら `hold` の方が高いときに押し続け、1 なら常に短押しです | 0.1 | 0〜1 |
| `--surface-map {text,none}` | surface に現在地の場所のマップを渡すか (「surface の実装」の節の state の `map`)。`text` は文字で渡し、`none` は渡しません (`map` を空文字列にします)。`--surface fake` では使いません | `text` | `text`、`none` |
| `--deep {claude,fake}` | deep のジョブを実行するもの (「deep の実装」の節)。`claude` は Claude Code を起動します | `claude` | `claude`、`fake` |
| `--safety {jev,fake}` | 安全の監視の実装 (「安全のための規則と安全の監視」の節)。`jev` は TypeSafe の Jev を呼び、環境変数 `TYPESAFE_API_KEY` が要ります | `jev` | `jev`、`fake` |
| `--safety-interval S` | 安全の監視が最新のフレームを確かめる間隔 (秒) | 1.0 | 0.2 以上 10 以下 |
| `--threshold-safety P` | 安全の問い (`online`・`purchase`・`system_settings`) のしきい値。確率がこれを超えた画面で止まります。照合 (`system_screen`) のしきい値には使いません | 0.7 | 0 より大きく 1 より小さい値 |
| `--max-safety-errors N` | 安全の監視の失敗がこの回数続いたら止まります | 3 | 1 以上の整数 |
| `--progress-window S` | 画面の停滞の計測で、新しい画面かを決めるときに見る範囲 (直近の秒数。「画面の停滞の計測」の節) | 300 | 0 より大きい有限の値 |
| `--stuck-advice-seconds S` | 新しい画面が出ていない秒数がこれを超えたら、助言の deep を求めます。超えたまま続く間は、この秒数ごとに求めます | 60 | 0 より大きい有限の値 |
| `--threshold-task P` | surface の先頭のタスクの 2 つの問い (`task_done`・`task_cancel`) のしきい値。確率がこれを超えた要求が、同じタスクについて続けて 2 回あったら成立にします (「surface の実装」の節) | 0.5 | 0〜1 |
| `--task-stuck-seconds S` | 現在の場面の最も古いタスクの続いた秒数がこれを超えたら、間隔を待たずに middle を呼びます (きっかけ `stuck`)。超えたまま続く間は、この秒数ごとに呼びます | 30 | 0 より大きい有限の値 |
| `--system-advice-seconds S` | 準備・復帰の段階がこの秒数を超えて続いたら、助言の deep をきっかけ `system` で求めます。超えたまま続く間は、この秒数ごとに求めます (「本体の画面の扱い」の節の「本体の画面の助言」の項) | 90 | 0 より大きい有限の値 |

Orchestrator 型だけで使う引数 (`--instruction`・`--instruction-file`・`--agent`・`--codex-model`・`--orchestrator-effort`・`--rotate-tokens`・`--turn-timeout`・`--max-decision-errors`・`--monitor-threshold`・`--max-monitor-errors`) は、「Orchestrator 型」の節の「Orchestrator 型の起動引数」の項にあります。委任型だけで使う引数 (`--delegate-image-width`・`--max-delegate-errors`) は、同じ節の「委任型の起動引数」の項にあります。

範囲外の値では、実機に触れずにエラーを表示して終了します (終了コード 2)。advisor 型で `--software` か `--user` が無いときと、値が空か空白だけのときも、引数の誤りとして使い方を表示し、実機に触れずに終了します (終了コード 2)。2 つの名前は、書かれたまま本体の画面の middle の入力に入れ、`run.jsonl` の `start` の行の `args` (`software_name`・`user_name`) にも書きます。Orchestrator 型で 2 つの名前を渡さなかったときは、`args` に空文字列を書きます。advisor 型で、`--middle luna` で環境変数 `OPENAI_API_KEY` が無いとき、`--surface jev` か `--safety jev` で環境変数 `TYPESAFE_API_KEY` が無いときも、範囲の確かめの後に、実機に触れず、実行ディレクトリーも作らずに終了します (終了コード 2)。`--surface jev` と `--safety jev` の両方でキーが無いときは、両方のメッセージを表示します。`--deep-auto-seconds` が `--deep-min-start-interval` より短いと、自動の呼び出しが最小の間隔で捨てられ続けるため、エラーにしています。

同じ文書 (種類と場面の組) の deep のジョブは、同時に 1 件までです。同じ文書への要求は、きっかけ (`surface`・`new_scene`・`auto`・`progress`・`system`) に依らず、次の順に確かめて扱います。

1. 終了処理の後なら捨てます
2. 前回の起動から `--deep-min-start-interval` 秒たっていなければ捨てます。実行中のジョブがあるかどうかより先に確かめます
3. 実行中のジョブがあれば (停止を求めて終わるのを待っているジョブを含みます)、要求を 1 件だけ保留します。保留中の要求があれば、古い要求を捨てて、新しい要求を保留します
4. どれにも当たらなければ起動します

保留中の要求は、実行中のジョブが終わったとき (ジョブが戻ったとき、強制終了したとき、ジョブのスレッドを起動できなかったとき) に、すぐ起動します。起動したジョブのきっかけと要求の時刻は、保留した要求のものです。前回と今回の最新のフレームの時刻は、起動するときに求めます (終わったばかりのジョブが正常に終わっていれば、その最新のフレームの時刻が前回の時刻になります)。保留した要求は、前回の起動から `--deep-min-start-interval` 秒たった後に来たものなので、起動するときに最小の起動間隔を確かめ直しません。前回の起動の時刻は、保留から起動した時刻になります。保留中の要求があるときは、ジョブの終わりの記録と保留からの起動の用意を、ほかの要求を挟まずに続けて行います。そのため、ジョブが終わるときに来た要求は、保留から起動したジョブが実行中のときの要求として扱います。

保留からの起動で、ジョブのディレクトリーを用意できなかったときは、前回の終了をエラーにし、`run.jsonl` に `deep_request_error` (`source` は `pending`) を書きます。ジョブのスレッドを起動できなかったときは、`deep_end` (`status` は `error`) を書きます。どちらの失敗でも例外を外に出さず、surface と middle はそのまま動き続けます。終了処理では、保留中の要求を捨てます。その後に実行中のジョブが終わっても、保留から起動しません。自動の呼び出しは、実行中の文書を対象にしないため、保留を作りません。起動から `--deep-timeout` 秒たったジョブには停止を求め、5 秒たっても終わらなければ強制終了します。

`run.jsonl` には、deep について次の行を書きます。

| `event` | 書くとき | 項目 |
|---|---|---|
| `deep_start` | ジョブを起動した | `kind`・`scene_id`・`trigger`・`job` (ジョブのディレクトリー)・`pending_t` (保留した要求の時刻。保留を経ずに起動したジョブでは null) |
| `deep_pending` | 実行中のジョブがあるため、要求を保留した | `kind`・`scene_id`・`trigger`・`since_last_start_s` (前回の起動からの秒数。ミリ秒に丸めます) |
| `deep_skipped` | 要求を捨てた | `kind`・`scene_id`・`trigger`・`reason`。`reason` は、最小の起動間隔の中なら `min_start_interval` (`since_last_start_s` も書きます)、保留中の要求を新しい要求で置き換えたなら `replaced` (`trigger` は古い要求のきっかけ)、終了処理の後に来た要求か、終了処理で捨てた保留中の要求なら `closed` です |
| `deep_stop` | ジョブに停止を求めた | `kind`・`scene_id`・`trigger`・`job`・`reason` (`timeout` か `close`) |
| `deep_end` | ジョブが終わった (強制終了とスレッドを起動できなかったときを含みます) | `kind`・`scene_id`・`trigger`・`job`・`status`・`message`・`stop_reason` (止めた理由。止めていなければ null) |
| `deep_request_error` | deep を求めたときに失敗した | `source`・`kind`・`trigger`・`scene_id`・`error`。`source` は、要求した側 (`surface`・`middle`・`auto`・`progress`・`system`) か、保留中の要求を起動するときにジョブのディレクトリーを用意できなかったときの `pending` です |

### 実行ディレクトリー

run は、実行ごとに `runs/<YYYYmmdd-HHMMSS>/` を作ります (同じ名前があれば、末尾に `-2` などを付けます)。中に次のファイルを書きます。時刻は、実行を始めてからの経過秒 (t) を小数第 3 位 (ミリ秒) までに丸めた値です。

| ファイル | 内容 |
|---|---|
| `run.jsonl` | 起動 (`start`。起動引数を `args` に含みます。`args` には `--software` と `--user` の名前 (`software_name`・`user_name`) も入ります。`args` の `deep` は、deep を Claude Code (`claude`) とフェイク (`fake`) のどちらで動かしたかです。`args` の `mode` は run の型 (`advisor`・`orchestrator`・`delegate` のどれか) で、Orchestrator 型の 6 つの値と委任型の 2 つの値と主ループのエージェントの 2 つの値 (`agent` は `claude` か `codex`、`codex_model` はそのモデル) も `--mode` に依らず入ります)、段階の変化 (`phase`) と片付けの終わり (`clean_up_end`。「本体の画面の扱い」の節。advisor 型だけ)、Orchestrator 型の主ループのセッションの開始・終了と JSON の誤り (「Orchestrator 型」の節)、委任型の委任の始まりと終わり (`delegate_start`・`delegate_end`。「Orchestrator 型」の節の「委任型の記録」の項)、surface と middle の失敗、deep のジョブの開始・停止の要求・終了・保留した要求・捨てた要求と deep を求めたときの失敗 (「run の起動引数」の節の表)、保存を捨てた画像の件数 (`frames_dropped`)、停止 (`stop`。止まった理由を含む) を、1 行 1 件の JSON で書きます。`stop` の行の後には何も書きません |
| `surface.jsonl` | surface の要求ごとの記録。送った画像の時刻とファイル名、読んだ文書の場面、その要求の先頭のタスクの ID (`task_id`。先頭のタスクが無ければ null。失敗の行にも書きます)、state の `map` に入れたマップの場所の `name` (`map_place`。マップを渡さなかった行、`--surface fake` の行、失敗の行では null)、送った操作、ボタンの制限で外したボタン (`blocked_buttons`)、deep を求めた文書の種類、情報ラベル (`info_labels`)、最新のフレームの box (`boxes`。対象の名前・座標・確信度・出どころ `jev` か `tracker`)、場面転換、待ち時間、失敗の説明を書きます。さらに、要求の番号 (`request`。1 から数え、`surface_requests.jsonl` の `request` と同じ値)、要求したすべての Choice と Noul の問いの確率 (`answers`。`choices` に問いごとの選択肢の確率を、`nouls` に問いごとの確率を入れます。Box の問いの答えは `boxes` に書きます)、Jev の応答の `usage` (受け取った形のまま) を書きます。`request` は、Jev を呼ばない `--surface fake` の行と、要求を送る前に失敗した行では null です。`answers` と `usage` は、`--surface fake` の行と、応答を読めなかった行 (失敗の行) では null です。`usage` は、応答に無いときも null です |
| `surface_requests.jsonl` | surface が Jev に送った要求の記録。Jev に送る直前に 1 行ずつ足します。要求の番号 (`request`)、送った時刻 (`t_sent`)、モデル名 (`model`)、送った state (`state`。画像は、その画像を保存した `frames/surface/` のファイル名 (`surface.jsonl` の `frames` の `file` と同じ値) に置き換え、保存できなかった画像は null にします)、送った問いの一覧 (`questions`。問いごとに ID・型・問いの文と、Choice の問いでは選択肢の名前と説明 (`criteria`)) を書きます。送った後に失敗した要求 (HTTP のエラー、応答を読めない、答えが足りない) の行も残ります。API キーと HTTP のヘッダーは書きません。`--surface fake` では何も書きません。1 時間に約 3,000 要求を送ると数十 MB になる見込みですが、切り詰めや間引きはしません |
| `safety.jsonl` | 安全の監視の確かめごとの記録 (「安全のための規則と安全の監視」の節)。送った時刻と受け取った時刻 (`t_sent`・`t_received`)、確かめたフレームの時刻 (`frame_t`)、確かめの種類 (`phase`。`start` か `monitor`)、3 つの問いの名前ごとの確率 (`probabilities`)、照合の選択肢ごとの確率 (`system_screen`)、照合の結果の見本の名前 (`system_screen_result`。照合の結果なしなら null)、Jev の応答の `usage`、失敗の説明 (`error`) を、1 行 1 回の JSON で書きます。失敗した行では `probabilities`・`system_screen`・`system_screen_result`・`usage` を null にします |
| `operations.jsonl` | コントローラーに操作を送ろうとした記録。きっかけ (`apply`・`system`・`orchestrator`・`monitor`・`delegate`・`neutral`・`stop`。`apply` は surface の操作、`system` は本体の画面の操作と `press_home` の HOME、`orchestrator` と `monitor` は Orchestrator 型の主ループと監視の操作、`delegate` は委任型の Jev が選んだ行動の操作)、操作 (押し続けるボタン `held`、押し続けの秒数 `hold_seconds`、短押し `taps`、スティック `sticks`)、成否を書きます |
| `tasks.jsonl` | 短期のタスクのキューの出来事の記録 (「middle の実装」の節の「短期のタスクのキュー」)。キューの部品が、出来事ごとに 1 行 `{"t", "event", "scene_id", "id", "text", "reason", "active_s", "destination"}` を追記します。`event` は `added` (足した)・`dropped` (足せなかった)・`done` (完了)・`cancel_requested` (取り消しの要求)・`canceled` (取り消し) です。`id` はタスクの ID (`dropped` では null)、`text` は整えた後の文、`reason` は `dropped` の理由 (`empty`・`duplicate`・`limit`。ほかでは null)、`active_s` は `done`・`cancel_requested`・`canceled` のときの続いた秒数 (ほかでは null)、`destination` は `added` のときの行き先 (`tasks.json` と同じ形。ほかでは null) です。middle は、前回読んだ位置より後の行を次の入力に使います |
| `frames.jsonl` | 保存した画像の一覧。時刻、種類 (`interval`・`surface`)、ファイル名、幅と高さを、画像を書き終えた後に 1 行ずつ足します |
| `frames/interval/` | 一定間隔で保存した画像 (JPEG)。ファイル名は、時刻をミリ秒にした 9 桁の数です (例: `000012345.jpg`) |
| `frames/surface/` | surface に送った画像 (JPEG。左上に時刻を、追えている対象の枠と名前を書き込んだもの)。時刻と、書き込んだ box の内容 (対象の名前・枠の色の番号・座標) の組ごとに 1 回だけ保存します。ファイル名は、その時刻で最初に保存した画像は `frames/interval/` と同じ 9 桁の数で、同じ時刻で書き込んだ box が違う 2 つ目以降は末尾に `-2`・`-3` … を付けます (例: `000012345-2.jpg`) |
| `middle/state.json` | middle の最新の出力 (場面、詰まっているか、surface の待ち時間、系列情報、次に読む記録 (`surface.jsonl`・`operations.jsonl`・`tasks.jsonl`) の位置、現在地の場所とマス、HOME を押して本体の画面に出るか `press_home`)。surface は要求ごとにこのファイルを読みます |
| `middle/calls.jsonl` | middle の実行ごとの記録。呼ばれた理由 (`reasons`)、足すタスクと取り消すタスク、行き先を直した内容、取り消しと追加を行ったか (「middle の実装」の節の「短期のタスクのキュー」)、`press_home` も書きます。その回に gpt-6-luna に送った要求の番号 (`request`) も書きます。`request` と `t_sent` は、同じ回の `middle/requests.jsonl` の行と同じ値です。`request` は、`--middle fake` の行と、入力を作れずに失敗した行では null です。`--middle luna` では、トークン数、概算の費用、応答の本文も書きます |
| `middle/requests.jsonl` | ゲーム用の middle が gpt-6-luna に送った要求の記録。送る直前に 1 行ずつ足します。要求の番号 (`request`。run では 1 から数え、middle-once では保存済みの最後の行の番号の次から数えます)、送った時刻 (`t_sent`)、モデル名 (`model`)、reasoning effort (`reasoning_effort`)、呼ばれた理由 (`reasons`)、user メッセージの節の文 (`sections`。送った順に、送ったままの文字列)、送った画像の時刻とファイル名 (`frames`。`middle/calls.jsonl` の `frames` と同じ形) を書きます。変わらない指示 (developer メッセージ)、出力のスキーマ、画像のデータ、API キー、HTTP のヘッダーは書きません。送った後に失敗した要求 (HTTP のエラー、完了しなかった応答、拒否、形の合わない出力) の行も残ります。`--middle fake` では書かず、本体の画面の middle の要求も書きません。追記に失敗しても要求は送り、middle の失敗には数えずに警告を書きます。1 行は節の文を含むため数 KB〜十数 KB になる見込みですが、切り詰めや間引きはしません |
| `middle/system_calls.jsonl` | 本体の画面の middle の呼び出しごとの行 (`kind` が `call`) と、操作の列を送り終えるごとの行 (`kind` が `run`)。「本体の画面の扱い」の節 |
| `progress/state.json` | 画面の停滞の計測の最新の値 (`t`・`static_s`・`no_novel_s`・`window_s`。「画面の停滞の計測」の節)。まだフレームが無いときは無く、surface と middle は要求ごとに、deep のスケジューラーは 0.5 秒ごとに読みます |
| `middle/map_records.jsonl` | middle のマップの記録。現在地の場所の名前とマス、新しく分かった場所のつながりと観察 (マス目型のマップではマスの座標を含みます) を、判断に使った画像の時刻と場面 ID とともに、1 行 1 回の JSON で足します (「middle の実装」の節)。deep の `map` のジョブが読みます |
| `deep/<種類>-<連番>/` | deep のジョブごとのディレクトリー (連番は種類ごと)。`job.json` (きっかけ、時刻、対象の文書の `notes/` からのパス、`map` のジョブで書くマップの型 `map_layout`) を置きます。Claude Code で動かしたジョブには、`stream.jsonl` (Claude Code の stream-json の出力。1 行に、起動からの秒と出力の 1 行) と `result.json` (終了コード、所要時間、費用、最後のメッセージ、エラーで終わったか、拒まれたツールの呼び出し、停止・強制終了したか、標準エラー出力) も置きます。起動前に止めたときは、`result.json` の `error` に理由を書きます |
| `notes/` | 文書 (次の表) |
| `orchestrator/` | Orchestrator 型の記録 (「Orchestrator 型」の節の「Orchestrator 型の記録」の項)。人の初期指示の写し (`instruction.md`。初期指示を渡さなければ無い)、主ループのセッションとターンの記録 (`sessions.jsonl`・`turns.jsonl`・`session-<NNN>/stream.jsonl`)、監視の要求の記録 (`monitor.jsonl`。監視型だけ)、委任の要求の記録 (`delegate.jsonl`。委任型だけ) を置きます。advisor 型では作りません |

`surface.jsonl` に書く画像のファイル名は、その要求で送った画像の保存を予約したものです。書き込みに失敗したときや、終了時に書き終えられずに捨てたときは、その画像はありません。書けた画像は `frames.jsonl` に載ります。画像の保存は裏のスレッドで行い、溜めておける件数 (64 件) を超えた分は捨てて、捨てた件数を `frames_dropped` に書きます。

advisor 型では、`notes/` に起動時に次の文書を作ります。Orchestrator 型では、`notes/` は空のディレクトリーで始め、主ループの Claude Code が書きます。

| ファイル | 内容 |
|---|---|
| `notes/common/controls.md` | 共通の操作説明。surface の押せるボタン (HOME を除く 16 個) を、まだ確かめていない印 `unknown` を付けて並べます |
| `notes/common/tips.md` | 共通の攻略情報 (見出しだけ) |
| `notes/common/box_targets.md` | surface が box で取る対象の共通の一覧。固定の 4 つ (自機・敵・敵の攻撃・目標地点) を `- 名前: 説明` の行で並べます |
| `notes/scenes/<場面ID>/` | 場面ごとの操作説明 (`controls.md`)・攻略情報 (`tips.md`)・タスクのキューの状態 (`tasks.json` と `tasks.md`)・box で取る対象 (`box_targets.md`)。起動時は空で、`tasks.json` と `tasks.md` はタスクのキューの部品が、ほかは deep が書きます。`tasks.md` は、未完了のタスクをキューの順に `- <文>` の行で並べたものです (行き先は書きません。タスクが無ければ空のファイル)。場面の操作説明・攻略情報・box で取る対象が無いか空なら、surface は共通の文書を使います |
| `notes/scenes/<場面ID>/tasks.json` | 場面のタスクのキューの状態。起動時には無く、キューの部品が、その場面のキューが変わるたびに置き換えの書き込みで書きます。形は `{"t": 書いた時刻, "tasks": [{"id", "text", "added_t", "active_s", "cancel_requested_t", "destination"}, ...]}` で、`tasks` は未完了のタスクをキューの順に並べたもの (無ければ空の配列) です。`active_s` は書いた時刻までの続いた秒数、`cancel_requested_t` は取り消しの要求の時刻 (無ければ null)、`destination` は行き先 `{"place": 文字列, "tile": {"x": 整数, "y": 整数} か null}` (無ければ null) です。`destination` のキーが無い項目は、行き先なしとして読みます。surface はこのファイルから先頭のタスクを読み、middle-once はこのファイルからキューを作り直します。どちらも、`notes/` の外を指すシンボリックリンクは無いものとして読みます |
| `notes/strategy.md` | 大方針 (見出しだけ) |
| `notes/advice.md` | 詰まったときの助言 (見出しだけ)。deep の `advice` のジョブが書きます。`## 本体の画面` の節は、きっかけが `system` のジョブが書き、本体の画面の middle が呼び出しごとに読みます |
| `notes/map/` | マップの文書 (起動時は空)。deep の `map` のジョブが、場所とつながりの一覧 `map.json` と、場所ごとの文章 `places.md` を書きます。middle は `map.json` を、大方針と助言の deep は両方を読みます |
| `notes/scene_labels.json` | 場面の名前と場面 ID (`scene-001` の形) の一覧。middle が初めての場面を足します |

ゲームの性質の文書 `notes/game.md` は、起動時には作らず、deep の `game` のジョブが作ります。surface は要求のたびに、middle は実行のたびに読み、deep はどの種類のジョブでも読みます。無いときは、surface は空文字列、middle は「(無い)」として扱います。

### 押せるボタン

surface が決めた操作は、コントローラーに送る直前に、surface の押せるボタンに制限し、段階が play のときだけ送ります。surface の押せるボタンは HOME を除く 16 個で、surface は HOME を押しません (起動時の `notes/common/controls.md` のボタンの並びも 16 個です。Jev へのボタンの問いは、このうち十字キーの 4 方向を除いた 12 個で、十字キーは方向と押し方の 2 問にしています)。外したボタンは `surface.jsonl` の `blocked_buttons` に書きます。本体の画面の操作と、middle のゲーム用の出力の `press_home` で押す HOME は、HOME を含む 17 個を押せます (「本体の画面の扱い」の節)。十字キーの相反する方向 (UP と DOWN、LEFT と RIGHT) を同時に押す指示は、両方とも外します (Jev の surface は十字キーの方向を 1 つの問いで選ぶため、相反する方向を同時に押す指示を出しません。これは、ほかの実装から来る操作のための処理です)。Orchestrator 型では、主ループと監視 (委任型では Jev が選んだ行動) の操作を、surface の制限を通さずに HOME を含む 17 個のボタンで送ります (段階は使わないため、play の確かめもしません)。

短押しは 120 ミリ秒押して離します。秒数の無い押し続けは、次の操作まで押したままにします。Jev の surface が `hold` を選んだボタンには秒数を付けず (`hold_seconds` は空の object です)、次の判断でも `hold` を選ぶと離さずに続けます。秒数を指定した押し続けは、押したレポートの送信が戻ってからその秒数がたったら、次の操作を待たずに離します。押し続けているボタンを次の操作でも押し続けにすると、離さずに、その操作の送信が戻った時刻から新しい秒数を数え直します。秒数が 0 以下・nan・無限大の押し続けは、押さずに外します (`blocked_buttons` には書きません)。秒数の上限は 60 秒で、超えた値は 60 秒として扱います。スティックは次の操作まで倒したままにします。

同じボタンを離してから 100 ミリ秒たつまでは、次の短押しを始めずに待ちます。同じ操作の短押しに十字キーの 2 つの方向 (斜め) があり、どちらかがこの間隔で待つときは、もう片方も同じ時刻まで待って、2 つを一緒に押します。秒数がたって離したボタンは、次の押し続けも 100 ミリ秒たつまで始めずに待ちます。`operations.jsonl` と `surface.jsonl` の操作には、押し続けの秒数を `hold_seconds` (ボタン名 → 秒) に書きます。surface が Jev に送る直近の操作にも、同じ形で秒数を入れます。

### 止まる条件

次のどれかが起きると止まり、`run.jsonl` の `stop` に理由を書きます。片付けの列に ○ を付けた理由では、準備・プレイ・復帰のどれかの段階に入っていれば、すぐには止まらずに片付け (「本体の画面の扱い」の節) をしてから止まります。ほかの理由では、すぐに操作を中立に戻して以後の操作を送らないようにし、3 層を止めます。

Orchestrator 型では段階に入らないため、どの理由でも片付けをせずにすぐ止まります。次の表のうち、surface・middle の失敗の行は advisor 型だけの理由です。Orchestrator 型だけの理由 (主ループと、操作の実行と監視のループの理由) は、「Orchestrator 型」の節の「Orchestrator 型の止まる理由」の項に、委任型の委任のループの理由は「委任型の止まる理由」の項にあります。

| 条件 | `stop` の理由 | 片付け |
|---|---|---|
| Ctrl+C を押した | `interrupted` | ○ |
| キャプチャーの出力が終わった | `capture ended` | |
| 最後のフレームから 2 秒以上、新しいフレームが届かない | `no new frame for 2 seconds` | |
| 起動から 10 秒たっても、最初のフレームが届かない | `no first frame within 10 seconds` | |
| コントローラーのブリッジが復旧できない状態 (第2章の `failed`) になった | `bridge recovery failed` | |
| surface の失敗が `--max-surface-errors` 回続いた | `surface failed <回数> times in a row` | ○ |
| middle の失敗 (ゲーム用の middle と本体の画面の middle のそれぞれ) が `--max-middle-errors` 回続いた | `middle failed <回数> times in a row` | ○ |
| 実行を始めるときの安全の確かめで、3 つの問い (`online`・`purchase`・`system_settings`) のどれかの確率が `--threshold-safety` を超えた | `unsafe screen at start: <問いの名前>` | |
| 実行を始めるときの安全の確かめが失敗した | `safety check failed at start` | |
| 安全の監視で、3 つの問いの同じ問いの確率が、答えのあった確かめで続けて 2 回 `--threshold-safety` を超えた | `unsafe screen: <問いの名前>` | |
| 安全の監視の失敗が `--max-safety-errors` 回続いた | `safety check failed <回数> times in a row` | |
| 安全の監視のスレッドが想定外の例外で終わった | `safety monitor failed: <例外の説明>` | |

準備と復帰の段階には時間切れがありません。ほかのソフトが「プレイ中」で指定のソフトを起動できないときなど、本体の画面の操作で解けない状態では、Ctrl+C (SIGINT) などで止めるまで、本体の画面の middle と deep (きっかけ `system` の助言) を呼び続けます。

ブリッジの復旧中 (第2章の `recovering`) は止まりません。surface は操作を中立に戻し、復旧が終わるまで要求を送りません。安全の監視は、復旧中も続けます。surface は失敗するたびに操作を中立に戻して 1 秒待ちます。middle が失敗した回は、前回の出力を残します。

止まるとき (片付けをしたときは、片付けを終えたとき) は、surface と middle のループ、本体の画面のループ、安全の監視と画面の停滞の計測のスレッドの終わりを最大 5 秒ずつ待ち、実行中の deep のジョブに停止を求めて、5 秒たっても終わらなければ強制終了します。Orchestrator 型では、操作の実行と監視 (委任型では委任) のループ、安全の監視、画面の停滞の計測のスレッドを最大 5 秒ずつ待ちます。主ループのスレッドは、主ループのセッション (claude か codex app-server) を閉じる時間 (標準入力を閉じてから SIGTERM まで、SIGTERM から SIGKILL までの各 5 秒) を足して、最大 15 秒待ちます。`--agent codex` のセッションの起動 (最大 30 秒待ちます) の途中に止めたときは、この 15 秒を超えることがあります。surface と middle と本体の画面の middle は、応答を受け取った時点で停止が決まっていれば、その応答を捨てます。操作を送らず、記録も書きません。`run` の終了コードは、止まった理由が `interrupted` (Ctrl+C) なら 0、ほかの理由では 1 です。片付けをしたときも、片付けを始めた理由で決まります。

## Claude Code に補助コマンドを渡すハーネス (switch2-harness)

`switch2-harness` は、第3章と同じく Claude Code に Switch 2 をプレイさせるための、補助コマンドと指示ファイル (`CLAUDE.md`) を用意するパッケージ ([`src/switch2_harness/`](./src/switch2_harness/)) です。第1章で取り上げた先行研究の手法を要素として足し、要素ごとに有効・無効を切り替えて効果を比べます。要素をすべて無効にすると、撮影とボタン入力のコマンドだけを使う、第3章に近い条件になります。第3章と違うのは、`press` で HOME を押せないこと (HOME 画面に戻るときは `finish` を使う)、人から指示されたとき以外はソフトを終了しないよう `CLAUDE.md` で指示すること、入力と撮影を記録すること、`run` で起動するときに起動した人の設定を混ぜないことです。

映像と入力には第2章のデーモンを使います。デーモン (`switch2-remote-daemon`) は、`ch02_setup` ディレクトリーで先に起動しておいてください。Pico 2 W は、[第2章の README](../ch02_setup/README.md) の「7. Switch 2 で Pico 2 W を 1P に登録する」の手順で 1P にしておきます。2026-11-17 に『ポケットモンスター ファイアレッド』で試したところ、2P のままでも HOME メニューは操作でき、ソフトの起動まで進みましたが、ゲームは入力に応じませんでした。

### 作業ディレクトリーを作る

プレイのたびに、`init` で作業ディレクトリーを作ります。このディレクトリーの中に、設定・指示ファイル・撮影した画像・記録が入ります。`plays/` は Git の管理から外してあります。

```bash
uv run switch2-harness init plays/dq3-baseline --game "ドラゴンクエストⅢ そして伝説へ…"
```

| 引数 | 内容 |
|---|---|
| `DIR` | 作る作業ディレクトリー。存在しないか、空のディレクトリーを指定します |
| `--game NAME` | ゲーム名。指示ファイルに書きます |
| `--goal TEXT` | 目標。省略すると「できるだけ先へ進める」です |
| `--enable NAME` | 有効にする要素の名前。繰り返して複数を指定できます |

作業ディレクトリーには次のものができます。

| パス | 内容 |
|---|---|
| `harness.json` | ゲーム名・目標・有効な要素・作った日時 |
| `CLAUDE.md` | エージェントへの指示。基本のテンプレート (`src/switch2_harness/instructions/base.md`) に、有効な要素の節を足したもの |
| `notes.md` | メモファイル (`notes`) を有効にしたときだけ置かれる。エージェントが Write・Edit ツールで書き込めるのは、このファイルだけ。振り返り (`reflection`) も有効にすると、末尾の「振り返り」の節をハーネスが書き換える |
| `frames/` | `look` で撮影した画像 (`000001.png` からの連番) |
| `multi-frames/` | 複数フレーム (`multi-frame`) を有効にしたときだけ作られる。`look` で続けて撮った 6 枚を縮小して並べた画像 (`frames/` の画像と同じ番号) |
| `records/events.jsonl` | サブコマンドの記録 (1 行 1 件) |
| `records/agent.jsonl` | `run` で起動した Claude Code の出力 (stream-json) |
| `records/agent-stderr.log` | `run` で起動した Claude Code の標準エラー出力 |
| `records/screen-samples/run-<NNN>/` | 停滞の知らせ (`stagnation-alert`) を有効にしたときだけ作られる。`run` の間に裏で撮った画面の記録と、最後の新しい画面の記録 (「停滞の知らせ」の節) |
| `records/reflections/` | 振り返り (`reflection`) を有効にしたときだけ作られる。批評役の入力と出力の記録 (「振り返り」の節) |

### サブコマンド

エージェントが使うサブコマンドは、作業ディレクトリーで実行します。`--workspace DIR` で作業ディレクトリーを指定することもできます。

| サブコマンド | 使う人 | 動作 |
|---|---|---|
| `look` | エージェント | 画面を撮影して `frames/` に保存し、保存した PNG の絶対パスを表示します。複数フレーム (`multi-frame`) を有効にすると、0.2 秒おきに 6 回撮り、6 枚を並べた画像のパスの行も表示します。停滞の知らせ (`stagnation-alert`) を有効にすると、新しい画面が 120 秒出ていないときに知らせの行も表示します。振り返り (`reflection`) を有効にすると、批評を `notes.md` に書いた後の最初の `look` で知らせの行を表示します。行動履歴 (`action-history`) を有効にすると、続けて直近の行動も表示します |
| `press ACTION ARGS...` | エージェント | `tap` / `hold` / `down` / `up` を、第2章のクライアントと同じ書き方でデーモンに送ります。HOME を含む入力と、11 個以上を並べた `tap` は送らずにエラーにします |
| `status` | エージェント | デーモンの動作状況を表示します |
| `finish` | エージェント | 押したままの入力をすべて離してから HOME を押します |
| `init DIR ...` | 人 | 作業ディレクトリーを作ります |
| `run --minutes N` | 人 | 作業ディレクトリーで Claude Code を起動し、N 分たったら止めます |
| `report` | 人 | 記録から実験の集計を表示します。`--json` で JSON にします |

`look`・`press`・`status`・`finish` は、成否によらず `records/events.jsonl` に記録します。記録は要素の有効・無効によらず取ります。

第2章のデーモンは `tap` を送り終えるまで次のコマンドを受け付けず、1 つの入力に約 370 ミリ秒かかります。`press tap` に並べる数を 10 個 (約 3.7 秒) までに限っているのは、`run` を止めたときに、実行中の `tap` が終わってから後片付けの `up ALL` が応答の上限 (10 秒) の中で実行されるようにするためです。

### 実験の実行 (`run`)

`run` は、作業ディレクトリーで Claude Code を headless (`claude -p`) で起動し、指定した分数がたったら止めます。

```bash
uv run switch2-harness run --workspace plays/dq3-baseline --minutes 10
```

| 引数 | 内容 | 既定値 |
|---|---|---|
| `--minutes N` | プレイする分数 (小数可) | なし (必須) |
| `--model MODEL` | Claude Code に渡すモデル | `claude-opus-5-5` (第3章の試行と同じ) |
| `--effort LEVEL` | Claude Code に渡す effort | 指定しない |
| `--max-budget-usd X` | Claude Code に渡す費用の上限 | 指定しない |

プレイ中のエージェントに、起動した人の環境の設定を混ぜないよう、次のように起動します。

- `--restricted` で、ユーザー・プロジェクト・ローカルの設定ファイルを読み込ませません。ユーザー設定で有効にした plugin と hook も読み込まれません。ファイルのツールは作業ディレクトリーの中に限られます。`--settings` で `permissions.blockReadsOutsideWorkingDirectories` を渡すと、cat などの読み取り専用の Bash で作業ディレクトリーの外を読むときも承認が要るようになり、後に書く `dontAsk` で拒否されます
- MCP サーバー (`--strict-mcp-config`)、Skill とスラッシュコマンド (`--disable-slash-commands`、`--disallowedTools Skill`) を読み込ませません。作業ディレクトリーは `ch04_techniques/` の下にあり、Claude Code は親ディレクトリーの `.claude/skills/` も読むため、既存の第4章の Skill を読ませないようにしています
- 環境変数 `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` で、`~/.claude/CLAUDE.md` を含むどの `CLAUDE.md` も読ませず、作業ディレクトリーの `CLAUDE.md` だけを `--append-system-prompt-file` で渡します。自動メモリーも `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` で無効にします
- 子のプロセスには、起動した人の環境変数から、`CLAUDE` で始まる変数 (Claude Code の認証・設定の場所・プロバイダーの選択に使うものを除く) と、`ANTHROPIC_` で始まらない `*_API_KEY` を除いて渡します。Claude Code のセッションの中から `run` を起動しても、そのセッションの変数は子に渡りません
- 子のプロセスの環境変数 `SWITCH2_HARNESS_WORKSPACE` に作業ディレクトリーのパスを入れます。この変数があるとき、`look`・`press`・`status`・`finish` はその作業ディレクトリーだけを使い、別の `--workspace` を指定するとエラーにします。エージェントが別の実験の作業ディレクトリーに画像や記録を書かないようにするためです
- 使える組み込みのツールを Bash と Read に限り (`--tools Bash,Read`)、Bash は `uv run switch2-harness <サブコマンド>` だけを許可します。`--permission-mode dontAsk` で、許可していない呼び出しは確認なしで拒否します。Web 検索はできません
- メモファイル (`notes`) を有効にしたときは、`--tools` に Write と Edit を足し、`--allowedTools "Edit(./notes.md)"` で `notes.md` だけに書き込めるようにします

2026-11-16〜17 に Claude Code 2.1.325 で起動し、次のことを確かめました。

- 読み込まれたツールは Bash と Read だけで、MCP サーバー・スラッシュコマンド・Skill は空、plugin は Claude Code の組み込みのものだけ
- `uv run switch2-harness status` は許可されて実行され、許可したサブコマンドの後ろに付けた出力のリダイレクト (`> out.txt`)・コマンド置換 (`$(...)`)・変数の展開 (`$HOME`・`"$PATH"`・`${USER}`)・`~` と、`cat ~/.bashrc`・Read での `~/.bashrc` の読み取りは拒否される
- 作業ディレクトリーの `CLAUDE.md` の内容がシステムプロンプトに入る
- `uv run switch2-harness status --workspace ..` と、環境変数を書き換えて起動する形 (`SWITCH2_HARNESS_WORKSPACE=/tmp uv run ...`・`env SWITCH2_HARNESS_WORKSPACE=/tmp uv run ...`) は拒否される
- `--tools` に Write と Edit を足して `--allowedTools "Edit(./<ファイル名>)"` を渡すと、そのファイルへの Write と Edit は通り、作業ディレクトリーのほかのファイル (`CLAUDE.md`・`records/` の中など) と作業ディレクトリーの外への書き込みは拒否される
- `--resume` で続けても session_id は変わらず、result の `total_cost_usd` はセッションの累計 (前の起動の分を含む)、`num_turns` はその起動の分になる。`--resume` で起動したプロセスの `--max-budget-usd` は、累計ではなくそのプロセスが使った分と比べられる (累計 0.00015 USD・そのプロセスの分 0.00008 USD で、予算 0.0001 USD の起動が `success` で終わった)

期限と経過時間は、記録の時刻と同じく壁時計 (`time.time`) で計ります。第3章の試行も、撮影のたびに `date` で時刻を取って期限を判断しました。`time.monotonic` を使わないのは、2026-11-17 に WSL2 で確かめたところ、実時間より約 8% 遅く進んだためです (20 分で約 1.5 分の差)。壁時計が NTP などで進んだり戻ったりすると、期限もその分ずれます。

エージェントが期限より前に終わった場合は、残りが 30 秒以上あれば、同じセッションを `--resume` で続けます (最大 20 回)。`--max-budget-usd` は、起動し直しを含めた run 全体の上限です。起動し直すときは、それまでの費用を引いた残りを渡し、残りがなくなったら止めます。

期限になったら Claude Code に SIGINT を送り、20 秒たっても終わらなければ SIGTERM、さらに 10 秒たっても終わらなければ強制終了 (SIGKILL) します。止めた後は、デーモンに `up ALL` を送って押したままの入力を離します。応答を待つのは合わせて 10 秒までです。デーモンが処理中で接続が拒否されたときは、その 10 秒の間に送り直します。

Claude Code の Bash ツールは、コマンドを別のセッションで起動します。2026-11-17 に Claude Code 2.1.325 で確かめたところ、SIGINT と SIGTERM では Claude Code が終わるときに Bash ツールのコマンドも止めました。強制終了する場合は Claude Code がコマンドを止められないため、強制終了の直前に Claude Code の子孫のプロセスとそのセッションを控えておき、強制終了の後に、控えたセッションに残っているプロセスを止めます。

`run` を Ctrl+C・SIGTERM・SIGHUP で止めた場合も、同じ順序で Claude Code を止めてから `up ALL` を送ります。Claude Code は新しいセッションで起動するため、端末の Ctrl+C は Claude Code に直接は届かず、`run` が受け取って止めます。`nohup` で起動したときのように、起動した時点で無視しているシグナルは無視したままにします。

`run` は HOME 画面には戻さないため、プレイを終えるときは人がゲームを終了するか、エージェントに `finish` を指示してください。

期限などで止まったときは `ok run finished reason=<理由> ...` を表示して終了コード 0 で終わり、止まった理由は `reason=` で確かめられます。Ctrl+C で止めたときは `error run interrupted`、SIGTERM・SIGHUP で止めたときは `error run terminated by signal` を表示して、終了コード 1 で終わります。後片付けの `up ALL` の成功を確かめられなかったときは、`ok run finished ...` に加えて `error up ALL after the run was not confirmed: <デーモンの応答>` を表示し、終了コード 1 で終わります。押したままの入力が残っているかもしれないので、デーモンの状態を確かめてください。

| `reason` | 止まった理由 |
|---|---|
| `deadline` | 期限になった (期限より前に終わって、残りが 30 秒未満だった場合を含む) |
| `budget_exhausted` | Claude Code が予算の上限で終わったか、run 全体の残りの予算がなくなった |
| `resumes_exhausted` | 起動し直した回数が 20 回になった |
| `no_session` | 起動し直すためのセッションの ID が、今回の run の出力に無かった |

### 記録の集計 (`report`)

`report` は、`records/events.jsonl`・`frames/` の画像・`records/agent.jsonl` から、実験の集計を表示します。

```text
$ uv run switch2-harness report --workspace plays/dq3-baseline
記録の時間: 21.0 秒
コマンドの回数: run=1 look=6 press=4
error の数: 2
look の間隔: 中央値 3.5 秒 / 平均 4.0 秒 / 最大 6.0 秒
変化なしの look の組: 3 / 4
変化なしが続いた最長の時間: 9.0 秒
press の後も変化なしの組: 2 / 3
エージェント: 起動 4 回 / 応答 12 回 / result 3 回
result を出した起動の分: 費用 1.5000 USD / ターン 6 / 時間 3.0 秒
```

| 行 | 内容 |
|---|---|
| 記録の時間 | 最初と最後の記録の時刻の差 |
| コマンドの回数 | サブコマンドごとの記録の数 |
| error の数 | 失敗した記録の数 (デーモンの error と、press の拒否を含む) |
| look の間隔 | 成功した `look` どうしの時刻の差。エージェントの 1 サイクル (撮影・判断・入力) の長さの目安です |
| 変化なしの look の組 | 続けて撮った 2 枚のうち、画面がほぼ変わらなかった組の数 / 組の数 |
| 変化なしが続いた最長の時間 | 画面がほぼ変わらない組が続いた区間の、最も長い時間 |
| press の後も変化なしの組 | 間に成功した `press` がある組のうち、画面がほぼ変わらなかった組の数 / 間に成功した `press` がある組の数 |
| エージェント | `run` で起動した回数 / Claude Code の応答の数 / 終わったときに出る result の数 |
| result を出した起動の分 | result に書かれた費用・ターン数・時間。費用は、セッションごとに最も大きい値を取って合計する (`--resume` で続けたセッションの費用は累計で書かれ、途中で異常終了した result には 0 が書かれることがあるため)。ターン数と時間は、起動ごとの値を合計する |

画面の変化は、2 枚をグレースケールにして 160x90 に縮小し、明るさの差が 24 を超える画素の割合で測ります。割合が 1% 未満の組を「変化なし」とします。期限で止めた起動は result を出さないことがあり (Claude Code のドキュメントには、SIGTERM で止めると result を記録しないとある)、その起動の分は費用・ターン数・時間に含まれません。起動の回数と応答の数は、result の有無によらず数えます。

`--json` を付けると、同じ集計を JSON の 1 行で表示します。

### 要素

要素は `init --enable <名前>` で有効にします。有効にした要素は `harness.json` に記録され、`CLAUDE.md` にその要素の節が加わります。

| 名前 | 内容 |
|---|---|
| `action-history` | 行動履歴。`look` の出力に、直近の行動と、`press` の前後の画面の変化を付けます |
| `notes` | メモファイル。作業ディレクトリーの `notes.md` に、エージェントが Write・Edit ツールで書き込めるようにします |
| `stagnation-alert` | 停滞の知らせ。`run` の間に裏で画面を撮り、新しい画面が 120 秒出ていないと、`look` の出力に知らせの行を付けます |
| `reflection` | 振り返り。`notes` と一緒に有効にします。`run` の間に 5 分ごとに別の Claude (批評役) に進め方を批評させ、`notes.md` の「振り返り」の節に書きます |
| `multi-frame` | 複数フレーム。`look` のときに 0.2 秒おきに 6 回撮り、6 枚を縮小して 1 枚に並べた画像のパスを、`look` の出力に付けます |

#### 行動履歴 (`action-history`)

`look` が成功すると、保存した PNG のパスの行の後に、直近の行動 (`look` と `press`、最大 20 件) を古い順に表示します。履歴は `records/events.jsonl` から作るので、前の `run` のセッションの行動も含みます。

```text
ok /home/user/ch04_techniques/plays/honogurashi/frames/000044.png
直近の行動 (古い順、最大 20 件。秒数はこの撮影の何秒前か):
- 40 秒前 look 000042.png
- 35 秒前 press hold LS:-1,0 500: 画面の変化 あり
- 20 秒前 look 000043.png
- 15 秒前 press tap A: 画面の変化 なし
- 14 秒前 press tap A: 画面の変化 なし
- 2 秒前 press tap B: error already pressed: B
```

- 画面の変化は、その `press` の直前と直後の撮影 (成功した `look` の画像) を、`report` と同じ方法で比べた結果です。直後の撮影がまだ無い `press` は、今回の撮影と比べます
- 同じ 2 枚の撮影の間に複数の `press` があれば、どれも同じ結果になります
- 直前の撮影が無い `press` (作業ディレクトリーで最初の `look` より前の `press`) は「不明」です
- 失敗した `press` と `look` は、画面の変化の代わりにエラーの応答を表示します

#### メモファイル (`notes`)

`init` で作業ディレクトリーの直下に `notes.md` を置き、エージェントが Write・Edit ツールで `notes.md` だけに書き込めるようにします。`CLAUDE.md` の節では、セッションを始めたら操作の前に `notes.md` を Read で読むことと、分かったことをその場で書くことを指示します。セッションは予告なしに終わるため、後でまとめて書く時間はありません。

同じ作業ディレクトリーで `run` を繰り返すと、`run` ごとに、前の会話を持たない新しいセッションが始まります。前のセッションで分かったことは、`notes.md` を通して次のセッションに渡ります。`run` の中で Claude Code が期限より前に終わり、`--resume` で続けた場合は、同じセッションの続きです。

`notes.md` の最初の内容は、次の 4 つの節の見出しだけです (`src/switch2_harness/instructions/notes-initial.md`)。

| 節 | 書くこと (`CLAUDE.md` の指示) |
|---|---|
| 操作方法 | ボタンの割り当て、会話の送り方、メニューの開き方など |
| ゲームの仕組み | 進め方、場所、物、人物など |
| 試して効かなかったこと | 試した入力と、そのときの場面 |
| 今の状況と次にやること | 今の場面と、次に試すこと。状況が変わったら書き直す |

`notes.md` への書き込みは `records/events.jsonl` には記録されません。Write・Edit の呼び出しは `records/agent.jsonl` (stream-json) に残ります。

#### 停滞の知らせ (`stagnation-alert`)

`run` の間、ハーネスが裏で 0.1 秒おきにデーモンへ `shot` を送って画面を撮ります。撮った画面は 160x90 のグレースケールに縮小し、時刻と一緒に `records/screen-samples/run-<NNN>/` に書きます。`run` を実行するたびに、番号を 1 つ増やしたディレクトリーを作ります。

撮った画面が、同じ `run` でそれまでに撮ったどの画面とも 1% 以上違うとき、その画面を新しい画面とします。違いは、`report` の画面の変化と同じく、明るさの差が 24 を超える画素の割合で測ります。`run` の最初の撮影も新しい画面です。前の `run` の撮影とは比べません。

最後の新しい画面から 120 秒以上たっていると、`look` は保存した PNG のパスの行の後に、次のような行を表示します。秒数は最後の新しい画面からの秒数で、小数は切り捨てます。新しい画面が出るまで、`look` のたびに表示します。行動履歴も有効なときは、この行の後に直近の行動が続きます。

```text
ok /home/user/ch04_techniques/plays/honogurashi/frames/000044.png
停滞の知らせ: 新しい画面が 135 秒出ていません
```

知らせを出した `look` は、`records/events.jsonl` の `look` の行の後に、`command` が `stagnation-alert` の行を足します。`args` は秒数、`reply` は知らせの行、`frame` はその `look` の画像です。`report` のコマンドの回数には、知らせを出した回数が `stagnation-alert=<回数>` として出ます。

`CLAUDE.md` の節 (`src/switch2_harness/instructions/stagnation-alert.md`) には、新しい画面の意味と知らせの出る条件を書き、`look` の出力を `head` などで切り詰めずに読むよう指示します。知らせが出たときに何をするかは指示しません。

| パス (`run-<NNN>/` の中) | 内容 |
|---|---|
| `samples.jsonl` | 撮影ごとに 1 行の JSON。成功は `{"index": 番号, "time": 時刻, "file": ファイル名}`、失敗は `{"time": 時刻, "error": デーモンの応答}`。時刻は、デーモンの応答を受け取った後の `time.time()` の値です |
| `000001.png` から | 縮小した画像。成功した撮影ごとの連番で、失敗した撮影では番号を進めません |
| `last-new-screen.json` | 最後の新しい画面の `{"index": 番号, "time": 時刻, "file": ファイル名}`。新しい画面が出るたびに書き換えます。`look` は、番号がいちばん大きい `run-<NNN>/` のこのファイルを読みます |
| `shot.png` | デーモンに元の大きさで保存させる一時ファイル。撮影のたびに上書きし、記録を止めると消します |

- 撮影の間隔は、撮影を始めてから次の撮影を始めるまでで数えます。撮影に 0.1 秒以上かかったときは待たずに次を撮ります。時計が戻ったときも、0.1 秒より長くは待ちません
- デーモンは映像を毎秒 10 枚 (`--process-fps` の既定) に間引いて最新の 1 枚を持つため、0.1 秒おきより細かく撮っても同じ画面が写ります
- 撮影の間の待ちは `threading.Event.wait` で、待つ長さは `time.monotonic` で計られます。2026-11-17 にこの WSL2 で確かめた範囲では、`time.monotonic` は `time.time` より約 9% 遅く進み、`time.time` で数えると撮れたのは毎秒約 9 枚でした
- 同じく `time.time` は約 30 秒ごとに約 3 秒ずつ飛んで進むため、`samples.jsonl` の `time` は、撮影が抜けていなくても約 30 秒ごとに約 3 秒空きます
- 裏の撮影は、エージェントの `look`・`press` と同じデーモンに送ります。デーモンは接続を 1 つずつ順に処理します
- デーモンの応答を 5 秒待っても返らない撮影は、失敗として次の撮影に進みます
- 記録は、最初に Claude Code を起動する前に始まり、後片付けの `up ALL` の後か、`run` が中断されたときに止まります
- すべての過去の撮影と比べると、撮影が増えるほど 1 枚の判定に時間がかかります。そこで、縮小した画像を強くぼかして 20x12 にした画像どうしの差が小さい過去の撮影 20 枚と、直前の 5 枚を選び、それらとだけ 160x90 で比べます。2026-11-17 に、2 つの `run` で撮った 3 つの記録 (0.1 秒おきの 18838 枚を含む) で、この比べ方の判定がすべての過去の撮影と比べた判定と一致することを確かめました
- 1 枚の判定にかかる時間は、2026-11-17 にこの WSL2 で、記録済みの 0.1 秒おきの撮影 18838 枚を順に流して 2 回測ると、中央値 12〜16 ms、99% 点 30〜53 ms でした。判定は撮影の間隔の中で行うため、撮影と判定を合わせて 0.1 秒を超えた撮影の後は、待たずに次を撮ります
- 新しい画面で見つけられるのは、画面がほとんど変わらない停滞です。画面が変わりながら同じ場所を行き来する停滞では、新しい画面が出続けるため知らせは出ません
- `look` は `run` の外でも、最後の `run` の `last-new-screen.json` を読みます。`run` を終えた後に人が `look` を実行すると、その `run` の最後の新しい画面からの秒数で知らせが出ます

#### 振り返り (`reflection`)

`run` の間、ハーネスが 5 分ごとに別の Claude (批評役) を起動し、プレイ中のエージェントの進め方を批評させます。批評は、ハーネスが `notes.md` の「振り返り」の節に、前の批評と置き換えて書きます。メモファイル (`notes`) と一緒に有効にする要素で、`notes` を有効にせずに `--enable reflection` を指定すると、`init` は `error feature reflection requires notes` を表示して終了コード 1 で終わります。

```bash
uv run switch2-harness init plays/pokopia --game "ぽこ あ ポケモン" --enable notes --enable reflection
```

`init` は、`notes.md` の最初の内容の末尾に「## 振り返り」の見出しを足します。`CLAUDE.md` の節 (`src/switch2_harness/instructions/reflection.md`) では、知らせが出たら `notes.md` を読み直すこと、批評から分かったことを「試して効かなかったこと」と「今の状況と次にやること」の節に書くこと、「振り返り」の節は書き換えないことを指示します。

批評役の起動と渡すものは次のとおりです。

- `run` の開始から壁時計で 5 分ごとに起動します。`run` ごとに数え直します。前の批評が終わる前に次の起動の時刻を過ぎた回は、起動しません
- 渡すもの
  - 直近 5 分に成功した `look` の撮影から、時刻がほぼ等間隔になるように選んだ最大 8 枚 (最後の撮影は必ず入れる)
  - 同じ 5 分の行動 (`look` と `press` の時刻・入力・応答)
  - 前回の批評役を起動した後 (`run` の最初の批評では `run` の開始の後) に `records/agent.jsonl` に書かれた、プレイ中のエージェントの発言
  - その時点の `notes.md`
- 指示は `src/switch2_harness/instructions/reflection-critic.md` です。先へ進んだか、まだ試していない方法、`notes.md` と画面の食い違いの 3 点を、400 字以内の箇条書きで書かせます
- モデルは claude-opus-5-5、effort は medium です。ツールは渡さず (`--tools ""`)、プレイ中のエージェントと同じく、起動した人の設定・`CLAUDE.md`・MCP・Skill を読ませません。撮影は、標準入力の stream-json のメッセージに PNG のまま base64 で入れます。会話はディスクに残しません (`--no-session-persistence`)
- 入力を渡し終えてから 240 秒たっても終わらない批評役は止めます。`run` が止まるときも、動いている批評役を止めます

批評役が返した批評は、次の形で `notes.md` の「振り返り」の節に書きます。節が無ければ末尾に足します。ハーネスは別のファイルに書いてから置き換えるため、プレイ中のエージェントが書きかけの `notes.md` を読むことはありません。ただし、エージェントが読んだ後にハーネスが書き換えると、エージェントの Edit は失敗します。

```markdown
## 振り返り

(run の開始から 10 分の時点の批評)

- この 5 分は、苔の段差と石壁の同じ一画を回っていて、先へ進んでいない
- ...
```

書いた後の最初の `look` は、保存した PNG のパスの行の後 (複数フレームの行と停滞の知らせがあればその後) に、次の行を表示します。

```text
振り返り: notes.md の「振り返り」の節を書き換えました
```

`records/events.jsonl` には、批評を書くたびに `command` が `reflection` の行 (`args` は批評の通し番号) を、知らせを出した `look` の後に `command` が `reflection-notice` の行を足します。`report` のコマンドの回数には、それぞれの回数が出ます。批評役の費用は、`report` の集計にも、`run` の `--max-budget-usd` の予算にも入りません。費用は `records/reflections/critic-<NNN>.jsonl` の result の `total_cost_usd` にあります。

| パス (`records/reflections/` の中) | 内容 |
|---|---|
| `reflections.jsonl` | 回ごとに 1 行の JSON。起動した回は、通し番号・`run` の中の回の番号・時刻・渡した撮影・発言を読んだ範囲 (`agent.jsonl` のバイト位置)・結果 (`written` / `failed` / `timeout` / `stopped`)・批評の本文・かかった秒数。起動しなかった回は `skipped` |
| `critic-<NNN>.jsonl` | 批評役の標準出力 (stream-json)。`NNN` は作業ディレクトリーの中での通し番号です |
| `critic-stderr.log` | 批評役の標準エラー出力 |

2026-11-17 に Claude Code 2.1.326 で、批評役と同じ起動引数に、1280x720 の PNG の撮影 8 枚 (入力の 1 行で約 10.9 MB) を渡したところ、約 11 秒で批評が返り、費用は 0.10 USD でした (Claude Code が計算した推定値)。

#### 複数フレーム (`multi-frame`)

`look` は、デーモンへ `shot` を 0.2 秒おきに 6 回送って画面を撮ります。6 回目の画像は、要素を有効にしないときと同じく `frames/` に元の大きさで保存します。6 枚は 640x360 に縮め、上の段の左から 1・2・3、下の段の左から 4・5・6 の順に並べた 1920x720 の画像にして、`multi-frames/` に `frames/` の画像と同じ番号で保存します。各コマの左上には番号を描きます。

`look` は、保存した PNG のパスの行の後に、並べた画像のパスの行を表示します。停滞の知らせ・振り返りの知らせ・行動履歴の行は、この行の後に続きます。

```text
ok /home/user/ch04_techniques/plays/mahou-joshikousei/frames/000044.png
複数フレーム: /home/user/ch04_techniques/plays/mahou-joshikousei/multi-frames/000044.png
```

- 撮影の間隔は、撮影を始めてから次の撮影を始めるまでで数えます。撮影に 0.2 秒以上かかったときは待たずに次を撮ります。1 回目から 6 回目までは約 1 秒かかり、`look` の応答はその分遅くなります
- 1〜5 回目の画像は、デーモンに `multi-frames/` の一時ファイル (`000044-1.png`〜`000044-5.png`) として保存させ、並べた後に消します。元の大きさで残るのは 6 回目の画像だけです
- `records/events.jsonl` の `look` の行は 1 つだけです。`time` は 1 回目の撮影の前の時刻、`elapsed_s` は 6 回目の応答までの秒数、`frame` は `frames/` の画像です。行動履歴と `report` が画面の変化を比べるのは、`frames/` の画像だけです。振り返りの批評役に渡す撮影も、`frames/` の画像から選びます
- 6 回の撮影のどれかが失敗すると、残りは撮らずにその応答を表示し、終了コード 1 で終わります。`frames/` と `multi-frames/` には画像を残しません

`CLAUDE.md` の節 (`src/switch2_harness/instructions/multi-frame.md`) には、撮り方・並び・番号と、並べた画像を読み、細かい文字を読むときは保存した PNG も開くことを書きます。並べた画像がどんな場面で役に立つか (点滅する表示、動いているものの向きなど) は書きません。

### 既知の制限

- Claude Code を強制終了 (SIGKILL) する場合、子孫のセッションを控えた後に、Bash ツールが新しいセッションで起動したコマンドは止められず、`up ALL` の後に入力を送る可能性があります。強制終了まで進むのは、Claude Code が SIGINT と SIGTERM の両方に 30 秒応じない場合だけです。2026-11-17 に確かめた範囲では、Claude Code は SIGINT 1 回で終わりました
- シグナルを受けてから後片付けに入るまでのごく短い間に、2 回目のシグナルが届いた場合の動作は確かめていません。期限などで `run` のループを抜けた直後の、後片付けの関数に入るまでのごく短い間に最初のシグナルが届いた場合は、後片付けが行われません
- Claude Code を起動している最中に割り込みが届くと、その起動の start / resume が記録されず、`report` の起動の回数が 1 少なくなります
- `run` を SIGKILL で止めると、後片付けは行われません。別のセッションで動く Claude Code は残るため、人が止めてから、`ch02_setup` ディレクトリーで `uv run switch2-remote up ALL` を送ってください
- 振り返り (`reflection`) の批評役を動かす裏のスレッドで例外が起きると (`claude` が見つからない、など)、その `run` の残りの間は批評役を起動しません。`run` は止まらず、標準エラー出力に例外の内容が出るだけです。批評が書かれているかは、`records/reflections/reflections.jsonl` の `written` の行で確かめてください
- 費用の集計と予算の残りは、Claude Code が result に書く `total_cost_usd` (Claude Code が計算した推定値) にもとづきます。Claude Code が result を書かずに異常終了してから起動し直した場合は、その起動の費用が次の起動に渡す残りの予算の計算に入らないため、`--max-budget-usd` をその分超えることがあります
